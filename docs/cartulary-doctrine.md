# Cartulary — Project Doctrine

## What Cartulary is

Cartulary is a **single-file HTML worldbuilding tool**. The application is one HTML file containing the entire substrate: code, styles, dependencies (React, marked, d3, JSZip, fonts), and data model. Open the file in any modern browser, build a world.

The audience is **broad worldbuilding**: novelists, RPG GMs, writers of long-form fiction, conlangers, story-bible maintainers — anyone with hundreds of interconnected entries that need to stay tangled. Not a SaaS, not a virtual tabletop, not a manuscript editor.

The schema-flexible foundation ships with 20 pre-built templates as starting points but expects users to define their own templates as needed. Every built-in template is editable, deletable, or replaceable. (A template promoted into a view stops counting against the user-facing tally. Map left the sidebar for Cartographia in v1.4 and the built-in set in v1.6, when maps became records; Astronomical Body and Language / Glossary left it in v1.5, when their entries became Ephemeris's bodies and Glossopoeia's records. None of the three is among the twenty. Plot Thread and Theme / Motif are, and stay so when v1.7's r016 moves them under Fabula as entries; the entry on templates that leave the sidebar's list has the rule.)

## Why Cartulary exists (positioning)

Most worldbuilding tools fall into two camps. **SaaS platforms** (WorldAnvil, Kanka, LegendKeeper, Campfire, lks.ltd's LoreKeeper, lore-keeper.com) are feature-rich but your data lives on someone else's servers and you pay monthly. **General-purpose tools** (Notion, Obsidian) are flexible but don't understand worldbuilding, so users spend weeks configuring before they actually start building.

Cartulary sits between: local-first like Obsidian (your data, your disk), but ships with worldbuilding-specific schema like the SaaS platforms (so no configuration phase). Schema flexible enough to model unusual settings, opinionated enough that defaults work out of the box.

Built by a worldbuilder who needs the tool, not by someone trying to sell a subscription. The biases reflect that.

## Distribution

- **Free, MIT licensed, ad-free, no premium tier, never will be**
- Distributed via itch.io at `drakhanas.itch.io/cartulary` (name-your-price, defaults free)
- Domain `cartulary.world` registered (will redirect to itch.io)
- Two builds ship together as a versioned `.zip` (e.g. `Cartulary_v1.4.zip`):
  - `Cartulary_v#.#.html` (~1 MB) — JSX precompiled, no Babel runtime. What users actually run.
  - `Cartulary_v#.#_Readable.html` (~4 MB) — JSX preserved with Babel-standalone bundled. The canonical source distribution. Open it in a text editor and read the source as authored.

The dual-build approach is the project's transparency commitment. **The `_Readable` build IS the canonical source distribution.** Anyone can verify the AI disclosure, the architecture claims, and the absence of telemetry by inspection. (Since session 19 the source is developed in `github.com/Drakhanas/Cartulary`, public since the v1.6 ship on 2026-10-23. The Readable build remains the source as shipped, inside the file users download; the repository is the source as worked on, with the build that assembles it and the gates that check it. The transparency claim rests on both, and on the fact that a clean checkout of the tagged tree reproduces the shipped file byte for byte, which the v1.6 release proved on a clean `git archive` before claiming it.)

**Filename convention.** Precompiled build is `Cartulary_v#.#.html`, readable build is `Cartulary_v#.#_Readable.html`, distribution zip is `Cartulary_v#.#.zip`. Working-copy build during development uses `Cartulary_v#.#_Working.html` for staging. The `VERSION` constant in `build_inline.py` rolls all three forward together.

**Mid-development build convention.** During iteration, only stage `Cartulary_v#.#_Working.html` to `/mnt/user-data/outputs/`. The dual-build (precompiled `.html` + `_Readable.html`) is release-prep only — running the inliner mid-development wastes time and clutters the outputs directory. Build the release pair when shipping or when Drak explicitly asks; otherwise the working copy is the deliverable.

## AI disclosure stance

Cartulary is **REAL Rating Level 4**: AI generation of major components or ideas, where the content of the work would have been different if AI was not involved. Disclosed openly and specifically on the itch.io page.

Drak directs design, scope, schema, and QA. AI implements under direction. **Without AI assistance, this project would not exist** — and the disclosure says so explicitly. There's no hedge. The disclosure is structurally backed: the readable build ships the source, so anyone skeptical can inspect what was built and form their own judgment about the human-vs-AI contribution.

The application itself contains **no AI features at runtime**. It does not call any LLM, does not generate content for users, does not phone home. Once on disk, it's a static, deterministic, fully offline application.

## Anti-monetization is structural, not aspirational

Cartulary is free and stays that way. No paid tier, no ads, no analytics, no server, no premium feature being held back. **This commitment is enforced structurally**, not by author intent that could change:

1. **MIT license is irrevocable for shipped code.** Even if intent ever shifted, every release that has ever shipped stays freely forkable forever. There's no take-backs on already-distributed MIT.
2. **The architecture forecloses paywall surface.** Single file, local data, no server, no remote endpoints. There's literally nothing to gate behind a paywall — would have to fundamentally redesign the tool to monetize, at which point it wouldn't be Cartulary.

**Don't soften this framing if it comes up.** The README says "I don't" without hedge. That's intentional. It's not a promise, it's a description of a structural impossibility. Hedging the language ("currently no plans..." / "if those plans ever change...") undermines the actual claim, which is that the structure prevents the change.

## Anti-monetization extends to project-controlled community surfaces

The anti-monetization stance governs every surface the project controls, not just the shipped application. The Cartulary Discord server prohibits paid content distribution: community-built packs shared in the server must be free. The constraint scopes to Discord-as-marketplace; users selling their own packs on itch, gumroad, or elsewhere is their business and outside the project's reach.

The principle applies prospectively to any future project-controlled surface — a website community section, a hypothetical itch.io community board, anything Drak operates as part of the project. These surfaces inherit the stance because they're part of the project's visible register.

A free tool announcing itself as free, with a project-operated channel that hosts paid sales next door, creates register dissonance that erodes the structural claim. Same principle, applied to surfaces rather than code.

## Adversarials never get public notation

External critiques — including from competing tools, reviewers, or anyone framing Cartulary against an outside standard — are never named, quoted, or referenced in public-facing Cartulary materials. This covers the itch.io page, devlogs, README, README screenshots, social posts, and anything else readers see. Internal docs (changelog, doctrine, handoffs, transcripts) may reference outside critiques for context on why specific work happened; public-facing prose cannot.

Even unattributed reference frames Cartulary as reactive to outside pressure rather than authored from intent. The release is the release on its own terms; what motivated specific work belongs to the project's internal history, not the announcement layer. The rule applies whether the critique was public or private, accurate or unfair, recent or old.

When release-prep prose drafts surface a sentence that starts "A recent critique," "Reviewers noted," "Someone pointed out," or any equivalent attribution-shaped opening, delete it. Lead with what the work did, not what prompted it.

## Patch notes describe what ship-to-ship users will see

User-facing patch notes (`.txt` patch notes file, devlog, README "what's new" section, itch.io page "what's new" section) only describe changes that a user upgrading from the previous shipped release will actually experience. Pre-release internal corrections — bugs caught in v1.4 mid-development that never shipped past Drak's working copy — don't surface to users because users never saw the broken behavior. Stay in the changelog as session-level history, stay out of the patch notes.

Two ways to recognize a pre-ship internal correction:

1. The feature being "fixed" was itself new in the same release. A bug in version history's pre-restore safety snapshot path, found during v1.4 development, doesn't ship to users because version history itself ships fresh in v1.4 — there's no v1.3 user who experienced the broken behavior.
2. The fix's wording references "previous behavior" that nobody outside the project saw. If the patch notes have to explain the bug to make the fix make sense, the user probably didn't have it.

Bugs that DID ship to users in earlier releases and are now fixed DO belong in patch notes. The deceased-character detection regression (v1.3 shipped wrong, v1.4 fixes) is a real ship-to-ship fix users will notice. Vertical Timeline silently dropping calendar-date-range fields (v1.3 behavior, v1.4 fixes) is another. The migration-tracker-marker fix (v1.3 fresh worlds could lose customizations on export/import, v1.4 ships with the fix in `makeInitialState`) is another.

When auditing a patch notes draft, the question for each line is: would this user, upgrading from the previous shipped release, observe a behavior change? If no, cut.

*Amended 2026-10-22 (v1.6, Drak's decision):* the notes may carry an Under The Hood section describing how the file is made (the module tree, the build, the gates), even though none of it is visible in the application, because the source is public from v1.6 and a reader of the notes may be a reader of the repository. The section says what changed in how the file is made and what checks it, and says plainly that nothing about it is visible. The ship-to-ship test still governs every line about the application's behavior.

## Standing principles

**Internal IDs preserved on user-facing renames.** Saved worlds load forever. User can rename anything; the underlying ID never changes. Migrations honor this — no schema change can break older saves.

**Defensive validation always before state touches.** Hand-edited JSONs WILL happen. Imports must validate, normalize, and bail-with-clear-error rather than trust-and-corrupt.

**Load is non-destructive; save reconciles.** When loading a world JSON, accept asymmetric or partial data and render what's there. Don't aggressively normalize or mirror data on load — the user may not be ready for changes, and the load path isn't the right place for editorial decisions. Reconciliation (e.g. mirroring spouse declarations across both partners) happens at save time, atomically, when the user has just expressed intent. This makes upgrades from older save formats safe and predictable.

**Per-feature QA after major features.** Severity-coded test checklists in spreadsheet form, structured pass/fail with conditional formatting. Parse passes are not runtime passes — they're necessary, not sufficient.

**Mobile UX deferred indefinitely.** Cartulary is not a phone app. The hover-heavy desktop UI does not translate. Don't try to make it work; the right answer is "this is desktop-shaped on purpose."

**High bar for new templates.** Threshold for adding a new pre-built template: three or more distinctive structured fields, OR native rendering/behavior, OR an absent worldbuilding domain that justifies inclusion. The 20-template default set is "very strong" — push back on additions that don't clear the bar.

**Other Names is not universal.** *(v1.3.)* Applies only to entries that can plausibly have in-world aliases — places get renamed, organizations have abbreviations, characters have epithets, gods have many names, languages have alternative names. **Authorial-tracking artifacts do not qualify.** Plot Thread is the established precedent — a plot thread is the writer's organizational construct, not an in-world thing characters might call by different names. The test: does the entry exist as an in-world thing that someone in the setting might refer to by different names? If yes, Other Names applies. If it's a writer's tracking artifact, skip it.

**Status fields get Other + otherTextField universally.** *(v1.3.)* Every Status field on every built-in template includes "Other" as the final option (after alphabetization) plus `otherTextField: true` so the user can type a custom value when the curated list misses. Type fields follow the same pattern. The escape valve prevents the curated list from feeling restrictive without giving up the structured-data benefits of select-based categorization.

**v1.3 field-order arc.** *(v1.3.)* Canonical sequence applied across the v1.3 built-in uplift pass: **identity** (Other Names or Former Names opener, Type, Status) → **roots/anchors** (genealogical/spatial refs like Parent, Father, Mother) → **quantitative descriptor** (Population, Size, Founded date) → **identity refs** (Allies, Members, Leadership) → **behavioral/cultural axes** (Alignment, Cultural Position) → **temporal narrative** (Origin / History) → **Notes**. Not every template uses every band, but the order is consistent so worldbuilders develop muscle memory for where to find what.

**Type + Scope split when axes are orthogonal.** *(v1.3.)* Some templates have two distinct categorical axes that don't compose well into a single mixed list. Plot Thread is the precedent — narrative-shape (Scope: Main / Subplot / Side Quest / Background / Arc) is perpendicular to story-type (Genre: Heist / Revenge / Tragedy / Coming of Age). Split into two fields when the axes are perpendicular; keep a single Type list when the axes are parallel.

**POV Character pattern.** *(v1.3.)* Single-template entry-ref Character (not multi), positioned above multi-participant fields. Applies wherever a narrative artifact has a designated viewpoint distinct from the broader cast.

**Half-width auto-pair.** *(v1.3.)* Adjacent half-eligible fields auto-pair into side-by-side rows in entry forms. Eligibility is purely type-based: text, number, date, calendar-date, color, url, tags, select, and single entry-ref. Multi entry-refs, textareas, name-history, repeating-group, calendar-date-range, and image are not half-eligible — always full-width. A lone half-eligible field with no half-eligible neighbor auto-expands to full. The rule is universal across built-in and user templates; no flag required. The legacy `halfWidth: true` markers on built-in fields are now inert metadata, kept in place for save-file stability — rendering ignores them. Built-ins were originally designed around a flag-driven version of this rule with half-width fields top-loaded contiguously; that visual arrangement is preserved under the new universal rule.

**Half-width pairing is visibility-aware.** *(v1.3, post-build hotfix.)* Pairing operates on the filtered visible field list, not the raw declared list. Hidden fields (showWhen unmet, secret-gated, empty-suppressed in display mode) are removed before pairing runs. The visible field whose declared pair partner is hidden re-pairs with the next visible half-eligible field, or auto-expands to full if no remaining half-eligible neighbor exists. No blank placeholder slots. Layout reflows as values change in edit mode (toggling a showWhen-controlling value reshuffles pairs from that point down); in display mode, populating or clearing values reflows their section. The earlier "stable layout doesn't reflow" stance produced asymmetric blanks instead — the trade is intentional.

**Concordance positions persist to world JSON.** *(v1.3.)* Manual node positions live in `state.concordance.positions = { [entryId]: {x, y} }`, saved with the world. Drag-end writes positions; force layout only runs for entries without saved positions. Filter toggles and focus mode preserve positions (Level 1 within-session stability). Defensive validation on load strips positions for non-existent entry IDs and malformed `{x, y}` shapes. The feature serves both abstract-graph and spatial-diagram use cases (star maps, faction-power diagrams, planar cosmologies) without requiring a separate "Star Map" view — same surface, different user intent.

**Small default set, unlimited user extension.** For features that would otherwise face open-ended user requests for variants — more templates, more themes, more drawing tools, more pack types — ship a curated built-in set that meets the high bar, plus a JSON spec users can author themselves and import. The system supports unlimited extension; the maintenance burden stays bounded at the built-in set; the polite-no answer to feature requests becomes *"the spec supports it, build your own."* Templates established the pattern (20 user-facing built-in + custom + `cartulary_template_export: 1` envelope with Skip/Replace/Rename collision modal). Packs v1.5 extends it to bundle distribution. The pattern is doctrinal — when a borderline feature comes up, *"is this extensible-via-spec?"* is the test that determines whether the maintenance burden stays bounded or goes open-ended.

**The "10 years for free" filter.** Every feature decision asks: would I maintain this for 10 years, for free, with no users to pay me? If no, don't ship it. This is the load-bearing scope discipline.

**Babel parse validation is non-negotiable.** Run `cd /tmp/babelcheck && node check.js` after every change to the working copy. If it fails, the file is broken. Fix before doing anything else.

**Sub-view zoom uses Ctrl+scroll with a native handler.** *(v1.4.)* Views that support in-view zoom (Chronometric, Vertical Timeline so far) bind their wheel handler via `el.addEventListener("wheel", h, { passive: false })` inside a useEffect, not via React's `onWheel`. React attaches wheel listeners as passive on modern browsers, which silently blocks `preventDefault()` — without `preventDefault` the browser's page-zoom fires and the in-view zoom never sees the event. The native handler reads the latest state through a `wheelStateRef.current = {...}` set on every render so the effect can stay bound once with empty deps. Continuous zoom (Chronometric, fractional 0.1-1000x) and discrete zoom (Vertical Timeline, year/month/day) both use this pattern. Future zoomable views should match.

**Vertical Timeline grouping granularity persists in viewPrefs.** *(v1.4.)* `state.viewPrefs.timelineZoomLevel` holds `"year" | "month" | "day"` (default `"day"`). Ctrl+scroll cycles between them, throttled to ~5 flips/sec so a single trackpad gesture doesn't burn through all three levels. Discoverable button row at the top of the controls. Year-level layout flattens months into a chronological event list under the year header with a compact "Mon D" date in the row's date slot. Month-level keeps the year/month/event hierarchy but drops the per-event "Day N" prefix. Day-level is the v1.3 layout (year → month → event with "Day N"). Picked over ephemeral local state because the user's grouping preference for scan-vs-detail workflows is durable — reopening the view should restore it.

**Chronometric tick generation is calendar-aware below 5-year visible range.** *(v1.4.)* Three modes keyed by `visEnd - visStart`. ≥ 5 years → year ticks at decimal-step scaling (original behavior). 0.4y–5y → month ticks at `viewCalendar.months` boundaries, first month of year gets year label and major-tick styling, others get three-letter month abbreviation. < 0.4y → day ticks decimated to target count, month-start days get "Mon Y" label and major styling, other days show day number only. Tick objects carry `{value, label, major}`; major ticks render with `var(--border2)` at 0.7 width, minor with `var(--border)` at 0.4 width. Max zoom 1000x (up from 50x) so any world size can reach day-level visibility.

**Image field ingestion supports drag / paste / picker with FSAA-or-base64 branching.** *(v1.4.)* The image field editor accepts files via three input methods: drag-and-drop onto the zone, paste from clipboard while the filename input is focused, click the picker button. Ingestion branches on FSAA: with a `dirHandle` connected, the file is written into the linked world-images folder via `dirHandle.getFileHandle(name, {create:true})` using `generateUniqueFilename` for collision avoidance, and the field stores just the filename. Without a `dirHandle` (Safari, Firefox-without-feature-flag, or write failure on a FSAA browser), the file is read via `fileToDataUrl` and stored inline as a `data:image/...;base64,...` URL with a flash warning that this bloats world JSON and pointing to World Settings for the folder-linking remedy. Field value shape is a single string in either mode; downstream consumers (`ImagePreview`, `imageManifestEntry`, the zip-export writer) already branch on `.startsWith("data:")` so both shapes flow through the existing pipeline without parallel code paths.

**Handoff procedure when a session approaches context limits.** *(v1.4.)* When context use crosses ~60% and the user wants to wrap up, produce a four-file handoff package: (1) `handoff.md` covering current state, what landed this session, file paths, open items, and a re-orient sequence for next-session Claude; (2) updated `cartulary-doctrine.md` with any new standing principles or locked design decisions from the session; (3) updated `roadmap.md` reflecting completed items and remaining scope; (4) updated `changelog.md` with a new dated entry for this session's deltas. The working copy at `/mnt/user-data/outputs/Cartulary_v#.#_Working.html` is the fifth artifact, always already staged. The handoff doc points at all four supporting files explicitly. Next session opens with the handoff as the primary entry point; the doctrine/roadmap/changelog give deeper context as needed. Write the handoff BEFORE doing any further code work in the current session so the artifact captures full state with maximum fidelity. **Verification rule:** before producing the handoff, cross-check every command in the release-prep block against `build_inline.py`'s current VERSION constant and emitted filenames, and verify any "status as of" claims in roadmap against the actual session's outcomes. A handoff that requires the next session to catch operational defects is a defective handoff.

**Current moment is stored as Y/M/D in primary's frame, not absoluteDay.** *(v1.4.)* `state.world.currentMoment` shape is `{year, monthIndex, day} | null`. Calendar-position invariance applies to primary-bound dates under primary structural edits — the user-visible "current moment" stays at the same Y/M/D label across a primary month-add/remove/reorder, same way entry-stored dates do. Storing absoluteDay would have been one less indirection on read, but would have made the displayed moment drift to a different Y/M/D after any primary structural edit (the absoluteDay axis is fixed, the Y/M/D mapping shifts). Consumers derive absoluteDay at read via `calendarDateToAbsoluteDay(state.world.calendar, currentMoment)`. Mirrors the choice made for entry `calendar-date` and `calendar-date-range` fields — same primitive, same invariant. Null on fresh worlds; defensive migration coerces wrong shapes to null. No multi-calendar variant (current moment is conceptually a primary-frame anchor); if a user wants the moment in another calendar's framing, that's a display-side derivation, not a storage axis.

**Auto-age person-likeness gate via Status options.** *(v1.4.)* A template is "person-like" for auto-age purposes when its Status field (case-insensitive) has options that include `"Deceased"`. Picked over name-matching `"Character"` because it works for user-renamed character templates, custom person-like templates the user authored, and the existing built-in Character template equally — and naturally excludes Faction, Historical Event, Religion, and other templates that have a `calendar-date-range` field but aren't person-like. The same heuristic also gates `isEntryDeceased`, so the two stay aligned: a template that produces deceased-state has age semantics, a template that doesn't, doesn't. Age computation fires on the FIRST `calendar-date-range` field on the template (matches Linea/Stemma/Concordance-hover lifespan convention). Deceased-without-end-date (Thalwen case) gets no age render — refuses to guess against currentMoment.

**Auto-age has two display surfaces.** *(v1.4.)* The shared primitive is `computeLifespanAge(value, calendar, entry, template, currentMomentDay)`, which returns `{age, isDeceased, approximate, suffix}` or null. Two consumers:

- **Inline suffix on the Lifespan field value.** Suffix string format: `" (age N)"` for living (start→currentMoment), `" (died at age N)"` for deceased (start→end), `"~"` prefix on the number when either endpoint is approximate. Fires in `FieldValueDisplay` only when called from a top-level field render path (entry+template props in scope; group-subfield recursion intentionally skips the suffix).
- **Obituary line in EntryView header band.** Below the `entry-badge` system-metadata strip, above `entry-tags-bar`. Renders only when the computation is `isDeceased: true` — biographical-summary surface for the death-fact. Living characters get no header line (their inline `(age N)` suffix is dynamic-with-currentMoment and reads correctly in field context). Format: `Died at age N` or `Died at age ~N` when approximate. Typography deliberately distinct from `entry-badge`: Cormorant Garamond italic, mixed-case, no letter-spacing — biographical fact, not system metadata. The `margin-top: -10px` pulls it tight against the badge so the two read as a single header band.

The two surfaces reinforce rather than duplicate: the suffix is on the data (here are the dates, here's the age computed from them), the obituary line is on the biography (this person died at this age). Living-character symmetry (a parallel `Age N` header line) is deferred indefinitely — currentMoment-dependent biographical claims feel less stable than the death-fact, and the inline suffix already covers the use case.

**Calendar extensions live on the calendar object.** *(v1.4 post-Kalendarium.)* The three v1.4-post-Kalendarium extensions — `week` (`{daysPerWeek, dayNames}`), `celestials` (array of `{id, name, cycleDays, offsetDays, color, icon}`), and `seasons` (array of `{id, name, startDay, endDay, color}`) — attach to each calendar individually, not at world scope. A multi-calendar world can have a 7-day Imperial calendar with Earth-style moons alongside a 10-day Elven calendar with different moons; each renders independently in its own grid with its own data. Storing per-calendar means no per-calendar/per-world routing decisions at render time and no schema work when calendars are added or removed.

**`ensureCalendarShape` is the canonical seam for adding calendar schema extensions.** *(v1.4 post-Kalendarium.)* Three call sites need to know about every new calendar-scoped field: `migrate()` to backfill existing worlds, `normalizeImportedCalendar` to validate at JSON import time, and `createCalendar` to apply defaults to freshly-created additional calendars. Routing all three through `ensureCalendarShape` means adding a new field only requires editing one helper. Pure-additive (never rejects valid existing data), idempotent (re-running produces the same result), defensive against malformed input (coerces bad shapes to defaults rather than throwing). When a future calendar-scoped feature lands, add to `ensureCalendarShape` first; the three call sites pick it up for free.

**Continuous-week calendar math.** *(v1.4 post-Kalendarium.)* Weekday of any (year, month, day) is `((absoluteDay mod daysPerWeek) + daysPerWeek) mod daysPerWeek`. Defensive double-modulo handles negative absoluteDay values (dates before a calendar's epoch). The calendar grid view renders each month with leading-blank cells before Day 1's weekday column so the week cycle stays continuous across month boundaries — Day 1 of February falls on whichever column follows January's last day, exactly like real-world calendars. Fantasy worldbuilders get familiar weekly rhythm without per-month manual alignment, and there's no special-casing of month transitions in the renderer.

**Five-phase moon glyph taxonomy with symmetric collapse.** *(v1.4 post-Kalendarium.)* Moon phase is computed as `((absoluteDay - offsetDays) mod cycleDays) / cycleDays`, then bucketed to one of eight cycle eighths via `Math.floor(fraction * 8)`, then mapped to one of five glyphs via `BUCKET_TO_PHASE = [0, 1, 2, 3, 4, 3, 2, 1]`. Waxing crescent (bucket 1) and waning crescent (bucket 7) collapse to the same 🌒 glyph; same for half (🌓 — both first and third quarter) and gibbous (🌔 — both waxing and waning). Five phases chosen over eight (which would distinguish waxing/waning emoji-by-emoji) to keep cell-level visual clutter down while preserving the visually-rich four named transition phases on top of new/full. Cap at five moons per calendar to prevent multi-moon cells from overflowing — five is the realistic upper bound for fantasy moon counts and gives the cell substrate predictable max density. Phase glyphs render as OS-native color emoji; per-moon `color` field drives tooltip badge, `icon` field is editor-and-tooltip metadata only (never replaces the phase glyph on day cells).

**Moon phase day boundaries follow 1-indexed lunar tradition.** *(v1.4.)* Day 1 of a cycle = phase 0 (new). Day N maps to absoluteDay (N-1), so phase position = (N-1)/cycleDays. For cycleDays=28 with offsetDays=0, full moon falls on Days 15-18 (bucket 4), NOT Day 14. Matches real-world Hebrew and Islamic calendar tradition where the 15th of the month is the full moon, derived from the ~29.5-day synodic cycle. The folk-math intuition "Day 14 is half of 28 so it must be full" doesn't hold — Day 1 sits at phase 0 and Day 29 sits at next-cycle's phase 0, so the midpoint between them lands on Day 15, not Day 14. When writing test expectations, example cases, or documentation, compute bucket positions explicitly from the formula `bucket = floor(8 * ((absDay - offset) mod cycle) / cycle)` and `Day N → absDay (N-1)` rather than going by symmetric-midpoint intuition. The real-world synodic month being ~29.5 days (not 28) is what makes Day 15 = full feel correct in lived experience — a clean 28-day cycle is a worldbuilder idealization that introduces small drift from physical reality, but the math itself is consistent with both lunar tradition and integer arithmetic. The bucket transitions for cycleDays=28 offsetDays=0 are: Days 1-4 new, 5-7 crescent, 8-11 half, 12-14 gibbous, 15-18 full, 19-21 gibbous (waning), 22-25 half (waning), 26-28 crescent (waning). Day 29 returns to new at the start of the next cycle.

**Seasons use 1-indexed dayOfYear with explicit wraparound.** *(v1.4 post-Kalendarium.)* Each season carries `startDay` and `endDay` as integers in `[1, totalDays]`. When `endDay < startDay`, the season is interpreted as wrapping through year-end (Winter `startDay 335 endDay 59` covers days 335..end-of-year AND 1..59 every year). `getSeasonForDayOfYear` handles both shapes with a single helper. Overlaps allowed (first-defined wins); gaps allowed (no season covers some days). Editor surfaces a "wraps year-end" notice inline when `endDay < startDay` so users know what they just did rather than puzzling over why two visual bands appear. Don't try to auto-normalize wraparound by swapping start/end — the math relies on the original orientation to determine which days are "in" the season.

**Calendar grid year initialization.** *(v1.4 post-Kalendarium.)* The grid's displayed year is `state.viewPrefs.kalendariumGridYear[rowKey]` if set; otherwise the year of `state.world.currentMoment` projected into the calendar's frame (so Imperial's currentMoment year 1024 lands at the equivalent Elven year on the Elven grid); otherwise year 1. Stepping the year via +/- or Jump-to-N writes through to viewPrefs so re-expansion of the same calendar's grid remembers per-calendar — primary at year 100 and Elven at year 50 persist independently. The `↺ Current` button only appears when currentMoment is set and lets users return to the world's "now" anchor across calendar context switches.

**Calendar grid cell-click projects through absoluteDay.** *(v1.4 post-Kalendarium.)* `collectEntryDatesAsAbsoluteDays(entry, template, state)` walks every date-bearing surface on an entry (calendar-date, range start/end, name-history from/to, spouse marriedOn/endedOn, recursive into group subfields) and projects each through the entry's bound calendar to absoluteDay. **Cell visual state layering pattern.** *(v1.4 post-Kalendarium.)* Calendar grid day cells stack three independent visual states without conflict: season tint (0.3 alpha background via `hexToRgba`), has-entries indicator (2px accent border), selected state (solid accent fill plus inverted text, overriding everything else). **Ephemeris is a new consumer of `state.world.currentMoment`.** *(v1.5.)* The pre-existing v1.4 `currentMoment` primitive (Y/M/D in primary's frame, see the earlier doctrine entry for storage rationale) is read by Ephemeris in two places: as the focal point for the default date range in Event mode (`currentMoment ± 100 years` in the primary calendar's year frame) and as the anchor for the "Now" button in Observe. **Ephemeris math depth is full Keplerian, not simplified.** *(v1.5.)* Body positions at a given time are computed via iterative Newton-Raphson solve of Kepler's equation (`M = E - e·sin(E)`, converging in 5-10 iterations for e < 0.9), true anomaly derived from eccentric anomaly, position in the orbital plane rotated to inertial frame via the standard three-rotation chain (Ω about Z, i about X, ω about Z). The simplified-Keplerian alternative — mean longitude as position with a coplanar-circular assumption — was considered and rejected. Three drivers for the choice: (1) eclipse alignment requires real 3D positions; without them, the finder produces phantom eclipses on inclined moons and misses real eclipses at non-zero ascending nodes, undermining the worldbuilding-useful event type. (2) Eccentric orbits (comets, elongated moons) deviate significantly from mean longitude near periapsis, so simplified math would silently misplace them by tens of degrees. (3) The cost delta is bounded — ~50-80 lines of standard textbook math, ~10-20× more floating-point ops per evaluation, still negligible at worldbuilder scales (a 100k-day × 10-body sweep finishes well under a second either way). Eccentricity capped at e < 1 (elliptical only) — parabolic and hyperbolic orbits are different math and not relevant for the worldbuilding use case. The six classical orbital elements (semi-major axis, eccentricity, inclination, ascending node, argument of periapsis, mean anomaly at epoch) were already in the v1.5 schema; no additional schema cost. Eccentricity input clamps to 0-0.99 on save. Phase alignment doesn't depend on the math depth (pure cycle-position modular arithmetic) and works identically under either model.

**Orbital position math is exposed top-level for cross-mode reuse.** *(v1.5 — Ephemeris.)* All orbital math primitives — `solveKeplerEquation`, `eccentricToTrueAnomaly`, `meanToTrueAnomaly`, `computeOrbitalPosition`, `computeBodyPositionAtTime`, `computeRootRelativePosition`, `angleBetweenVectors`, plus `DEG_TO_RAD` / `RAD_TO_DEG` constants — live in a single top-level section, decomposed into single-responsibility functions, exposed as module-scope. Three drivers: (1) every Ephemeris mode that needs positions consumes the same helpers — Compute uses them for alignment math, Observe will use them for SVG rendering, future Event mode lookups same. Single source of truth. (2) Testability — the sed-extract-then-eval pattern can verify code-as-shipped against synthetic and JPL Horizons reference data. Decomposed helpers can each be unit-tested in isolation. (3) Symmetric with AsBo's primary and secondary derived-value pattern (pure functions of body state). The trade is one large module-scope section instead of clean per-mode encapsulation; the trade was correct because position math is shared infrastructure, not a Compute-internal concern. Pattern applies prospectively: any future math infrastructure that more than one Ephemeris mode needs should live at top-level, not buried inside a mode's component tree.

**Alignment finders use period-based sampling for wide events, geometry-aware sampling for narrow ones.** *(v1.5 — Ephemeris.)* Phase and conjunction events span fractions of a body's orbital period (10% of cycle, several degrees of separation); `shortest_period / 100` is a sufficient sample step. Eclipse and nodal events span fractions of a body's angular size or a small angular tolerance — much narrower windows, sometimes orders of magnitude smaller than the orbit. Period-based sampling will miss them entirely. Pattern discovered during r013 eclipse work: Earth-Moon-Sun eclipse events have ~0.04-day windows; the naive period/100 step (~0.275 days for Moon) missed every one. Final formulas: eclipse step = `(approxAng_eclipsed_deg / eclipsingSpeedDegPerDay) / 5`, capped above by `T_eclipsing / 100`. Nodal step = `tolerance × min_period / (5 × 180)`, capped above by `min_period / 100`. Pattern applies prospectively: every new alignment-type proposal must categorize its event window — is it period-fraction (wide, period-based step OK) or geometry-fraction (narrow, need angular-size-derived step)? Pick the matching formula or the finder will silently miss events.

**The body tree is per-mode multi-select, not single-select.** *(v1.5 — Ephemeris.)* `EphemerisBodyTree` accepts `currentMode`, `selectedBodyIdSet`, `eligibilityFn`, and `onToggleBody` props. In AsBo and Observe modes, click on a body sets the focused/edited body (single-select). In Compute mode, click on a body toggles its membership in `currentQuery.bodyIds` (multi-select). The tree dims ineligible bodies (opacity 0.35), blocks clicks on ineligible, and stable-sorts eligible-first within each level. This is per-mode behavior of one component, not multiple components or a wrapping picker layer — the interaction concern lives in props, the tree-rendering concern stays in the component. Adopt this pattern when designing future multi-mode views that share a sidebar tree. Don't proliferate near-duplicate tree components.

**The grid field type is general-purpose engine infrastructure, not a Paradigm one-off.** *(v1.5.)* `grid` is a top-level field type (`FIELD_TYPES`) for 2D tabular data. It was built because the ConLang Paradigm template needs an inflection table, but it clears the bar as a *field type* (the "maintain for 10 years for free" filter, not the template bar) only because it's general — relationship matrices, stat blocks, comparison tables, orthography/script charts all want one. Paradigm is the first consumer, not the justification. Locked design decisions:
- **Axes are per-entry, not per-template-field.** Each entry defines its own rows and columns. Required for paradigms (a noun declension and a verb conjugation are different shapes); also the strict superset — a per-entry grid can replicate a fixed-axis grid by defining the same axes each time, the reverse is impossible. The template author drops a bare `grid` field with no axis config; the entry author shapes it. The per-template (fixed-axis) variant is a v2 maybe, not built.
- **Each CELL chooses its own type.** Not one type for the whole grid. Cell value shape is `{type, value}`. Allowed cell types are exactly five: `text`, `number`, `entry-ref`, `calendar-date`, `calendar-date-range`. Cells default to text; a new cell isn't stored until it carries a non-text type or a value (text+empty stays sparse). Switching a cell's type clears its value (no cross-type coercion).
- **Ref cells target ANY entry — no per-grid or per-cell target config.** A ref cell reuses the unconfigured single-ref `EntryRefEditor` (option c, chosen over a shared grid-level target or per-cell targets). This makes pack import a non-issue: a grid field carries no `refTemplatesId`, so `remapField` has nothing to remap, and cell values (entry ids) never travel in packs anyway.
- **Value shape.** `{ rowAxisLabel, colAxisLabel, rows:[{id,label}], cols:[{id,label}], cells:{ [rowId]:{ [colId]:{type,value} } } }`. Cells key off stable row/col **ids**, not labels or positions — the "internal ids preserved on rename" rule applied to axes, so rename/reorder never disturbs cell bindings. `coerceGridValue` is the defensive read-time normalizer (wraps legacy bare scalars, drops orphaned cells, keeps non-text type choices even when blank). Grid is top-level only — excluded from group subfield dropdowns at every depth.
- **Documented v1 limitations (conscious, not oversights):** grid-cell entry-refs produce edges in the Concordance graph (labeled by the grid field) but NOT in Linea — family roles live on `relationKind` fields, never cells. Grid date cells are covered by the date-integrity walkers but NOT by `collectEntryDatesAsAbsoluteDays` (the day-click popover; see that entry). Number cells store strings (`<input type=number>` convention, same as the number field). Empty non-text cells persist in storage (to retain the type choice).

**Registration is a data contract: non-entry node sources become first-class through a registry, not per-view code.** *(v1.5, r075–r081.)* "Entry" was the only first-class linkable node type in the app: Concordance builds nodes from `state.entries` and its `addLink` guard drops any edge whose endpoint isn't an entry; the entry-ref picker lists only real templates. So any class of objects living in its own state slice — Ephemeris bodies in `state.celestialBodies`, ConLang entities next — was invisible to Concordance AND un-targetable by entry-ref fields. This is a *structural property of the promote-to-view decision*, not an Ephemeris one-off: the moment a view gets its own state surface, its objects fall out of the entry-graph. The fix is a `NODE_SOURCE_REGISTRY` that any such slice registers a descriptor into:

```js
{ id, name, color, icon, refEligible,
  getInstances(state) -> [{id,name,kind}],
  getColor(inst)      -> colorString,
  getEdges(state)     -> [{source,target,label,kind}] }
```

- **Registration is a DATA CONTRACT, not a code API.** A node type is graphable + ref-targetable iff it provides the descriptor, regardless of whether the provider is a core view (satisfies it in code, an adapter over its slice) or — eventually — a pack (satisfies the same descriptor by declaration, once the Packs framework grows past templates-only). The only piece that differs is `getInstances` (core reads a known slice; a pack would ship its own store). The descriptor is kept declarative on purpose so that future is "ship a descriptor," not "rewrite the registry."
- **Registered types present as SYNTHETIC TEMPLATES.** `getRegisteredSyntheticTemplates()` vends `{id, name, icon, color, kind:"synthetic", origin:"builtin", synthetic:true, refEligible, fields:[]}` so the existing templateId-keyed machinery (ref picker, Concordance coloring + legend, wiki-link `nameToId`, click-through via `openEntryFromAnywhere`'s body fallback) reuses with minimal branching. The `synthetic:true` flag is the "skip me" marker for the template editor and migration framework — these types have no editable field schema.
- **Registering buys BOTH halves.** Graphable (contributes nodes + intra-type edges to Concordance — bodies bring `parentBodyId` "orbits" edges, the sector graph) AND ref-targetable (entry-ref fields can point at the type by name). The read side has nothing to show until the author side exists, so they ship together.
- **Packs target registered types by name for free.** A pack's entry-ref field declaring `refTemplates: ["Astronomical Body"]` resolves through the same `fix()` name→id path that handles built-in template names — `canonicalTemplateForReconcile` (r071) already handles the name-vs-resolved-id diff, so re-import doesn't false-conflict. The only obligation is that registered-type names are a **published allow-list** (the pack-authoring contract). Packs need nothing else from the registry: their own instances are entries, already first-class.
- **Where the wall is and isn't.** Real gaps are the *type-general* surfaces: Concordance (read) and the entry-ref picker (author). Correct-by-design (NOT gaps): Linea (kinship is `relationKind` among entries — a star isn't kin) and Chronometric/Timeline (driven by calendar dates bodies/lexemes don't have). Soft optional gaps (manual-linking surfaces, brought in scope for bodies): Stemma nodes and Cartographia pins. Kalendarium already referenced `celestialBodies` by id for moon unification — the prior proof a non-entry slice can be cross-referenced, just done bespoke.
- **First registrant: Astronomical Body.** Body deletion silently scrubs inbound *entry* refs (`scrubEntryRefs`, id-agnostic; intentional deletion isn't data loss, so no dead label) with a "referenced by N entries" count shown before confirm — the count is entry-refs only; Stemma/pin links to a deleted body degrade to their orphan/broken-link state and aren't counted. One node per body record, no dedup.
- **`SYNTH_TPL_ASTROBODY === BODY_REF_SENTINEL` (`"__bodies__"`).** The value-picker half pre-existed from r004; r077 unified the r075 registry id onto it (one id everywhere) and renamed `BODY_REF_LABEL` "Celestial Body" → "Astronomical Body" to match the workspace, keeping "Celestial Body" as a resolving alias. **The label is now a reserved type name** — see the collision watch-pattern below.

**A gate that prints a check but excludes it from the verdict is not a gate.** *(v1.6, session 16.)* The reconstitution gate computed three results and scored its verdict from two of them: `ok = seq_ok and decls_ok`, with `byte_ok` printed and ignored. Because the canonical form drops blank lines before comparing, a dropped or added blank line passes sequence and decl-set untouched, and byte-identity is the only check that can see it. So for twenty r-numbers the gate reported GREEN on exactly the combination the doctrine called a RED. The information was on screen the whole time; a human caught the one real occurrence (the r014 dropped blank) by reading the line, not by the gate failing. Two rules come out of this. First, every check a gate computes either enters the verdict or gets deleted; a printed-but-unscored check is worse than no check, because it reads as coverage. Second, **re-prove the teeth after any change to a gate or to the thing it measures.** The three-probe protocol: drop one code line, drop one BLANK line, rename one declaration; expect a specific failure signature from each; restore and confirm green. The blank-line probe is the one that found this bug, and it is the one most likely to be skipped because it feels redundant.

**A view being contiguous says nothing about whether its sub-modules are.** *(v1.6, session 16.)* Ephemeris was surveyed as a single scattered zone and unified with one gather (r020). Its six proposed sub-modules then turned out to need a second gather (r021), because four of the six were interleaved with each other inside the now-contiguous zone. Contiguity is a property of a specific proposed boundary set, not of a region. When a module is going to be carved as a directory, check the contiguity of the intended parts, not just of the whole, and expect two gather episodes rather than one. The same check applied to glossopoeia found two of five parts scattered, needing its own gather (r022).

**Sub-module groupings are proposals, not constraints, and content should overrule tidiness.** *(v1.6, session 16.)* The manifest proposed ephemeris as six parts with one `orbital-math` group. That group held body-kind taxonomy and a record factory alongside Kepler solvers and alignment finders, and the two halves sat in separate contiguous runs at opposite ends of the zone. Honouring the proposal would have cost a relocation of either 187 or 1,265 lines to produce a file whose contents were never coherent. Splitting into `body-kinds` and `orbital-math` cost nothing, carved with zero relocation, and describes the code better. When a planned grouping requires work to achieve and the work buys only conformance to the plan, change the plan.

**Boundary rule 5: a doc comment can sit behind a blank line, which defeats a walk-back.** *(v1.6, session 16.)* Boundary rule 4 says a doc comment travels with its declaration. Finding where that comment starts by walking backward from the declaration over `//` lines fails whenever the author left a blank line between the comment block and the code. This bit twice in one cut: `EphemerisPlaceholderPane` computed as 36 lines when it is 9 (the other 27 were the *next* block's section header and doc comment), and the Compute block computed as 395 when it is 412 (its section header sits above the first declaration). Both errors were quoted to Drak before being caught. **Print the actual seam lines and read them before slicing.** A computed span is a hypothesis; the eight lines around each cut point are the evidence. This is cheap, and it is the difference between a correct cut and a cut that steals another module's header.

**A pure split that changes no product bytes does not need a browser pass; a gather always does.** *(v1.6, session 16.)* r023 and r024 carved two directories out of the trunk and emitted output byte-identical to the last browser-verified build. The gate proves the enumeration ordered correctly, which is the only thing a directory carve can get wrong, and byte-identity proves the product is unchanged. Asking for a browser pass there is ritual, and ritual verification erodes the meaning of the real ones. The rule is narrow and stays narrow: it applies when byte-identity against the active anchor is exact AND the assembled artifact hashes equal to one that was actually passed. It never applies to a gather, which changes bytes on purpose and is gated on a weaker check.

**Prefer the smaller relocation, except where it costs a temporal-dead-zone argument.** *(v1.6, session 16.)* Established practice (r016, r018) is to move the smaller block. r020 departed from it: unifying the ephemeris zones by moving 187 lines down to the tail was cheaper than moving 1,265 lines up, but tail placement would have put seven const arrows below every consumer and left a spine registry callback reaching forward across thousands of lines. Head placement needs no TDZ reasoning at all. Line count is the tiebreaker between options that are equally safe, not a reason to take on a safety argument. An eval-order argument that has to be re-derived by a future reader is a recurring cost; a few hundred extra moved lines are paid once and gated by multiset.

**Assembly enumeration is the one place to write the ordering rule down explicitly.** *(v1.6, session 16.)* When the module tree gained directories, `module_files()` moved from `glob` to `rglob`. Path ordering happens to produce the correct interleaving of outer and inner `NN` prefixes on its own, but relying on it means the build's correctness depends on `PurePath.__lt__` semantics that nobody reading the file can see. The sort key is now explicit (`f.relative_to(MODULES_DIR).as_posix()`). Corollary: **any code that rebuilds the assembly by hand is a second source of truth and will drift.** The standalone gather-check snippet did exactly this and silently stopped seeing directory parts; it now calls `assemble_body()` instead. One assembly path, called from everywhere.

**An audit that only checks the artifact is half an audit.** *(v1.6, session 16.)* The session-15 turnover was fully accurate about the bundle: every line count, every gate result, every hash held. It contained seven defects anyway, and all of them were internal inconsistencies between one part of a document and another, or claims that had gone stale relative to a fact that was itself recorded elsewhere in the same file. The highest-yield audit move is not re-verifying the artifact, which the gates already cover; it is reading each document against itself and against its siblings. Specifically: a "re-sync owed" list against the actual file states, an ownership map against the full declaration set (which is how `SettingsView` surfaced as unowned), markdown table rows against their own column counts (which is how an invisible decision record surfaced), and a stated exception's scope against the rule's scope.

**A section header is a separate block and does not travel with a relocation.** *(v1.6, session 16 post-turnover audit.)* Boundary rule 4 says a doc comment travels with its declaration, and it does, because the two are adjacent with nothing between them. A section header (`// ─── Name ───`) sits ABOVE the doc comment and is frequently separated from it by a blank, so a relocation that takes the declaration and its doc comment leaves the header behind, labelling whatever now follows. Twelve of the 66 column-0 box-drawing headers in the tree are sheared this way, and at least one was produced by the r013 gather this project ran and documented without noticing. Two consequences. First, **every relocation must decide explicitly whether the section header travels**, the same way it decides where the boundary blanks go. Second, **headers are not trustworthy evidence at a seam**: boundary rule 5 says read the seam lines rather than trusting a computed span, and a wrong header is exactly the kind of plausible-looking evidence that rule was written to guard against. Confirm against declaration names.

**Give a defect class an invariant, not a note.** *(v1.6, session 16 post-turnover audit.)* The first instinct on finding twelve sheared headers (thirteen as first counted; one was wrongly accused, see the next entry) was a doctrine note plus a one-time sweep. That is the wrong shape, because it fixes the instances and leaves the mechanism running: the sweep would have been undone incrementally by the next several gathers, exactly as the previous twelve accumulated. The correct fix pairs a cheap machine-checkable invariant with the cleanup, in that order. `header_pairs()` (the ordered list of section header to next declaration) is the same shape and same rationale as the existing 419-name `decl_names` set: independent of the line-level checks, and able to see a class of damage that is structurally invisible to all of them (a sheared header passes canonical sequence because the line is still present, passes multiset because it is the same line in a different position, and passes byte-identity on a gather because bytes are supposed to move). The cleanup then exists to give the invariant a clean baseline, not as the fix itself. **Generalize: when an audit finds N instances of a defect, ask what check would have caught the first one, and build that before fixing the N.** Otherwise the count is the deliverable, and counts regrow.

**A hedge in a spec document is usually a defect wearing a disguise.** *(v1.6, session 16 second-pass audit.)* A corrected set of carve spans shipped with the note "sizes shift by one depending on which slice owns the boundary blank, so use them as sizes and never as slice boundaries." That reads like appropriate caution and is not: boundary rule 1 already decides blank ownership, so every seam has exactly one correct answer, and the hedge was covering ranges that ended on the boundary blank instead of before it. The tell was checkable and nobody checked it: the ranges overlapped pairwise, and one module's published range and published size disagreed by a line. **When a document hedges a number, ask whether a rule already determines it.** If a rule does, the hedge is an error report in disguise and the number is wrong. If no rule does, write the rule. The same correction overshot in the opposite direction from the previous one, which is the signature of fixing a symptom without deriving the constraint: derive spans FROM rule 1 and verify they tile the arc, rather than measuring and then hedging.

**Do not accuse a correct artifact during a defect sweep.** *(v1.6, session 16 second-pass audit.)* A census of sheared section headers listed thirteen. One of them, `// ─── Marked configuration ───`, correctly heads a `marked.use({...})` call block; it looked like a shear only because the census tool paired headers with the next top-level DECLARATION and a call expression is not one. The proposed remedy included "if it heads nothing, delete it," which would have destroyed an accurate header on the strength of a tool's blind spot. **A sweep's tool defines what it can see, and anything outside that definition reads as a defect.** Before acting on a census, check the tool's coverage against the artifact for at least the items whose remedy is destructive. The blind spot then becomes a specification requirement for the permanent check rather than a deletion.

**An invariant that runs on the assembled body cannot see file placement.** *(v1.6, session 16 second-pass audit.)* The `header_pairs()` check proposed to prevent header shear operates on the concatenated body, where module boundaries do not exist. One item in the census, a header sitting at the end of the wrong file, pairs CORRECTLY at +2 in assembled order; its defect is which file it lives in, and the invariant is structurally blind to it. So the check cannot validate its own cleanup for that item. **State the scope limit at the same time as the check**, and route the out-of-scope class to a separate per-file assertion or to a recorded manual verification. A check whose coverage gap is undocumented is read as covering everything it is named after.

## Template origin (built-in vs user)
*(v1.3.)* Templates carry an `origin` field with values `"builtin"` or `"user"`, orthogonal to the existing `kind` field (`"standard"` vs `"map"`). The two dimensions answer different questions: `kind` describes what kind of system entity this is; `origin` describes where it came from.

- **`origin: "builtin"`** — template was created by `makeTemplateFromBuiltin` from `BUILTIN_TEMPLATES`, or backfilled to builtin during the one-time origin classification (name matches a built-in name or a `TEMPLATE_RENAMES.from` slot)
- **`origin: "user"`** — template was created by `saveTemplate` (template builder) or imported via `insertImportedTemplate`; user is taking ownership of the template

**Migration filter.** Every name-based template matcher inside `migrate()` filters `&& t.origin === TEMPLATE_ORIGIN.BUILTIN` so user-created templates that happen to share a built-in name are never force-merged with canonical schema, force-renamed by TEMPLATE_RENAMES, or have their option lists rewritten by OPTIONS_UPDATES / FIELD_TYPE_CONVERSIONS / FIELD_VALUE_REMAPS / etc. The 13 migration matchers all carry this filter.

**Dedup filter.** The dedup pass keys on `${name}::${origin}` so a user-origin "Character" and built-in "Character" coexist without merging. Only same-origin same-name pairs collapse (those are genuine historical bug-state duplicates).

**Reset behavior.** Reset to Default is gated on `origin === "builtin"` at three layers: render-side button visibility, `analyzeReset` returns null on user-origin, `resetTemplate` returns the unchanged state on user-origin. User-origin templates have no canonical factory schema to reset to.

**Restore Built-ins behavior.** `deletedBuiltinNames` counts a built-in as present only if a builtin-origin template with that name exists. `restoreBuiltinTemplates` is only blocked from restoring a built-in by a builtin-origin same-name template. A user-origin same-named template doesn't block the canonical built-in being restored; they coexist.

**Acknowledged limitation.** Pre-v1.3-protection worlds with a user-created template sharing a built-in name get classified as builtin at the one-time backfill. There's no way to retroactively distinguish them. Users can recover by either deleting + Restore Built-ins (loses their custom data on that template; gets canonical back) or Reset to Default (same outcome). From this version forward, new user templates created via `saveTemplate` get clean `origin: "user"` and the protection works fully.

## Packs framework (v1.5)

A pack is a named reference-set over `state.templates` — `{id, name, description, templateIds:[]}` — never a container or a copy. Templates live in the one flat store; a pack only references them by id. This keeps a single source of truth per template, and the standing "internal ids preserved on rename" rule covers packs for free.

- **Built-ins are never members.** Packs layer over user/imported templates only (`origin === "builtin"` is the guard). The Templates sidebar section always shows built-ins; user templates that belong to a pack move under their pack group(s).
- **A template may belong to multiple packs** (decision, v1.5). It renders under each owning group.
- **Pack delete never cascades.** It removes the pack record only; member templates and their entries survive and fall back to ungrouped Templates. `deleteTemplate` is the only path that takes entries with it — a pack delete must never route there.
- **Pack id is file-stable.** Carried verbatim through export/import so re-import reconciles against the same pack rather than spawning duplicates.
- **Import namespaces deterministically.** Each imported member gets a world id `${pack.id}__${fileTemplateId}`; internal entry-refs (refTemplatesId, legacy refTemplateId, refFilters keys) remap through the file→world map, recursing into groups. The determinism matters: it's what lets re-import land on the same ids and reconcile per template. Same-named templates across different packs coexist (different namespaces), disambiguated in flat pickers by a ` · PackName` qualifier rather than a forced rename.
- **Export keeps template ids** (unlike single-template export, which strips them) — the import namespace + remap key off the in-file ids.
- **Re-import reconcile compares AUTHORED intent, not resolved caches.** *(v1.5, r071.)* The reconcile diff stable-stringifies the file template against the world template to classify new / unchanged / conflict. Naively comparing the raw objects false-flags a conflict on EVERY member of a hand-authored pack after the first world reload: `fix()` resolves label/name-sourced cache keys at load (`showWhen.fieldId` from `fieldLabel`, `dependsOn` from `dependsOnLabel`, `refFilters[*].fieldId`, ref ids from `refTemplate(s)` names) into the stored copy, but a hand-authored file declares those by label with no resolved id, so file `{fieldLabel}` ≠ stored `{fieldLabel, fieldId}`. The export round-trip hides this (export carries the already-resolved copy); hand-authored files — the ConLang pack case — don't. Fix: `canonicalTemplateForReconcile` strips the resolved-cache keys (only when their label/name source is present) from BOTH sides before the diff, so comparison is on authored intent. A genuine local edit still flags, because it alters the authored intent or uses builder-set id-only values the file's label-based declaration doesn't carry. Any future load-time field enrichment must be added to this stripper or it reintroduces false conflicts.
- **v1 won't-have:** no entries/assets/fonts/CSS in a pack; no versioning beyond re-import reconciliation; no inter-pack deps; no nested packs; no enable/disable toggle; no in-app registry or network fetch (sharing is manual file exchange via itch.io + Discord).

**A pack is a themed stack, not a curated built-in set.** *(v1.5, 2026-06-05, from the Space Opera design pass.)* The built-in high bar (3+ structured fields / native render / absent worldbuilding domain) gates the *built-in* roster — the set maintained forever. It does NOT gate pack templates. A pack is opinionated for its genre, and overlapping a built-in is the point: a Space Opera pack ships Vessel even though Vehicle exists, because the pack user wants a coherent sci-fi stack, not a pointer to the generic template. The roster filter is instead: coherent kit + (when the pack doubles as the framework QA vehicle) collective code-path coverage + sane size (4–7, held fluid). **Specialized-slice over self-contained:** a genre pack ships the genre-specialized slices and leans on the genre-neutral built-ins (Faction for orgs, Location for generic places, Race/Species + Creature for biology, Artifact/Weapon for personal gear) rather than re-skinning them — the built-ins are the genre-neutral floor, the pack is the genre layer on top. And don't collapse the app's deliberate entity distinctions into one mega-template even under pack logic: an "Entities" template merging Race/Creature/Character/AI is a worse modeling tool than the existing split; ship the genuinely-missing slice (AI) and lean on the built-ins for the rest.

**Pack file format: single JSON for templates-only.** *(v1.5, 2026-06-05.)* A templates-only pack is pure structured data — one JSON array, human-authorable and diffable, matching the project idiom (JSON for structured data, ZIP only when binary assets are in play, as the world+images export already does). ZIP earns its place only if packs gain assets (fonts/CSS/images), and even then the form is one manifest JSON holding all templates plus an asset directory — never per-template fragmentation (that buys nothing and adds a manifest/ordering layer). Hand-authored packs use **name-based refs** (`refTemplate`/`refTemplates`, resolved to ids every load — works for built-in and intra-pack targets alike), an **explicit `id` on every field** (load-time resolution reads field ids to wire showWhen/cascade/refFilters; import does not generate them), and `refFilters` keyed by target name with `fieldLabel`. `build_pack.py` is the self-validating generator; reuse it rather than editing pack JSON by hand.

**Imported templates must be resolved like loaded ones.** *(v1.5, r082 — found by the Space Opera browser pass.)* `resolveTemplateRefs` wires the label/name forms (`showWhen.fieldLabel`→`fieldId`, `dependsOnLabel`→`dependsOn`, `refFilters[*].fieldLabel`→`fieldId`, `refTemplate(s)` names→ids) into the stored copy. World load runs it; **any path that adds templates to state must run it too**, or those features silently fail — `isFieldVisible` fails OPEN on an unset `showWhen.fieldId` (gate always shows), cascades find no parent value, filters go inert. The bug is invisible to the parse-gate and masked by a world reload (load re-resolves), so it surfaces only on first import. All three pack-import commit paths now resolve the merged set; carry the same rule to any future single-template or bulk import path. (Related round-trip guard: the import id-map skips re-prefixing an id already `${pack.id}__…`, so re-importing an exported pack re-adopts originals instead of double-namespacing into duplicates; and `importWorld` rejects pack/template export envelopes rather than loading them loose as a world.)

**Affordances derive from schema, not per-field authoring.** *(v1.5, r084–r085.)* The editor ref-field hints (dotted underline + hover tooltip naming a ref's target and any filter, on every entry-ref field's label) are generated from the field's `refTemplate(s)`/`refFilters`, not authored per field — so they cover built-in, pack, and user templates uniformly with zero config, editor-only. The generator must handle BOTH ref shapes: built-in/pack fields carry target NAMES (`refTemplate`/`refTemplates`) and refFilters `fieldLabel`; the in-app `MultiTemplateRefConfig` builder stores multi-template targets by ID (`refTemplatesId`, no names) with refFilters `fieldId`, and `fix()` only resolves name→id — so the helper resolves id→name and fieldId→label through the template list. A names-only helper silently reads "any entry" for user-built multi-template refs (the r084→r085 bug).

## Glossopoeia: the ConLang core view (v1.5)

The standing decisions established building the Glossopoeia view (core view r088–r104 and Phase 2 r105–r109, all browser-verified — r106–r109 confirmed 2026-06-22 via a full Ethlinde whole-language import). The schema reference is `glossopoeia-design-handover.md`; the design-phase doctrine block dated 2026-06-18 (later in this file) is the historical design rationale.

**Glossopoeia is a VIEW with its own state slice, not templates.** `state.glossopoeia = { conlangs:[], lexemes:[], phonemes:[], ui:{activeLangId, workspace} }`, exactly as Ephemeris owns `state.celestialBodies`. A Glossopoeia entity is NEVER an entry in `BUILTIN_TEMPLATES` (an early attempt to do that was reverted, r089–r090). Each entity type gets its own slice array (extend the `lexemes`/`phonemes` pattern); every entity except ConLang carries a `langId` to its parent ConLang; records are `{id, langId, name, tags:[], fields:{}}`. Entities render through the existing `EntryForm` with a per-type schema built by a `glossopoeia*Schema(state)` function. These schemas are authored in code and do NOT pass through the migration framework, so they declare `showWhen:{fieldId, values}` and `refTemplatesId:[...]` directly (no `resolveTemplateRefs` step). This is the general pattern for any future view that owns its own data.

**Two built-in `group` fields are now sanctioned: Senses and Word Pieces.** The standing rule "tags and group stay user-only" carries two named exceptions, both on the Lexeme: the **Senses** group (Gloss / Definition / per-sense Part of Speech / Register / Example), and the **Word Pieces** group (r106: Sounds / Role / Affix — how a built word splits into pieces in order, so the syllabifier sees the seams and which piece is the root). Word Pieces was a **deliberate waiver** of the one-group rule, with the cost weighed: the precedent (built-in views get groups when warranted; the flat-schema principle erodes a little) traded for the per-piece Affix edges into Concordance and a clean structured input the syllabifier reads. Subfields of both are frozen on ship. This does NOT generalize further — no third group without a deliberate call, and no other view or built-in template uses `group`/`tags`. The `multiselect` type (r088) remains the built-in-safe fixed-set multi-pick everywhere else. (Engine fact that made the waiver safe: the graph walker, delete-scrubber, and import relink all descend into group subfields, so a `group` can carry an `entry-ref` subfield that graphs and remaps; `SUBFIELD_TYPES` allows everything except group-at-depth-3 and grid.)

**Node-source registration is the seam Glossopoeia entities use** to become ref-targets and graph nodes (same as Ephemeris bodies). Registered as nodes (graphable in Concordance + targetable by entry-ref): **ConLang, Lexeme, Phoneme** (built), and later **Grammatical Value, Inflection Class, Affix, Word-Building Process** (Morphology) and **Writing System** (Orthography). Deliberately NOT nodes (view-internal data only, nothing points at them): the Phonotactics components (Syllable Structure, Stress, Phonotactic Constraint, Phonological Rule), Pronoun Set, the Syntax and Complex-Structures components, Grapheme, Spelling Rule, and Corpus entries. Register a type iff something refs it or it belongs in Concordance.

**The Glossopoeia nav glyph is "α" (LOCKED).** Not a placeholder. The sidebar `VIEW_DEFS` entry uses it.

**`GlossEntityList` is the reusable list-detail for Glossopoeia entity slices.** A component (per-language list + `EntryForm` editor + new/delete, manages its own selection, `onCreate` returns the new id) used by every list workspace from Inventory onward. The **Lexicon keeps its own hand-rolled version** because of the Unassigned bucket (the supersede leaves orphan Lexemes with `langId` null; the Lexicon adds a selector "Unassigned (N)" option, a per-word Move-to-language control, and disables New in Unassigned). Before migrating the Lexicon onto `GlossEntityList`, that bucket logic must be preserved.

**A singular entry-ref repoint must set BOTH the name AND the id.** `resolveTemplateRefs`'s `fix()` derives `refTemplateId` from the `refTemplate` name ONLY when the id is absent — so repointing a singular ref (as the supersede does for the five external language fields) must set `f.refTemplate = "ConLang"` AND `f.refTemplateId = SYNTH_TPL_CONLANG` explicitly, or a stale id survives. Multi refs rewrite names and set `refTemplatesId = null` for `fix()` to re-derive every load. The `byName` sentinel mapping for a registered type's label stays conditional (`if (!(LABEL in byName)) byName[LABEL] = SENTINEL`) so a real same-named user template wins.

**"Longform" in worldbuilding views means `textarea`, not `longform`.** The `textarea` type is the rich longform (wiki-links + images; the 134-use standard). The r086 **`longform`** type is a separate, plainer literal-text field (no wiki-links) with the indent/divider tokens. Glossopoeia overview/notes/definition fields use `textarea`. ConLang Overview was authored `longform` by mistake in the first draft and corrected to `textarea` — the general rule: reach for `textarea` for any view longform unless plain literal text is specifically wanted.

**The Language/Glossary supersede is the entry→slice supersede precedent (mirrors Astronomical Body).** Removing a built-in template and migrating its entries into a view slice: tracker flag, origin-filtered name lookup (`t.name===X && t.origin===BUILTIN`), push to the slice preserving `entry.id`, filter the moved entries out of `state.entries`, filter the template out of `state.templates`, rewrite surviving templates' refs (recursing subfields). Idempotent, lossless (dropped data folds into Notes), IDs preserved. The pre-existing v1.3 migration-framework entries for the removed template are KEPT (they normalize old-world data before the supersede runs; no-op on fresh worlds). Use this shape for any future promote-an-entry-type-into-a-view migration.

**Glossopoeia Phase 2 is all-in-one: build the compute substrates in-tool.** Decided 2026-06-21, over the integration-layer alternative (round-trip the lexicon out to Lexurgy for the sound-change math, import the result back as a child language). The integration route was the stronger argument on paper — Lexurgy is free and Turing-complete, and the moat is the in-world population (cross-type Concordance edges; the apex diachronics outputting a child language living in the same world with cognates auto-linked and the family tree drawn), not the rule math — but Drak chose all-in-one and accepted the per-language QA burden a homegrown engine carries. Keep the paradigm rule mechanism and the IPA rule engine as **separate** rewrites over different data; the sound engine buys nothing toward paradigms, and merging them wastes a build.

**The syllabifier is sonority-based maximal onset (r112), no per-language flag.** Each syllable keeps the largest *rising-sonority* run as its onset and drops the rest into the coda, with sonority read from each Phoneme's **Manner**; a consonant never crosses a Word-Piece seam. So `ranfir` splits `ran.fir` (a nasal can't sit before a less-sonorous f in the onset) and `atra` stays `a.tra` (a stop rising to a liquid is a legal onset). This **replaced the original r109 rule** (plain count-based maximal onset, coda held back only at a seam), which over-pulled on every non-seam case and seeded the lexicon with invented onsets. The r109 rule was a settled decision; it was reopened at r112 because it was the cause of the generator's bad output, and the replacement was prototyped spike-first before the verified function changed (r109 spikes preserved, 114 of 599 Ethlinde splits corrected). Sonority is a general principle, not any language's exact cluster set, so a rising cluster a language happens to forbid can still appear; pinning to the precise set is the deferred exact-cluster refinement (parse the Permitted onset-cluster rule). Inside-a-root breaks with no seam (the Celeban class) fall to the manual override. The earlier per-language "resyllabify forward vs. retain coda" inversion was already wrong before this; both languages obey the one rule.

**A per-record computed value with an override can live outside `fields` (not a schema field, not exported).** The syllabifier's per-word Syllables readout is computed live; its override is saved on the record but is NOT a schema field, so it stays out of the per-type schema and out of the import/export envelope. Use this shape for assistive/derived per-record values that shouldn't become authored data.

**The IPA palette is a `field.ipa` / `schema.ipaName` flag, computed once per active language.** Any Glossopoeia text field flagged `ipa:true` (or a symbol-as-name schema flagged `ipaName:true`) gets an inserter palette in `FieldEditor`, ahead of `WikiLinkInput` (so IPA fields drop wiki-link autocomplete). The symbol list (the active language's phonemes + the full IPA chart) is computed once in `GlossEntityList` / `GlossopoeiaView`, not prop-drilled. Reach for the flag rather than a bespoke input when a new IPA field appears.

**Whole-language `.conlang.json` files are import artifacts, not part of the HTML.** Populating a language at scale (e.g. the Ethlinde + Gutter Elf delivery, 2026-06-22) is done by generating a file for the **r104 per-language import**, not by hand entry and not by changing cartulary.html. Such a build does NOT move the r-counter (the counter increments only on HTML changes). Discipline: build the payload with placeholder `src_` ids, run it through the **real extracted `importConlangPayload`/`glossDeepRemap`** in a Node harness, and assert counts + ref integrity post-remap + grids intact + **no `src_` id leaked** (proof that id remapping and ref rewiring both ran) before delivering. A sociolect/dialect is modeled **lean** for non-phonological divergence — only what differs from the parent, with `varietyOf` (a by-name cross-language link) marking the relation. NOTE (superseded for phonology, see the self-contained-variety principle below, r115): a `varietyOf` carries no executable inventory after import, so any variety that must compute (syllabify, validate, generate, run rules) needs its own copy of the inventory — do not rely on `varietyOf` to carry phonemes. Import order matters: a parent must be imported before any `varietyOf` child, since the link and any cross-language phoneme refs resolve by name. In-world vocabulary (including crude/profane sociolect slang) is preserved verbatim, not sanitized.

## Migration framework patterns

These are the patterns the v1.3 template uplift pass established for handling schema changes against existing user data.

**FIELD_TYPE_CONVERSIONS preferred over DEPRECATED+Notes-prepend** for converting `text` → `select` on category-like values. The conversion preserves old free-text values as `{value: "Other", customText: t}` under the new Other slot — the data stays semantically attached to the same field, accessible in the UI, and doesn't bloat Notes. Faction Type and Magic / Tech System Type are the v1.3 precedents. Required: the new select must have `otherTextField: true` so the customText surface exists.

**DEPRECATED + Notes-prepend as fallback** for text values that don't categorize cleanly (Festival Frequency held things like "every spring equinox at midnight" — not a category) or for true field removal where the old data should survive but doesn't belong on the new schema. Standard "we don't want to break your stuff" data preservation pattern — old values get prepended to Notes with a `{Label}: ` prefix.

**DEPRECATED for unshipped-but-leaked QA cleanup.** When a BUILTIN_TEMPLATES field-add lands in an in-progress working build and gets absorbed by a QA test world via `runFieldAddPass`, then the field gets removed from BUILTIN_TEMPLATES before release, the field stays orphaned on those QA worlds. DEPRECATED_BUILTIN_FIELDS with a data-preserving migrateEntry hook strips the orphan cleanly. Plot Thread Other Names is the precedent.

**Per-rev re-versioning for in-place migration corrections.** When an already-shipped OPTIONS_UPDATES entry's `newOptions` needs correction in place, do NOT edit the original entry. Add a follow-up entry with a fresh rev — `v1.3-scifi` corrected by `v1.3-scifi.1` — using the previously-shipped order as the new `oldOptions` and the corrected order as `newOptions`. Settlement subtype alphabetization is the precedent.

**`runFieldAddPass()` called twice in `migrate()`.** Step-4 (canonical) and step-9.5 (post-DEPRECATED). The second call enables same-label same-template `text` → typed replacement in a single migration pass. Without the second call, the user would have to save and reload to see the replacement field appear.

**`OPTIONS_UPDATES` cascade-select support.** The migration handler optionally takes a `parentValue` parameter to target `field.optionsByParent[parentValue]` instead of root `field.options`. Migration key includes parentValue so cascade slots track independently.

**Template-pass doctrine.** *(v1.3.)* When restructuring a template, the new schema IS canonical. ALL migrations to bring older worlds to that state land in the SAME PASS — schema, option strips, renames, type/multi conversions, value remaps, halfWidth, field-order. No deferred-to-release TODOs. Template is "done" only when reload from any older state produces the canonical result. `FIELD_VALUE_REMAPS` framework handles value-moved-between-fields. `OPTIONS_UPDATES` else-branch strips in append-only mode.

**Non-destructive migration doctrine.** *(v1.3.)* Nothing should ever be destroyed in any migration. If a field changes or is removed, whatever it contained gets appended to the Notes field textarea with a labeled prefix. Mandatory for FIELD_REMOVALS. Forward-looking for other migration frameworks where data-loss edge cases arise (FIELD_VALUE_REMAPS conflicts, FIELD_TYPE_CONVERSIONS that can't fully convert, OPTIONS_UPDATES strips on fields without otherTextField).

**Fresh-world state must carry all migration tracker markers from creation.** *(v1.4.)* `makeInitialState()` wraps its return value in `migrate()` so every per-rev tracker (`state.world.fieldOrderUpdates`, `.optionsUpdates`, `.seededFields`, `.iconMigrations`, `.templateRenames`, all the rest — fourteen trackers total) gets populated with "this migration has run" markers as a side effect of running migrate() on canonical state. Without this, fresh worlds export with empty tracker maps; on reimport, `migrate()` sees no markers and re-imposes canonical schema, silently wiping user customizations (field reorders, deleted built-in fields, edited options) made between creation and any reload. The fix is single-source-of-truth: `migrate()` owns the canonical knowledge of which markers exist, and any future migration framework added later automatically pre-seeds its marker on fresh worlds without parallel edits. Don't manually pre-seed individual trackers in `makeInitialState`.

## HTML export design

These are the locked design decisions for the v1.4 HTML export feature. The export produces a single self-contained `.html` file per world for sharing with non-Cartulary users; read-only artifact, no install required to view.

**Anchor IDs use entry.id, not slugified names.** *(v1.4.)* `<a href="#entry-{entry.id}">` — the same internal-ID-stability principle that governs save-file references applies to in-document navigation. Slugified URLs would be readable but would break when the user renames an entry between exports; entry IDs are doctrine-stable. Anchor IDs are purely internal navigation targets, never exposed to users as URL surface — the file path is the artifact, the fragment is implementation detail.

**Image manifest pattern — async pre-resolution before render.** *(v1.4.)* `collectImageRefsForHtmlExport` walks every entry's field tree (recursing into group subfields) plus `mapData.image` on map-kind entries, collecting a deduped Set of source refs. `resolveImageManifestForHtmlExport` then async-fetches each: data URLs pass through, FSAA filenames fetch through `dirHandle.getFileHandle` + `fileToDataUrl`, missing files resolve to null. Pipeline plumbed through `ctx.imageManifest` (a Map keyed by source string); both `renderFieldForHtml`'s image case and `renderMapHtml` read from the same map. Splits the async work cleanly from the synchronous rendering pass — render-time has no awaits, errors during async resolution don't corrupt half-rendered HTML. Pattern extends to any future export that needs to inline-base64 user-owned binary content.

**Section break design.** *(v1.4.)* Inter-entry separator (within same template group): `※※※※※` (five reference marks). Inter-template separator (between template sections): `⁂⁂⁂⁂⁂` (five asterisms). Both render as `<div class="entry-separator">` / `<div class="template-separator">` with each glyph as a `<span>` child; flex container with `justify-content: space-between` distributes the spans edge-to-edge across the content width — first glyph flush with left margin, last flush with right, equal gaps between. The flex pattern was picked over CSS letter-spacing because Drak's explicit requirement was full-width distribution, which letter-spacing can't deliver. Inter-template separator uses larger font size (24px vs 18px) to signal heavier visual hierarchy. ToC adds a 25%-centered HR between template groups via `::before` pseudo-element with `margin: 0 auto`.

**HTML export trust model.** *(v1.4.)* The exported artifact is designed to be opened by readers who are not the world's author. This is a different trust model from the in-app view, where the user trusts their own content. The export therefore hardens against user-content XSS in places where in-app rendering doesn't: URL field values get protocol-allowlist sanitization (rejecting `javascript:`, `vbscript:`, `data:`, `file:` — dangerous URLs render as `.field-link-blocked` struck-through text instead of clickable links). Markdown-in-textarea raw HTML pass-through is intentionally NOT sanitized; that's a Cartulary-wide trust-yourself feature (legitimate uses include `<sub>`, `<br>`, etc.), and inverting the trust model there would limit legitimate uses. The export's trust hardening is targeted at well-known attack vectors (href protocols), not blanket sanitization.

**Auto-age obituary respects field-level secret status.** *(v1.4.)* The obituary line ("Died at age N") and the inline lifespan-field suffix both derive from the same field — the first `calendar-date-range` on the template. When that field is marked `secret` and secrets are excluded from the view (in-app `!showSecrets`) or export (`!includeSecrets`), the obituary line suppresses; without this guard, the obituary would render the age even though the source data is supposed to be hidden, defeating the field's secret marking. Applies in both `EntryView` and `renderEntryArticleHtml`.

**HTML export modal lives on the Project page.** *(v1.4.)* Not Home, not per-template, not Settings. Drak's call — the Project page had been "neglected and could use the love." World-level export only for v1.4; per-template filtering deferred until someone asks. Modal controls reduce to two when relevant: include-secrets checkbox + render-dates-in dropdown (the dropdown is hidden entirely on single-calendar worlds because there's no choice to make). currentMoment-null warning banner shows when the world contains map entries and currentMoment isn't set — the user can cancel and go set it in Kalendarium, or proceed past the warning with all-pins-rendered as the fallback.

**Map rendering uses image + numbered pin overlay + numbered legend.** *(v1.4.)* The chosen pattern is the hybrid Drak picked over (a) hover-only labels, (b) always-visible labels, (c) numbered-only with no labels. Pins render as numbered circles via absolute-positioned `<a>` (linked) or `<span>` (unlinked/broken) elements over the embedded map image. Title attribute carries the pin's label + linked-entry name + `[permanent]` flag for hover discovery. Numbered legend below the map (`<ol class="map-legend">`) lists each pin with `N. Name → link` — works for print and accessibility where hover-only doesn't. CurrentMoment-aware filtering via the same `isPinVisibleAtAbsDay` helper Cartographia uses in-app; permanent pins always visible. When filtering hides pins, a `.map-filter-note` line below the map reports the count delta. Null currentMoment renders all pins (warned-and-proceed flow from the export modal).

## Presentation conventions for template work

**Half-width pass field tables.** When reviewing or presenting a template's current field state, use a copyable monospace 3-column table — Label / Type / Notes. All field info on ONE line per field (no wrapped lines). Type column shows type with `otherTextField` appended when set (e.g. "select otherTextField"). Notes column shows "half-eligible" for half-eligible types, with "· Other +" appended when otherTextField is set.

**Field order presentation.** When proposing template field reorders, present the proposed list as a labeled monospace table (no numbering). Group with blank lines to indicate semantic clusters (half-width block, identity tail, multi-ref block, descriptive textareas, etc).

**QA sheet visual frame.** *(v1.4.)* Every QA test xlsx Drak gets generated for him carries the alternating-yellow + black-moat fill pattern. The pattern is a focus aid for long manual test runs — strong visual stripes plus a large black surround help keep place and prevent attention drift on row-after-row of similar-looking test items. Specs:

- Header row (row 1): cols 1-7 (TC / Sev / Test / Steps / Expected / Status / Notes) use the warm-dark `FF3D3835` header fill. Cols 8-67 solid black.
- Yellow data rows (first data row, third, fifth, ...): cols 1-7 fill solid yellow (`FFFFFF00`). Cols 8-67 solid black.
- Clear data rows (second, fourth, ...): cols 1-7 unfilled. Cols 8-67 solid black.
- Below last data row: 60 rows of solid black across cols 1-67 (closes the L). Row heights stay at Excel default — visual mass comes from column extent, not row height.

Geometry rationale: black extends 60 cols right of Notes (out to col 67) and 60 rows below the last test, forming an L-shape that wraps the test data into the upper-left corner of the visible viewport. The size is deliberate — 40-cell width was tested and felt cramped; 60 gives a real visual moat that holds focus even on widescreens.

Implementation notes: all fill colors must use 8-char hex with explicit `FF` alpha prefix (`FFFFFF00`, `FF000000`, `FF3D3835`). Without the prefix, openpyxl serializes the value with `00` alpha, and Excel reads `00000000` as the "no fill" sentinel — the black silently disappears. Build helper `apply_frame_fills(ws, n_data_rows)` lives in `build_qa_sheet.py` and is called from `build_tab` after the row-height pass. Conditional formatting on the Status column composes correctly with the yellow base — PASS/FAIL/etc. fills override the yellow when populated.

Reuse: paste `apply_frame_fills` plus the `YELLOW_FILL` / `BLACK_FILL` / column-geometry constants into any new QA-sheet builder script for the project. The pattern is not specific to the calendar-grid sheet — it's the standing visual format for every Cartulary QA sheet Drak runs.

Storing as absoluteDay (rather than Y/M/D in primary's frame) means entry-dating stays stable across primary structure edits: if the user adds a month to primary, anchor.absoluteDay doesn't shift, so additional calendars don't silently re-frame. Primary has no anchor — it IS the absolute frame.

But the settings UI for primary is in Kalendarium, not in the world-settings panel. World-settings has a stub pointing users to Kalendarium. Unified locus for all calendar work; no split UI.
- **Per-view calendar selectors are per-view, not global.** *(v1.4.)* Each cross-entry date-rendering view (TimelineView, ChronometricsView, FamilyView, MapView) carries its own `state.viewPrefs.<viewKey>CalendarId`. Picked over single global because per-view is strictly more capable — a user who wants global-feeling behavior can manually set all four to the same value, but the inverse isn't achievable with single global. Supports specialized workflows like "Chronometric in primary for factual sort, FamilyView in Elven for cultural display" side by side.
- **Reference moment is hybrid edit + pin.** *(v1.4.)* In Kalendarium index view, literal-edit on a calendar auto-pins it as the reference (drives the comparison strip showing each calendar's date at that moment). Explicit pin button per row also available. Hybrid was picked over edit-only or pin-only because both affordances are useful in different workflows; supporting both costs little and surfaces both behaviors visibly.
- **Primary calendar swap on import is intentionally unsupported.** *(v1.4.)* The calendar import collision modal hides the Replace option when the imported name matches primary. Replacing primary would re-frame every entry's stored dates (since primary IS the absolute frame for entry-bound dates with `calendarId: null`), with no way to undo. Rename-to-import-as-additional is the only path for primary-name collisions. User who actually wants to swap primary can do it manually via the editor + conversion modal flow.
- **Two invariants for date operations.** *(v1.4.)* AbsoluteDay invariance governs cross-calendar work: additional calendar anchors, entry rebinds via the EntryForm dropdown, the pre-deletion conversion modal, and cross-calendar sort and projection on Chronometric / Timeline / FamilyView / MapView. Calendar-position invariance (preserve month name + day; roll forward when the named month is removed; skip past months whose day count can't hold the day value; roll to next year's first month if no later month qualifies) governs same-calendar structural edits: month add, remove, reorder, day-count change. The two answer different questions — "where is this moment in absolute time?" vs "where does this position go now that I've edited the calendar?" Consequence: entries' absoluteDay is not preserved across structural edits of their bound calendar; only anchors are. Cross-calendar ordering can shift after primary structural edits when additional calendars exist (an Elven event anchored at a fixed absoluteDay might end up before or after a primary event whose absoluteDay shifted, depending on which way primary's year-length changed). Deliberate trade-off: the absoluteDay-preserving alternative produces user-hostile Y/M/D ("Dec 15 Y2024" becoming something like "Sep 27 Y2212") because year-length changes re-slice the absolute axis. The drift surface is contingent on multi-calendar setups, visible on cross-entry views, and an acceptable cost for structural edits that behave the way a worldbuilder expects. Don't try to "fix" the cross-calendar drift later by switching invariants.

The cell substrate gets more room (three-column month grid layout instead of four) to accommodate OS-rendered emoji at their native size.

- **Stress instrumentation must be flag-gated and not hook-bound.** *(v1.4 post-Kalendarium.)* When adding measurement code or debug surfaces to the working copy, use a plain conditional block (`if (STRESS_MODE && window.__cartularyStress) { ... }`) placed past any early-return in App. Never use `useEffect` for this purpose if its closure references variables declared after an early-return — TDZ fires on the early-return render path because the const was never reached. Hooks placed before an early-return also violate React's hook-order invariant (error #310) when the early-return causes hook counts to differ across renders. The plain conditional is idempotent (each render re-binds the same closures), zero-cost when the flag is off, and indifferent to hook order. - **Centered-bucket convention for quantized continuous celestial values.** *(v1.4 final.)* When quantizing a continuous astronomical fraction (phase, orbital position, alignment angle) into discrete buckets, the bucket boundaries must sit half a bucket on either side of each phase event — `bucket = floor((fraction + 1/(2N)) * N) % N` for N buckets — so the displayed phase event occupies the **center** of its window, not the start. The naive `floor(fraction * N)` puts events at bucket starts, displaying every phase ~half a bucket late (~1.3 days late on a 21-day cycle, ~1.8 days on a 29.5-day cycle). Centered buckets matter for the upcoming Ephemeris work where computed phase event times must align with bucket centers, not edges. Switched from the naive convention during v1.4 final cleanup; pre-stable feature surface, no migration concern. Test for "is this the right convention": at fraction 0.5 the bucket must be N/2 (Full for moon phases), and the bucket centered on Full should contain the day closest to the astronomical peak.
- **Cycle-length fields take tenths precision; phase-offset fields stay integer.** *(v1.4 final.)* For celestial bodies (and any future periodic-cycle abstraction), the cycle length (cycleDays) is a tenths-precision float — enables 29.5-day near-lunar synodic months and similar near-integer cycles — while the offset (offsetDays, the absolute day on which the body was at phase zero) stays integer because it's a snap-to-day anchor. UI input uses `step="0.1"` + `parseFloat` + clamp `>= 1` + `Math.round(x * 10) / 10` to enforce the tenths invariant on writes. Migration rounds existing values to tenths (preserves integers as identity, normalizes out-of-spec precision like 29.5499 → 29.5). `computeMoonPhase` needed no math changes — modulo and division were already float-safe. Pattern extends to future Ephemeris orbital periods.
- **World-replacement operations fire pre-op pinned safety snapshots.** *(v1.4 final.)* World Reset, World Import, and Snapshot Restore all create a pinned snapshot of the current world before swapping state, labeled "Before reset" / "Before import" / "Before restore from \<ts\>". Reset and Import wipe prior history first (since a fresh world's history would be irrelevant); Restore preserves history so the rollback is itself reversible. Pre-restore snapshots are capped at SNAPSHOT_PRE_RESTORE_CAP via `kind: "pre-restore"` tagging + `snapshotEvictPreRestore()` because repeated restores would otherwise accumulate pinned snapshots indefinitely. Pre-reset and pre-import don't accumulate because their wipe-first semantics mean only one of each ever exists at a time. Pre-op safety snapshot failure is surfaced to the user — if `snapshotCreate` returns null during restore, the user is prompted with a confirm explaining the undo path is lost.

- **Forced Alignment is its own workspace, not a Compute tab.** *(v1.5 r045–r047, shipped 2026-05-31.)* The fifth Ephemeris workspace, slotted between Compute and Observe. **Architectural rationale**: read vs write semantics differ fundamentally (Compute is non-destructive analysis; Forced Alignment writes body data); locked-mode behavior splits cleanly (Compute reads work locked, Forced Alignment apply doesn't, so they shouldn't share a tab strip with one half grayed out); eligibility rules differ (Forced Alignment needs parent + parent mass + body sma, stricter than Compute's per-type rules); cross-links to AsBo / Compute / Observe make it a hub, not a Compute subordinate. **State shape**: `state.ephemeris.forceAlign = { alignmentType, bodyIds, targetDate, targetCalendarId, recurInterval }`. Disc coverage isn't enforced either (depends on radii and distances post-apply; verify via a Compute Eclipse query). Math validated end-to-end *(r047)*: three bodies with inclinations 2°/25°/60°, eccentricities 0.05/0.1/0.2, different ω and Ω — after forcing, unit direction vectors `(1.000000, 0, 0)` for all three at the target day.
- **Habitable zone is a derived display, but with three models and a luminosity escape hatch.** *(v1.5 r049, shipped 2026-05-31.)* The HZ default uses Kasting et al. (1993) conservative bounds (`0.95 √L` to `1.37 √L`) — the narrowest defensible range, the "this is definitely the HZ" choice. Per-star `physicalParams.hzModel` field lets the user switch to Kasting/Kopparapu (2013) optimistic bounds (`0.75 √L` to `1.77 √L`, ~25% wider on inner, ~30% wider on outer) or to manual bounds (`hzInnerAU` / `hzOuterAU` set explicitly, formula bypassed). All three are display options the user picks per-star; precedence is manual > optimistic/conservative formula. Independent of model, `physicalParams.luminosity` is an optional L☉ override applied at the M-L step — when set, skips the `L = M^3.5` derivation. **Critical**: the luminosity override decouples L from M. Mass still drives orbital periods (via Kepler), so changing the L override affects HZ width without disturbing any satellite's orbital math. This is the right knob when the worldbuilder wants a brighter sky without breaking their calendar. Real stars deviate from main-sequence M-L (giants, subgiants, pre-main-sequence) so the override is physically defensible, not just narrative. The display caveat in the Derived block tells the user which model is active: `"Kasting (conservative)"` / `"Kasting (optimistic), L override"` / `"manual bounds"`. No migration disruption: `pp.hzModel || "conservative"` and `Number.isFinite(pp.luminosity)` guards mean pre-r049 star bodies load with current behavior unchanged.
- **Apsides language is generic by default — periapsis/apoapsis, never perihelion/aphelion.** *(v1.5 r050, shipped 2026-05-31.)* The terms "perihelion" and "aphelion" specifically mean "closest to / farthest from the Sun" (Greek *helios*). For a moon orbiting a planet they're misnomers — the moon doesn't have a perihelion, it has a periapsis. Using generic terms ("periapsis", "apoapsis") is correct for any parent, marginally more technical-sounding around stars but never wrong. The terms perigee/apogee (Earth-specific) and periselene/aposelene (Moon-specific) are even more correct in their narrow contexts but unworkable as defaults — the generic pair is the right cut. Same rule applies to all derived display labels and any future Compute output. **Field tooltip framing follows the same rule**: orbital-element explanations should give BOTH a planet-scale reference (Earth-Sun = 1 AU) and a moon-scale reference (Earth-Moon = 0.00257 AU) so the copy works regardless of the parent body. Star-specific framing ("Earth-Sun-sized orbit") is misleading when applied to moons; generic framing with multiple scale references is the rule.
- **Chain-break is a first-class diagnostic surface, not a silent fallback.** *(v1.5 r050 + r052, shipped 2026-05-31.)* When `computeRootRelativePosition` fails (because some parent in the chain has no mass set), the body falls through to (0,0,0) in display memos — but the fallback is NEVER shown without a warning. Two surfaces: (1) **AsBo orbital elements block** shows an accent-color warning when the body's immediate parent has no mass, naming the parent and explaining the consequence. (2) **Observe diagram** shows a top banner listing affected bodies, AND r052 extends this to skip rendering broken-chain bodies' orbit rings, trails, and body dots entirely — banner is the only surface. Skipping is right because a fallback (0,0,0) draw at the root star is visually indistinguishable from a real body at that position; the user can't tell what's broken vs what's intentional without the banner doing the work. **Doctrine implication for future Ephemeris features**: any code path that depends on parent-mass-derived values (orbital period, position, etc.) should either (a) gate eligibility on parent mass at picker-time so the user can't even select unusable bodies (Compute does this as of r052), or (b) surface a banner/warning naming the affected bodies. Silent skips that produce empty results are the wrong choice.
- **Force-Align writes are revertable and verifiable through `lastApply`.** *(v1.5 r051, shipped 2026-05-31.)* Forced Alignment is the only Ephemeris workspace that writes orbital data. To make the write reversible without building a general undo system, the Apply pipeline captures a per-body before/after snapshot of *only the fields the apply actually touched* (M₀ always, sma if recurring, Ω if eclipse). Snapshot lives in `state.ephemeris.forceAlign.lastApply` until explicitly cleared. **Revert** restores each snapshotted body's pre-apply values field-by-field — manual edits to other fields (or to bodies that weren't part of the apply) are preserved. **Verify** switches to Compute mode and pre-fills the query with the same bodies, alignment type, and target day, so the user can confirm the alignment shows up under Compute's detection. **Three buttons** (Verify, Revert, Dismiss) render in a banner at the top of the Force-Align workspace whenever `lastApply` is non-null — persists across mode switches and even across the empty-world bridge, so a user can apply, navigate away, come back to revert. Only the MOST RECENT apply is revertable — a second apply overwrites the snapshot. That's an intentional simplification; a real undo stack would be a much bigger feature. **Doctrine implication**: any future Ephemeris workspace that writes data should follow the same lastApply pattern — capture only-affected-fields snapshots, surface a revert affordance, and provide a verification cross-link to a non-destructive workspace.
- **Engineer test-world mean anomalies for deterministic Compute results.** *(v1.5 QA practice, 2026-05-24.)* When building an Ephemeris QA fixture, do NOT use physically-real mean anomalies — real Mercury/Venus/Mars don't align within a 1-year window at the 18° Phase default tolerance (min spread ~36°, Mars too slow), so Compute returns nothing and reads as a code bug when it isn't. Instead set each body's `meanAnomalyAtEpoch` so all converge to phase 0 (perihelion + ascending node) at the start of the test window; with `argOfPeriapsis = 0` and `ascendingNode = 0` every body then sits at `(a,0,0)` from its root → Phase spread 0, Conjunction separation 0, Nodal all-at-nodes, Eclipse magnitude ≈ 1. Keep non-zero inclinations (Nodal eligibility needs > 0) and small eccentricities (predictability). The fixture is engineered for deterministic alignment, not realism.
- **Force-Align fixtures want the OPPOSITE: bodies deliberately UN-aligned.** *(v1.5 QA practice, 2026-05-31.)* Compute fixtures converge everything to phase 0 so a hit is deterministic; a Force-Align fixture must do the reverse — spread `meanAnomalyAtEpoch` across bodies (e.g. 10/40/80/120/…/300) so that *applying* an alignment produces a visible current→new delta. If the bodies are already aligned the preview deltas are ≈0 and the apply/revert path can't be told apart from a no-op. Same fixture should also carry one body per exclusion branch (no parent; parent with no mass; coplanar inclination 0 for the nodal filter; narrative kind; synodic-cycle-only) so eligibility dimming, the Skipped list, and the chain warnings all get exercised from one import.
- **A zero-width Compute date range (start == end) is a valid single-day query.** *(r053, 2026-05-31.)* The four `find*Alignments` finders use `if (dateRangeEnd < dateRangeStart) return [];`. Verify-in-Compute writes `start == end == targetDayAbs` and depends on this. Do not re-tighten to `<=`.

## Project naming

"Cartulary" was chosen via a 10-15 candidate process with due diligence on each. A cartulary is the medieval term for a single bound volume containing all the charters, titles, and privileges of an institution. Maps structurally to the single-file source-of-truth design.

Don't suggest alternative names. The name is locked.

### View naming register

*(v1.4 + v1.5.)* Top-level sidebar views use a scholarly-Latinate register: real Latin or Greek-rooted terms with documented historical meaning in their domain, two-to-five syllables, distinctive enough not to feel generic. Linea (line, family-tree line of descent), Stemma (a stemma, the tree a scholar draws for descent; here a radial mind map, never a family tree), Concordance (index of cross-references), Kalendarium (medieval calendar document), Cartographia (the discipline / curated map collection), Ephemeris (tabulated astronomical positions/events over time). The names lean toward naming the *artifact* rather than the *discipline* (Linea is a line, Stemma is a diagram, Concordance is an index, Kalendarium is a calendar, Ephemeris is a table); Cartographia is a soft exception, naming the discipline instead of the artifact — minor tonal inconsistency, not a real problem.

**The Tiffany issue.** A naming failure mode where a term is genuinely historical and period-appropriate but has been so thoroughly absorbed by modern commercial usage that it can't carry the original register anymore. Named for the medieval given name *Tiffany* (attested from at least the 12th century) which now reads as quintessentially modern-American despite being older than most period-appropriate alternatives. The test: can the term be used in a contemporary commercial context without dissonance? If yes, it has the Tiffany issue. *Atlas* fails this test (Atlas Obscura, Atlas Shrugged, atlas missile, road atlas, every textbook publisher's atlas series). *Cartographia* passes it. *Stemma* and *Concordance* pass it (nobody's named a software company Stemma Inc. or printed a Concordance of US Highways). *Ephemeris* passes it for view-naming purposes — the term appears in modern astronomy-software contexts (JPL ephemeris data, Skyfield ephemeris files) but as a category/datatype reference rather than as a product name, comparable to how "Concordance" appears in modern academic indexing without being a product name. Keep this test in mind for future naming decisions. Some Latin/Greek terms that look like they should fit the register fail on inspection — Codex, Forum, Aegis, Compendium are all real scholarly terms heavily claimed by modern commercial usage.

**Direct-collision variant — worse than Tiffany.** *(v1.5.)* A naming failure mode worse than the Tiffany issue: when a term is already the name of an established software product in the *exact adjacent domain*. Stellarium considered and rejected for the celestial-mechanics view because stellarium.org is well-known open-source planetarium software in the precise adjacent domain Cartulary would be building in. Anyone familiar with the existing Stellarium would expect Cartulary's feature to behave similarly, and the comparison wouldn't flatter Cartulary (the real Stellarium has 25 years of development, full sky rendering, real catalogs). Direct collisions like this make Cartulary look like it's name-jacking. Stronger filter than Tiffany: ask not only "is the term diluted by modern usage" but "is there already a software product with this name in or adjacent to the domain I'm building in." If yes, eliminate it. Astrarium considered as a real-Latin alternative (Giovanni de' Dondi's 14th-century mechanical astronomical clock) but rejected for phonetic awkwardness — the `astr-AR-i-um` consonant cluster doesn't flow even though it matches the `-arium` suffix of Kalendarium. Ephemeris won on phonetic flow and semantic accuracy (the view's output IS an ephemeris in the technical sense).

## What Cartulary isn't (don't drift)

- **Not multiplayer.** No real-time collaboration, no shared editing, no permissions system.
- **Not a cloud service.** No accounts, no sync between devices. Move worlds via JSON export/import.
- **Not a virtual tabletop.** Maps support drawing, painting, stamps, pins, and time-aware filtering, not fog of war, dice, or initiative tracking. *(Amended 2026-10-23: it said maps had no drawing, stale since v1.6's map editor.)*
- **Not a prose tool.** Cartulary plans a story down to its scenes and their beats, with the author's notes on each, and never holds the writing itself: no prose editor, no chapter-by-chapter drafting, no auto-linking from typed text. *(Amended 2026-10-23, Drak's call for v1.7's Letters: it was "Not a writing tool", with no manuscript module.)*
- **Not a phone app.** Mobile UX is deferred indefinitely.
- **Not under active monthly development.** Hobby project. Bug fixes happen when bugs surface. New features happen when Drak wants them. No roadmap promises, no release schedule, no support contract.
- **Not a physics simulator.** *(v1.5.)* Ephemeris stays scoped to: define celestial bodies and their orbits in a world, compute alignment events between them, render the resulting sky. Hard exclusions: no real-star catalogs (Yale Bright Star, Hipparcos), no real-world ephemeris data import (JPL, NASA, Skyfield), no observation simulation (light pollution, atmospheric refraction, twilight phases), no weather, no tides, no astrology, no precession/nutation, no N-body simulation, no animated playback (users step dates, don't watch orbits unfold), no atmospheric scattering, no body shading or lighting realism. The adjacent territory (Universe Sandbox, Stellarium, real-world astronomy software) has effectively unlimited feature surface, and the cumulative pressure to add "just one more thing" is exactly how a focused tool turns into Universe Sandbox-lite. The boundary stays drawn even when individual requests sound small. Test for any candidate Ephemeris feature: is this a worldbuilder need or a physics enthusiast need? The former gets considered; the latter declined.

=== ADDED 2026-06-29 (session 10, v1.6 r001 maps promotion: build-surfaced doctrine) ===

- **A retired system-template KIND is removed regardless of origin, departing from the builtin-only migration-matcher convention.** *(v1.6 r001.)* The standing migration convention spares user-origin templates (the `origin === "builtin"` filter; user templates are never touched by canonical migrations). The maps promotion deliberately breaks that for `kind:"map"`: after the promotion a map-kind template is functionless (its entries are swept into the slice, the kind drives nothing, and `TemplateBuilder` can no longer create one), so a leftover user-origin map template would be an inert orphan, worse UX than removal. Its entries' data is already preserved in the slice before the template is dropped, so nothing is destroyed. The rule generalizes: when a kind is being RETIRED (not renamed, not re-skinned, genuinely removed from the system), strip every template of that kind regardless of origin, because origin-sparing exists to protect user INTENT and there is no intent to protect once the kind does nothing. This is the one case where the builtin-only matcher does not apply; it is not license to touch user templates in ordinary migrations.

- **When a fixed schema cannot literally inherit per-world field ids, preserve VALUES by label-remap, not ids.** *(v1.6 r001; corrects the spec's "preserve field ids" premise.)* Built-in template fields are seeded `fld-<slug>-<rand>`, so every world's copy of the same built-in has DIFFERENT field ids. A promotion that swaps a per-world template for a fixed `*Schema()` therefore cannot carry the old ids onto the new schema, the new schema's ids are constants and the old data is keyed by random suffixes. The migration remaps each value from the old per-world field id onto the fixed schema id by matching field LABEL (the one stable key across worlds), and preserves any unmatched field under its original id with a Notes line. "Preserve ids" in a promotion spec means preserve RESOLUTION (the value still renders in the right field), not literal id identity, which was never achievable. Any future template-to-fixed-schema promotion uses label-remap; do not assume id stability across worlds for built-in fields.

- **De-couple a feature from a shared component with a generic slot, not a kind-check.** *(v1.6 r001, the canvasSlot pattern.)* `EntryView`/`EntryForm` had `isMap` branches that reached into map-specific components (`MapView`/`MapEditor`). Removing the feature's special-casing from a shared component means replacing the conditional branch with a generic render slot (`canvasSlot`) that the CALLER fills, so the shared component stops knowing the feature exists. The map route now supplies the canvas through the slot; entry routes pass nothing. This is the inverse of adding a kind-check: when a shared component accretes per-feature branches, the de-coupling move is a caller-supplied slot, which also leaves the seam open for the next view that needs a canvas without another branch.

- **Extract the real committed migration into a Node harness and assert against synthetic old states before any browser pass.** *(v1.6 r001.)* A data-moving migration is the one place where parse-green proves nothing and the browser happy-path can miss silent data loss (a value dropped, a field mis-keyed, a non-idempotent double-run). The practice: pull the ACTUAL committed `migrate()` block out of the source (not a paraphrase), wrap it with minimal stubs in Node, and run it against hand-built synthetic states covering the builtin case, the custom-template case, the empty case, the malformed-data case, and a double-run for idempotency, asserting value preservation, removal, and stability. This caught nothing only because it was done; it is the verification that browser-smoke-on-one-world cannot give, because the migration's edge cases live in the worlds the tester does not happen to load. Run it before staging, separate from and ahead of the browser gate.

- **An invisible promotion is net-additive; the source only grows.** *(v1.6 r001.)* Promoting an object out of the entry path does not shrink the file, even though it removes the old coupling. The migration, the registrant, the new routing, and the export slice-walks cost more than the branches they replace, and the old machinery (the `kind:"map"` handling) cannot leave until no saved world can still carry it, which under the "load forever" rule is never. Combined with append-only migrations, this means the source grows monotonically: every feature is permanent and every migration accretes. The 2 MB the r001 source crossed is that doctrine working as designed, not the app getting fat. It is also why the byte count is a real, quotable input to the modularization decision rather than a vanity number, and why the single-file constraint should be enforced at DISTRIBUTION (one assembled HTML) rather than at SOURCE.

- **Append-only applies WITHIN the active file; closed versions freeze to per-version archives.** *(v1.6 session 10, amending the session-9 turnover rule as the changelog/roadmap ballooned past navigability.)* The "full integrated documents, history verbatim" rule stands, but "the document" is now per-version, not one monolith. The changelog splits: `changelog.md` holds the CURRENT open version only; each closed version is frozen verbatim to `changelog-vX.Y.md` (e.g. `changelog-v1.5.md`). When a version ships and the next opens, the active file freezes to its own `changelog-vX.Y.md` and a fresh `changelog.md` starts. The roadmap splits once: active `roadmap.md` (forward plan, backlog, standing principles) plus `roadmap-archive.md` (the verbatim "Done -- vX.Y release" retrospectives, which only ever grow and are never read during planning). Turnover delivers the ACTIVE files complete plus any archive that CHANGED this batch; frozen archives are not re-shipped every turnover (they do not change). History is still preserved verbatim and never reworded, it is just relocated out of the working file. The driver: the single changelog crossed ~1,800 lines and the per-iteration verbatim record already lives in `/mnt/transcripts/journal.txt`, so the changelog carrying full closed-release detail in the active file bought nothing but context cost. Archive on version close; keep the active file scoped to the open line.

- **Reference-heavy sections relocate to context-scoped companion files, loaded when relevant, not every session.** *(v1.6 session 10, extending the archive amendment above; supersedes its "standing principles stays in active roadmap" clause.)* Archiving closed-version history was the first cut; the second is pulling the big reference blocks out of the active working files. A section earns relocation when it is consulted in a specific context rather than read top-to-bottom each session, and it has grown large. The splits: `roadmap-principles.md` (the planning/scope/sequencing principles, out of `roadmap.md`); `doctrine-code-watch.md` (the code-review / bug-pattern catalog, loaded when coding); `doctrine-site.md` (cartulary.world build doctrine, loaded during site work). The active `cartulary-doctrine.md` keeps the product/build principles that guide daily decisions plus the dated entries; the active `roadmap.md` keeps the forward plan, backlog, and pointers. This mirrors the modularization philosophy: load the spine plus the one module the task needs, not the whole tree. Pointers stay in the active file so nothing is lost, only deferred. Append new reference content to the companion file, not back into the active file.


=== ADDED 2026-06-30 (session 11, v1.6 pillar 2 phase-1: modularization-method doctrine) ===

- **The spine manifest is step one of modularization, authored before any carve.** *(v1.6 pillar 2.)* The first artifact is not a build-pipeline change and not a module file; it is the manifest: the module list, per-module ownership, the irreducible spine core, and the cross-module seam edges. It exists before a single view is carved because it is the oracle both gates check against (first-step verify: does this context have the whole module; end-step confirm: does the reconstituted whole match). The manifest is updated in the same pass as every split or combine, never out of band, or the gates verify against a lie. Defining the seam IS the carving work; moving the text afterward is trivial. Ground it in the actual source (declaration inventory off the real file), not in memory of the architecture.

- **Size the spine to relief: minimize the core, push everything load-on-demand-able into its own module.** *(v1.6 pillar 2; Drak's call over a maximal-spine reading of the frozen plan.)* The justification for modularization is per-session context cost, so the win is measured by what a typical editing session must load, not by file count. The spine core is the irreducible universal set: the `App` shell + router, `Sidebar`, the node-source registry, the state factories, and the constant tables. Anything else that a given task does not need is its own module. More, smaller modules beat fewer large ones for AI-assisted editing, because the load granularity is what controls context. A maximal spine caps the win before any carve runs.

- **A central function that runs once on load and is never touched during editing is a COMPANION, not spine, however large or central.** *(v1.6 pillar 2; `migrate`.)* `migrate` is 5,511 lines and is called by the registry-bearing core, which reads as "irreducibly central." But centrality at runtime is not the test; what a typical editing session must LOAD is. `migrate` runs once, on load, and no view-editing task touches its body (only `App` calls it). So it is a companion: loaded whole for migration-work sessions, excluded from every view-editing session. It cannot be split (its steps are an order-dependent version-era sequence; later steps assume earlier ones ran), but it can be fully lifted out of the core. Splittable and liftable are different properties; a thing can be one without the other.

- **Static content data is a data module behind its sole consumer, not spine.** *(v1.6 pillar 2; `HOME_SECTIONS`.)* `HOME_SECTIONS` is 1,328 lines of help/reference text consumed only by `HomeView`. Size plus single-consumer plus zero-logic equals a data module that loads only when its consumer is in play. The `HomeView` component (small) can stay near the shell; its data does not ride along into every other session. Separate the data from the shell that renders it.

- **Module ownership is decided by caller-trace, not by where the code physically sits.** *(v1.6 pillar 2; the "stemma" calendar helpers and the pre-`App` orphan block.)* Three calendar-import helpers sat in the stemma region but were called by the date math, `migrate`, `App`, and `CalendarEditor`: they are calendar-engine, misfiled. The pre-`App` orphan block looked like one pile but caller-trace split it cleanly: four file helpers used across export + image editors + `App` (a standalone `io-utils` module) versus three ref-integrity helpers used by delete handlers and `migrate` (folded into `field-system` next to the existing ref family). Physical adjacency in the source is an accident of edit history; ownership follows the call graph. Trace callers before assigning a module.

- **Gather before you carve: relocate scattered module members into one contiguous run, as a pure-relocation pass, before any carve.** *(v1.6 r002, r003.)* A module whose members are scattered across the body cannot be carved by a contiguous-range slice without dropping pieces. The fix is a relocation pass that gathers each module's members adjacent to its main cluster, changing only position, not code. Proof that it is pure relocation: the multiset of non-blank code lines and the set of top-level declaration names are identical before and after (only ordering changed). Then parse gate, then browser-verify. Five gathers found this release; all resolved across r002/r003. Do the gather as its own r-cut, separate from the carve, so the relocation is verified invisible before any structural split rides on it.

- **Relocation is eval-order-safe only for definitions with no definition-time external reference, and the parse gate does not catch a violation.** *(v1.6 r002, r003.)* A moved function declaration, component arrow, or literal-initialized const is safe to relocate anywhere: its body resolves references lazily at call or render time, so nothing it needs has to precede its new position. A const whose initializer evaluates another declaration at module-eval time is NOT freely movable (temporal-dead-zone throw if it lands before its dependency). The parse gate proves syntax, not eval order, so this is verified by hand: confirm every mover is a function/component/literal before trusting parse-green plus browser-happy-path. Cartulary's movers were all in the safe class; the one source-order use-before-define (`ensureCalendarShape` used by the date math, defined just below it) is a lazy call inside a function body, the same invariant the browser-verified original already relied on.

- **Data-consolidation and code-layout-consolidation are different operations; doing one does not do the other.** *(v1.6 r001 vs r002.)* r001 unified the maps DATA (one `state.cartographia` slice) and rewrote `CartographiaIndexView`'s internals in place, but left its JSX definition ~3,800 lines from the canvas components it belongs with. Consolidating the data model said nothing about where the components are defined. The layout gather (r002) was a separate pass. Do not assume a data-model change tidied the source layout; the two are orthogonal and each needs its own pass.


=== ADDED 2026-06-30 (session 12, v1.6 pillar 2 phase-1: module-assembly pipeline + gate-tooling doctrine) ===

- **Module assembly is ordered concatenation, never dependency resolution.** *(v1.6 pillar 2.)* The build assembles the babel body by concatenating the module files in a fixed order (a two-digit `NN` prefix on each filename, honored by `sorted()`), not by resolving imports and topologically sorting. Two reasons resolution is wrong here: it reorders top-level declarations, which breaks the byte-parity the reconstitution gate depends on; and it can move a declaration ahead of something its initializer evaluates at module-eval time, a temporal-dead-zone break the parse gate does not catch. Concatenation in source order reconstitutes the monolith exactly, which is the only assembly a pure-split parity proof accepts. The module boundary IS the file boundary; there are no in-output boundary markers, so the assembled body carries no scaffolding to strip.

- **The working HTML splits into a shell plus a module tree; the babel body no longer lives in an editable file.** *(v1.6 pillar 2, r004.)* Once the babel body moves into module files, the page scaffolding around it (head, dependency script tags, mount div) becomes a source artifact too: `cartulary-src/shell.html` with a single `@@CARTULARY_BABEL_BODY@@` sentinel where the assembled body injects. The body's own trailing newline is owned by the shell (placed after the sentinel), so no module file ends with a meaningful trailing blank and an editor adding a trailing newline to a module can't inject blank lines at a seam. The cold-start ritual changes with this: load the shell + the target module(s), not one monolith HTML.

- **One r-bump per full carve, not per HTML edit.** *(v1.6 pillar 2; supersedes the pre-modular r-rule for the modular era.)* A pure carve is relocation into files; its assembled output is byte-identical to the prior build. The old "r increments only on HTML changes" rule would sit still through the entire modularization because no carve changes the assembled bytes. So the counter now advances one per completed carve, tracking carve progress rather than output-byte change. The pipeline rework itself carries no bump (infra); it rode into r004 with the first carve. r002/r003 keep their numbers, staged as monolith HTMLs under the old rule before the policy changed.

- **Residue files are named bare `trunk` with the order prefix, no letter suffixes.** *(v1.6 pillar 2.)* Carving a module out of the trunk interior fragments the trunk into arcs. Naming those arcs trunk-a/trunk-b/trunk-c and renumbering them every carve is churn that desyncs bookkeeping. Instead every residue arc is just `trunk`, distinguished only by its `NN` assembly-order prefix; carved modules get real names. When a carve splits a trunk file, both halves stay `trunk` at their new prefixes. The module filenames are internal (the build globs by prefix; the turnover artifact is one zip), so this churns nothing on the human side.

- **The reconstitution gate uses two normal forms against a frozen parity anchor.** *(v1.6 pillar 2; `canonicalize.py`.)* The anchor is a frozen babel body that every pure carve must reassemble to. **CORRECTED 2026-09-05 (session 15): this entry originally said the anchor is the r003 body "frozen once", which is no longer true and was never quite right. The anchor ROTATES on every gather, not only on a behavior-changing cut** -- three rotations so far (r013, r016, r018), because a gather moves lines and so breaks byte-identity to whatever was frozen before it. The active anchor at r019 is `reference-r018-body.jsx`; r003, r013 and r016 are retired and are not shipped in the bundle. The rotation always happens AFTER the browser pass on the gather, never before. The normal form is decided once, in one module, so the diff is a clean signal every time. A **pure split** (order preserved by construction) is checked with the ordered non-blank-line SEQUENCE (position-sensitive), so any reorder, addition, or deletion of code shows. A **relocation/gather** (the r002/r003 operation, where lines move on purpose) is checked with the MULTISET of those lines (order-independent), which proves nothing was added, dropped, or altered while allowing the move. Both drop blank lines and trailing whitespace (no JS semantics), so join noise never false-fails. The top-level declaration-name SET is an independent invariant on both.

- **Carve boundary discipline keeps every pure split byte-exact.** *(v1.6 pillar 2.)* Cut points follow four rules so `assemble(tree)` equals the pre-carve body byte-for-byte: (1) boundary blank lines lead the FOLLOWING file, so no slice ends in a blank and the assembler's per-file rstrip can't eat a real blank at a seam; (2) the body's trailing newline lives in the shell, not the last module; (3) a section-divider comment travels with the block it heads; (4) a doc-comment sitting directly above a declaration (no blank between) travels with that declaration. Rules 3 and 4 are for readability of the module files; rules 1 and 2 are what the byte-parity actually depends on. Confirm each cut by matching SHA256 of the assembled HTML against r003.

- **Prove a gate has teeth before trusting its green.** *(v1.6 pillar 2.)* A reconstitution gate that only ever passes is worthless; a green run shows the pipeline reconstitutes but not that the gate can catch a bad carve. When standing up gate tooling, run a negative test: corrupt a module (drop a code line, rename a declaration) and confirm the gate goes RED with a pinpointed diagnosis, then restore. The dropped-line case must surface as a sequence-length and first-divergence failure; the rename must surface in the declaration-name-set diff. Only after the gate has failed on purpose is its pass trustworthy.

- **Validate a new assembly pipeline against a real split, not the degenerate single-file case.** *(v1.6 pillar 2.)* The trivial way to stand up the pipeline is to put the whole body in one module file and prove assemble-equals-source by identity. That never exercises the canonicalizer's seam handling or the diff-across-a-split path, so the first time the gate runs its real logic is the first real carve, where it's already being trusted. Instead validate against a genuine split of one clean module (home-data was the choice: one contiguous block, static data, no logic, no eval-order exposure, one consumer). The real split runs the join normalization and the position-sensitive diff for the first time against known-safe input, so the gate is proven before a carve depends on it.

- **A pure carve is invisible at the byte level; the gate proves it, the browser confirms the assembled file runs.** *(v1.6 pillar 2, r004-r006.)* Every pure-split carve reassembles to the same r003 bytes, so successive carve builds are byte-identical to each other and to the pre-carve HTML (matching SHA256). The reconstitution gate is the proof that no code moved or vanished; the browser pass is not re-testing the same bytes for behavior so much as confirming the assembled artifact opens and the carved surface still works. Both are cheap and both are kept: the gate is the machine proof, the browser pass is the standing rule that parse-and-gate-green is not "works."

=== ADDED 2026-09-05 (session 15, v1.6 pillar 2: gather-episode doctrine from r013-r019) ===

- **Byte-identity is a THIRD check, not a restatement of the first two; it catches what canonical-sequence structurally cannot.** *(v1.6 pillar 2, r014.)* The first r014 cut ended the trunk head on a blank line. The assembler joins modules with a per-file `rstrip('\n')`, so that trailing blank was silently eaten and the assembled body lost one line. Canonical sequence PASSED (it compares non-blank lines only) and the decl-name set PASSED (no declaration moved). Only byte-identity caught it, reporting "differs" where every prior pure split had said "exact". Two consequences. First, boundary rule 1 -- boundary blanks LEAD the following file, no slice may END on a blank -- is a hard constraint of the assembler, not a formatting preference; violating it silently changes the output. Second, do not treat "canonical sequence PASS" as sufficient for a pure split. The gate reports three results because a carve can be wrong in three different ways, and a green on the first two with a "differs" on the third is a RED, not a rounding error.

- **A gather's anchor freeze waits for the browser pass. Never anchor an unverified body.** *(v1.6 pillar 2, r013/r016/r018.)* Each gather breaks byte-identity on purpose, passes on multiset, and then must re-freeze a new `reference-r0NN-body.jsx` with `REFERENCE_BODY` repointed. Freezing an unverified body makes it the parity baseline, and every subsequent pure split then proves only that it faithfully reproduces a body nobody has confirmed works. The gate stops being able to tell you the body is wrong -- it will happily certify a broken baseline forever. The sequence is: gather -> multiset + parse -> STOP -> browser pass -> freeze -> repoint -> re-verify green -> carve. This is also why a pure split following a gather is cheap to verify: its bytes are identical to a body the human already exercised.

- **Carved-module filenames go stale as `NN` prefixes reflow; find modules by NAME and sweep filename references on every doc pass.** *(v1.6 pillar 2, r013-r019.)* The `NN` prefix is assembly order, so inserting a module upstream renumbers everything after it.
