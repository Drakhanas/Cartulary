# Cartulary roadmap

Forward-looking only. What shipped, and the plans and session blocks that got it there, are in `roadmap-archive.md`, verbatim. The standing planning and scope principles are in `roadmap-principles.md`. The sections below are the standing backlog, edited in place as items move. The dated `=== ADDED ... ===` blocks after them are the session log, and the newest block is the current status. The doc gate reads that block for figures, file names, and anchors, and the whole file for em dashes, banned phrases, tables, and required strings, so the standing sections are kept true by hand (`tools/turnover/conventions.md`).

Nothing in the backlog is committed to a version. A row is a claim about the tree, so check it against the source before scheduling work on it.

## v1.8

Not named or opened. Drak put two things in it on 2026-10-23: the leap rules (the review's Pipes item 5), and Kalendarium and Ephemeris improvements he has a rough idea of and hasn't written down yet. The leap rules want a spec before code. On 2026-11-02 he added mobile support as its headliner, then computed fields and cloud-drive guidance.

- **Mobile support: the headliner** (Drak, 2026-11-02: "add for 1.8: mobile support, it'll be the headliner"; out of Deferred indefinitely). Its scope isn't set, and like Fabula, Stemma v2, and Pipes it wants a plan before code. Where the tree stands: the help's Browser Compatibility topic (`26_home-data`) says Cartulary loads on phones and tablets but the UI is desktop-shaped, that most mobile browsers need desktop-site mode for menus and controls to behave, and that mobile is not the target audience; that line changes with whatever v1.8 builds.
- **Computed fields** (Drak, 2026-11-02: "add computed fields to 1.8"). Scope not set; it wants a plan before code. Where the tree stands, from a search of the help text for formula, rollup, computed, aggregate, and dashboard, not a read of the field code: the field types (Field Types topic, `26_home-data`) include none that evaluates over an entry's other fields or over other entries; the filter and saved lists are the only query layer; the Project page is fixed. What the tree computes today is built in and either display-side or the calendar and sky math: Ephemeris's and Kalendarium's absolute-day, orbit, phase, season, and alignment math; Chronometric's duration bars and lane heights; Fabula's outline positions and unpaid-promise flags; the link index behind Referenced by, the delete counts, and Concordance's edges; Name History's label at a shown date. None of it writes a value into a field a user can filter, sort, or reference. Open questions for the plan: a user-written formula or only built-ins (age from a birth Calendar Date through Kalendarium's absolute day is the obvious first), whether a computed value is stored or derived at read, what it can reference (the entry's own fields, linked entries, both), what happens to a value when a calendar rule changes (the leap rules in this section move absolute days), and how the filter, sort, CSV export, and import treat a field that can't be edited.
- **Cloud-drive guidance** (Drak, 2026-11-02: "make a note for 1.8 to point users toward placing their json & cartulary folders into their drive/onedrive/dropbox/whatever"). Scope not set. The drive's own client does the syncing, so Cartulary still makes no network request. Where the tree stands: the help's Back Up Your World topic (`26_home-data`) names "a cloud drive" once, in a list, with no how-to. Folder backups (r040) write the world into `cartulary-backups` inside the images folder, so an images folder inside a synced drive already carries the backups off the machine. At r039's pass Chrome and Brave refused persistence for a page opened from a file, which makes that copy the one that counts for Chromium users. Browsers without the folder (Firefox, Safari) only have Export, so for them the advice is where to save the .json. Surfaces: that help topic, Settings' Image Folder row, the backup banner, the itch page's "No cloud sync" limitation, cartulary.world, and the zip README. To check before writing the copy: whether moving the HTML file into the drive keeps its world in each browser, since the file's address changes (the copy should say export first); what two machines editing from one synced folder produce (a conflict copy, not a merge, so the copy says one machine at a time and import on the other); that the newest-ten rotation's deletes sync too, leaving older history to the drive's own version history; and what each drive's client does with the `.crswap` file Chromium writes before swapping a file into place.
- **Leap rules.** No leap or intercalary rule exists anywhere in the source, and absolute-day math multiplies a fixed days-per-year. A leap rule reaches that math, the cross-calendar anchors, the grid, seasons, date validation, and everything downstream that reads absolute days (Chronometric, Ephemeris). Dates are stored as year, month, and day, so adding a rule to a calendar that already holds dates moves the absolute day of every date after the first leap, and whatever is pinned to an absolute day (a calendar's `anchor.absoluteDay`, a moon's `phaseAnchorDay`) has to move with it or knowingly stay. The review's Dul Pantra figure is arithmetically right (a leap week every eight years is 0.875 days a year, 87.5 a century); the leap week itself lives in Drak's world file, not in the repository.

## Backlog: features

- **Concordance sector graph.** Half shipped in v1.5: the node-source registry already puts stars, planets, and moons in Concordance and draws the `parentBodyId` hierarchy as "orbits" edges, so the star-planet-moon view exists. Still open: connections between star systems with distance stored on the edge (topological, not coordinate-accurate), distance labels on those edges, and a stars-only filter mode. Open design questions: binary stars, 2D or 3D, the single-system empty state, and whether it's a Concordance mode or its own view. The same two primitives (kind-aware filtering, per-edge metadata) would also serve trade routes and faction links. It's one of three items here big enough to headline a release, with variant filter v2 and the Game Mechanics pack. The full sketch is in `roadmap-archive.md`, in the v1.6 record's copy of the backlog.
- **D.4, recurrence on the calendar-date field.** A recurring date as part of the field's value (`recurrence: {periodDays, count?, until?}`), expanded for display by Chronometric, the Kalendarium grid, and entry rendering. Every date-walking helper would have to learn it. Days only for v1, because months and years drift under calendar edits; a cap on displayed occurrences; additive, with no migration. It's a different layer from the rejected holidays-as-entities idea below. The trigger is users saying the prose-in-notes fallback for promoted Ephemeris events is what's in their way. The full sketch is in the same place.
- **Concordance: a per-node "auto-place this" action** that clears one saved position so the layout re-places that node. Not in the tree as of 2026-10-23; the only reset the view has is zoom. The old row also asked for edge-label polish, but labels already fit their lines and offset when reciprocal (`truncateLabels` and `labelPosFor` in `17_concordance`), and the row named nothing further.
- **Per-map JSON import and export** (Cartographia). Deferred at v1.6 "to the later, larger Cartographia work", which no plan defines yet.
- **CSV lexicon import** (Glossopoeia), deferred with a plan: a column-mapping step rather than a fixed header, add-only, aimed so a Vulgarlang export lines up without hard-coding its columns. Its "small inline parser" isn't needed: the release build bundles d3 7.9.0, and `d3.csvParse` handles quoted fields (checked 2026-10-23). A Swadesh starter list is a separate and weaker follow-on, never built alongside it. The plan is in `roadmap-principles.md`, the 2026-06-23 (deferred) block.
- **Variant filter v2.** v1.5's r087 filter, generalized: variant as an entry-level attribute, the first world-scoped config slice, filtering across the specialty views, `showWhen` reading the variant, exports aware of it. Estimated at 14 to 22 r-bumps; the open question is how each view treats edges into entries the filter hides. It wants its own release slot. The plan is in `roadmap-principles.md`, the 2026-06-09 block.
- **Pen pressure** for Brush and Eraser (Drak, 2026-10-23, taking up the 2026-10-22 note that it wasn't in any scope he'd support yet, "potentially in the future"). The map editor handles Pointer Events throughout (`18_cartographia`), so a pen's `pressure` is readable on every pointer sample. Today a stroke keeps only each sample's position, interpolates the dabs between samples, and applies opacity once per stroke, so pressure-driven size has to ride through that interpolation and pressure-driven opacity means drawing dab by dab. Neither changes the schema, because a raster stroke lands as pixels. A mouse reports a constant pressure and has to keep today's behavior. Freehand is a vector tool, so pressure there would mean variable-width paths, a bigger job.
- **Game Mechanics pack.** Shelved since 2026-06-17, mid-design, with no code written; `packs/game-mechanics-pack-reference.md` is the resumption point. Of its 15 templates, 8 are locked (with revisions awaiting sign-off), 1 is proposed, and 6 are not designed, and seven decisions are open. The full SRD seed for both editions is 12 to 18 sessions, most of it extraction. Templates first and the seed later is the cheaper route, and nothing is built against either.
- **Corpus-level research notes** (Drak, 2026-10-25: per story for now). A Fabula research note belongs to one story (`docs/fabula-spec.md`, section 5.11), so research a series shares lives in one story's notes or in a world entry. A note owned by a corpus would show on the corpus page and in each of its stories, and its Used In could reach any of their scenes; it changes which records can own others, so it waits until Fabula has been used. Kept here at the Sweep's plan (Drak's call 2, 2026-10-31).
- **What Fabula's timeline leaves for later** (r020's plan, 2026-10-26). An image export, as Chronometric's SVG export, which r023's export left out by its plan's default, the timeline not being exported (the spec's section 9); and editing on the timeline, as Chronometric's edit mode does, which Drak's call left for a cut of its own if the timeline shows it's wanted. At r022's plan (2026-10-27) he added Anachronia's lines per lane, each POV's, thread's, or arc's scenes joined in telling order with colors of their own and a legend, where r022 draws one line, the book's, if the plot shows they're wanted. **To the backlog at the Sweep's plan** (Drak's call 2, 2026-10-31): each waits until using Fabula shows it's wanted.
- **The Meaning tab's grid of themes against scenes** (r015's plan, 2026-10-26; `docs/fabula-spec.md`, section 4). A grid of a story's themes against its scenes in the outline's order, which would lay out where a theme drops out, drawn from what the tab already reads. At r015's plan it was the strongest of the ways offered and the most work; Claude recommended the row of positions instead, Drak took the row (option b), and the grid was left for later. Filed at the Sweep's plan (Drak's call 2, 2026-10-31), to wait until using Fabula shows it's wanted.
- **Typed relations** (the review's Pipes item 2, to the backlog by Drak's call, 2026-10-23). `relationKind` has two values, parent and spouse, and the template builder offers both. Spouse declarations carry Married and Ended dates and mirror to the partner (since v1.2), and parent declarations carry a label; every other entry-ref is a bare id, one-way, with no date, note, or reciprocity. Typed relations with properties are a schema change across the form engine, Concordance, Linea, and the exports. Backlinks, in v1.7, cover reading the other direction without one.

## Tolerated

- **v1.6's r025 through r030's cut scripts can't run where they sit.** r025 names an absolute path from the sandbox before the repository and r026 through r030 count two folders up, so since the 2026-10-19 move into `inlining/cuts/` they point at folders that don't exist. Their earlier trees aren't in the history either, so they couldn't be replayed anyway; they stay as the record of what ran (Drak, 2026-10-23).
- **A reference field that still holds a deleted template's id is left alone by r002's name sync and its flags.** `deleteTemplate` doesn't take the id out of other fields' target lists, so such a field keeps its stale names, and a target removed from it in the builder can come back at the next re-resolve, which drops the dead id; the builder's save after that sticks. The flags skip such a field. The rule stayed for r004, whose repair runs after the sync and mends the ids the upgrades retired; a deleted template's id it can't tell from any other, so the rest stays as it was. Kept at the Sweep's plan (2026-10-31, `docs/sweep-spec.md`, section 6).
- **A map template of the user's own, promoted to Cartographia before r004, keeps its id in the fields that targeted it.** Once the template is gone its id can't be told from a deleted template's. A field that takes one template offers no maps and keeps its references; choosing Map in the builder fixes it. A field that takes several keeps the id the same way, unless it also names Map and a load from r002 on resolved its names, which took the maps back. Kept at the Sweep's plan (2026-10-31, `docs/sweep-spec.md`, section 6).
- **A world last saved before r002 doesn't get back the targets of a multi-target field naming Language / Glossary that v1.4's builder switched to one target and back.** r002's one-time name sync runs first in such a world, reads the field's null id list and null filters as the builder's switch leaves them, and takes its names, so r004's repair has nothing to rebuild from. The field stays open to any template, its references kept. A world that went through r002 or r003 isn't affected. Kept at the Sweep's plan (2026-10-31, `docs/sweep-spec.md`, section 6).
- **A map record has no createdAt** (found 2026-10-30, probing r044, and said with its staging as a defect). `saveMap` (`12_trunk`) writes a map from its draft's id, name, tags, fields, and drawing with an updatedAt, and the save format's map record has no createdAt either (the help's JSON Save File Schema topic, `26_home-data`), and nothing in the app gives a map one, the v1.5 promotion of map entries (`10_migrate`) included, so only a world written by hand has a map with a createdAt, as r044's probe world did, for its first Save to drop. Nothing reads it. It stays unless something needs a map's date of making. Kept at the Sweep's plan (2026-10-31, `docs/sweep-spec.md`, section 6).
- **A built-in template's Reset to Default keeps a field's values through a change of its type** (found 2026-11-01, planning r056). The reset matches the factory's fields to the template's by label and keeps a matched field's id, and with it the field's values, so a reference field made a Short Text, or another type, and then reset holds what it held, ids or typed text, as a reference again. A delete while it wasn't a reference cleared nothing from it, so a link to what was deleted reads (missing entry), and so does typed text in a field that holds one reference, until the next load, whose clean-up (`migrate`, `10_migrate`) clears from a top-level reference with a target list every value that names no record it takes; typed text in a field that holds several shows nothing. r056 took this case for Fabula's kinds, whose reset drops a value that names no record from a field it turns back into a link; `resetTemplate` (`12_trunk`) could do the same. A field the reset brings back after it was deleted gets a new id, so a deleted field's values don't come back. Filed here by Claude's default in r056's plan, for a cut that chooses to take it.

## Decided no

- **The map editor.** From the v1 won't-have list (`docs/cartographia-plus-spec.md`, section 7) and the shipped Limitations: no custom color picker; no layer opacity, blend modes, or per-layer export; no procedural generation; no image export beyond SVG and PNG; no grid or snapping beyond the rotation knob's Shift snap; no fog of war, measurement or scale tools, dice, or initiative tracking.
- **Kalendarium.** No per-day weather data, no holidays as recurring first-class entities, no auto-advancing current date: writers and GMs move time narratively. Field-level recurrence (D.4 above) is a different layer.
- **Concordance.** The empty-on-open template filter stays blanket; a size-threshold variant was declined at v1.5's r134.
- **Glossopoeia** stops at the diachronic fork: no stem-level paradigm derivation, no per-word derivation locks, no live parent-inventory fallback for varieties (all declined 2026-06-23).
