### Pipes: the review's eight and Drak's ninth and tenth, checked against the tree (2026-10-23; the tenth filed 2026-10-28)

1. **Backlinks.** The entry view lists nothing that points at an entry; only Concordance shows inbound links, as a graph (its focus mode walks both directions). The entry list's search (`12_trunk`) matches names, tags, and `JSON.stringify(fields)`, and an entry-ref is stored as the target's id, which is built from its name at creation (`ent-<slug>-xxxx`): searching a one-word form of a house's name finds its members by accident, a query with a space misses them, and a rename leaves the old slug behind, while "year" matches every entry with a date. `countInboundEntryRefs` (`05_field-system`) has one caller, the Ephemeris body-delete confirmation. A "Referenced by" list on the entry view is derived at render time and needs no schema change; counting `[[links]]` as well as reference fields, as Concordance's edges do, gives item 3 the scan it needs. **v1.7** (Drak, 2026-10-23).
2. **Relations beyond family carry nothing.** **The backlog** (Drak, 2026-10-23); the check moved there, under Typed relations.
3. **Renames break wiki-links.** Wiki-links resolve by primary name, then by Name History (`13_form-engine-display`), so `[[Old Name]]` survives only if the old name is in the entry's Name History field. **Wiki-links reach entries and bodies only** (found 2026-10-27, probing v1.7's r027): the entry view's `MarkdownDisplay` and the exports' `entryByLowerName` resolve a `[[name]]` against entries, their Name History, and bodies, so a wiki-link to a map, a Glossopoeia record, a Fabula record, or a stemma is a broken link in the entry view and the exports, though Concordance builds its own name index with the registered records and draws the edge; `getRegisteredNameToId` (`22_trunk`), written at v1.5's r076 "for wiki-link resolution parity with entries", has never had a caller. It belongs with the renames cut, which rewrites the same resolution, or takes a small cut of its own. Nothing puts it there: saving a renamed entry records and rewrites nothing, and only 4 of the 20 built-in templates have a Name History field. Concordance's wiki-link edges resolve by primary name only (`17_concordance`), so a renamed target loses its edge even with the old name in Name History. The choices: rewrite the links across the world on rename, with a count shown first, or add the old name to Name History where the template has one. **v1.7** (Drak, 2026-10-23).
4. **No query layer.** The entry list filters by one variant axis, then by a tag or a template, then by the search above; nothing filters on arbitrary field values (the variant axis is one select field), so "every living member of House X" can't be asked. The review expected it to fail the 10-years filter, and so did Claude. **v1.7** (Drak, 2026-10-23): it's his filter, and he doesn't think an internal query and search system is hard enough to fail it. Two calls in its spec set what it costs to keep: whether a query is built fresh each time or saved in the world, which would make its shape part of the save format, and which of the seventeen field types it reads (groups and grids nest their values). Matching what an entry shows, a referenced entry's name or a date as written, rather than the stored ids would also end the accidental matches item 1 describes.
