### Pipes: the review's eight and Drak's ninth, checked against the tree (2026-10-23)

1. **Backlinks.** The entry view lists nothing that points at an entry; only Concordance shows inbound links, as a graph (its focus mode walks both directions). The entry list's search (`12_trunk`) matches names, tags, and `JSON.stringify(fields)`, and an entry-ref is stored as the target's id, which is built from its name at creation (`ent-<slug>-xxxx`): searching a one-word form of a house's name finds its members by accident, a query with a space misses them, and a rename leaves the old slug behind, while "year" matches every entry with a date. `countInboundEntryRefs` (`05_field-system`) has one caller, the Ephemeris body-delete confirmation. A "Referenced by" list on the entry view is derived at render time and needs no schema change; counting `[[links]]` as well as reference fields, as Concordance's edges do, gives item 3 the scan it needs. **v1.7** (Drak, 2026-10-23).
2. **Relations beyond family carry nothing.** **The backlog** (Drak, 2026-10-23); the check moved there, under Typed relations.
3. **Renames break wiki-links.** Wiki-links resolve by primary name, then by Name History (`13_form-engine-display`), so `[[Old Name]]` survives only if the old name is in the entry's Name History field. Nothing puts it there: saving a renamed entry records and rewrites nothing, and only 4 of the 20 built-in templates have a Name History field. Concordance's wiki-link edges resolve by primary name only (`17_concordance`), so a renamed target loses its edge even with the old name in Name History. The choices: rewrite the links across the world on rename, with a count shown first, or add the old name to Name History where the template has one. **v1.7** (Drak, 2026-10-23).
4. **No query layer.** The entry list filters by one variant axis, then by a tag or a template, then by the search above; nothing filters on arbitrary field values (the variant axis is one select field), so "every living member of House X" can't be asked. The review expected it to fail the 10-years filter, and so did Claude. **v1.7** (Drak, 2026-10-23): it's his filter, and he doesn't think an internal query and search system is hard enough to fail it. Two calls in its spec set what it costs to keep: whether a query is built fresh each time or saved in the world, which would make its shape part of the save format, and which of the seventeen field types it reads (groups and grids nest their values). Matching what an entry shows, a referenced entry's name or a date as written, rather than the stored ids would also end the accidental matches item 1 describes. Variant filter v2 (backlog) plans filtering across the specialty views, so the spec also says where one stops and the other starts.
5. **Leap years.** **The cheap half in r001, the leap rules in v1.8** (Drak, 2026-10-23); the check of the tree moved to the v1.8 section below. `DEFAULT_CALENDAR` (`06_calendar-engine`) is named Gregorian but has a 28-day February and no leap rule, and the calendar-name placeholder suggests Gregorian, Julian, Islamic, and Hebrew, none of which Kalendarium can express. The cheap half stops calling the default Gregorian: its name, the placeholder, the Kalendarium help, the schema examples in the help and on the site, and `16_trunk`'s fallback label.
6. **World durability.** Nothing calls `navigator.storage.persist()`, and Version History keeps its snapshots in the same IndexedDB store as the world, so an eviction or a cleared site takes both. The images-folder handle (kept in IndexedDB, re-permissioned in `11_io-utils`) already writes image files, so a rolling world JSON beside them needs no new permission flow. The limits: the folder exists only where `showDirectoryPicker` does (Chromium browsers), a write without a click can only happen while the permission still holds, and whether a browser grants persistence to a page opened from a file has to be tested in each one. **v1.7** (Drak, 2026-10-23).
7. **No CSV import.** Nothing in the application reads CSV, but the release build bundles all of d3 7.9.0, whose `d3.csvParse` handles quoted fields, so there's no parser to write; the deferred plan's premise that none is bundled (`roadmap-principles.md`) is wrong. That plan in the backlog below (a column-mapping step, add-only) is the same door, and a field-mapped importer for entries (item 9) would reuse it. A parser for one generator's format fails the 10-years filter; a generic mapper doesn't. **Drak's call (2026-10-23):** CSV comes in through item 9, one template at a time.
8. **The free-forever argument answers the wrong question.** cartulary.world's "Free, and not as a pricing decision" and "Free by construction" sections argue from the MIT license and the architecture, which guarantee the price but not that fixes keep coming. The answer the project has now is the public repository and its deterministic build: anyone can rebuild the shipped file byte for byte and carry on. It's a site edit with no r-bump; the itch page and the zip README already name the repository, and the site's stale line about having no repository is in the product-text defects below. **Done and live** (Drak's go and upload, 2026-10-23), with the repository line in the same edit (`site/helloworld.html`); the itch page's version of the argument is his to replace (the changelog has both).
9. **Template-level entry import** (Drak's, 2026-10-23; not from the review). Only one importable file carries entries today: a world file, whose import replaces the whole world after a confirmation (`importWorld`, `12_trunk`). Template and pack files carry definitions only, and the Markdown exports aren't read back. Importing entries into one template from any source needs a mapping onto its fields, new ids, a rule for names already taken (wiki-links resolve to the first same-named entry in storage order), spouse declarations mirrored onto the partner as the editor does, and references resolved against this world: a value is an entry id, and `migrate()`'s cleanup drops one that matches nothing at the next load (in top-level fields with a target list; elsewhere it dangles), so the import has to report them itself. A file from another world adds three problems. Field ids won't match even on built-ins, which every world seeds with random suffixes (`makeTemplateFromBuiltin`, `01_builtin-templates`); they match only where a template came from the other world's template or pack file, or both came from the same one. Entries name their calendar by a world-scoped id, and `getCalendar` (`06_calendar-engine`) falls back to the primary calendar for an unknown one without a word, so their dates, stored as year, month, and day, would be read in the wrong calendar. And image fields name files in the other world's images folder. **Drak's call (2026-10-23): both JSON and CSV**, through one mapping screen; the CSV half is item 7 with the destination fixed to one template. The reset-to-built-in path already matches fields by label (`12_trunk`), but no rule makes labels unique within a template, so the mapping has to flag a repeated one. **The JSON half reads a format of its own** (Drak, the same evening), written by a new Export entries action on each template: a `cartulary_entries_export: 1` envelope, like the template, pack, and calendar files, naming fields by label with the id alongside, and references and calendars by name. Entries move between worlds as an export and an import, with field matching and calendars settled at the export, where the ids are known; world files aren't read. Images still travel as file names only, and secret fields should follow the other exports, left out unless asked for (`08_export-layer`). **v1.7** (Drak, 2026-10-23). By Claude's estimate it's about three cuts: the export and its format, JSON import through the mapping screen, then CSV through the same screen; if v1.7 runs long, it splits before the CSV cut.

## v1.8

Not named or opened. Drak put two things in it on 2026-10-23: the leap rules (the review's Pipes item 5), and Kalendarium and Ephemeris improvements he has a rough idea of and hasn't written down yet. The leap rules want a spec before code.

- **Leap rules.** No leap or intercalary rule exists anywhere in the source, and absolute-day math multiplies a fixed days-per-year. A leap rule reaches that math, the cross-calendar anchors, the grid, seasons, date validation, and everything downstream that reads absolute days (Chronometric, Ephemeris). Dates are stored as year, month, and day, so adding a rule to a calendar that already holds dates moves the absolute day of every date after the first leap, and whatever is pinned to an absolute day (a calendar's `anchor.absoluteDay`, a moon's `phaseAnchorDay`) has to move with it or knowingly stay. The review's Dul Pantra figure is arithmetically right (a leap week every eight years is 0.875 days a year, 87.5 a century); the leap week itself lives in Drak's world file, not in the repository.

## Backlog: features

- **Concordance sector graph.** Half shipped in v1.5: the node-source registry already puts stars, planets, and moons in Concordance and draws the `parentBodyId` hierarchy as "orbits" edges, so the star-planet-moon view exists. Still open: connections between star systems with distance stored on the edge (topological, not coordinate-accurate), distance labels on those edges, and a stars-only filter mode. Open design questions: binary stars, 2D or 3D, the single-system empty state, and whether it's a Concordance mode or its own view. The same two primitives (kind-aware filtering, per-edge metadata) would also serve trade routes and faction links. It's one of three items here big enough to headline a release, with variant filter v2 and the Game Mechanics pack. The full sketch is in `roadmap-archive.md`, in the v1.6 record's copy of the backlog.
- **D.4, recurrence on the calendar-date field.** A recurring date as part of the field's value (`recurrence: {periodDays, count?, until?}`), expanded for display by Chronometric, the Kalendarium grid, and entry rendering. Every date-walking helper would have to learn it. Days only for v1, because months and years drift under calendar edits; a cap on displayed occurrences; additive, with no migration. It's a different layer from the rejected holidays-as-entities idea below. The trigger is users saying the prose-in-notes fallback for promoted Ephemeris events is what's in their way. The full sketch is in the same place.
- **Concordance: a per-node "auto-place this" action** that clears one saved position so the layout re-places that node. Not in the tree as of 2026-10-23; the only reset the view has is zoom. The old row also asked for edge-label polish, but labels already fit their lines and offset when reciprocal (`truncateLabels` and `labelPosFor` in `17_concordance`), and the row named nothing further.
- **Per-map JSON import and export** (Cartographia). Deferred at v1.6 "to the later, larger Cartographia work", which no plan defines yet.
- **CSV lexicon import** (Glossopoeia), deferred with a plan: a column-mapping step rather than a fixed header, add-only, aimed so a Vulgarlang export lines up without hard-coding its columns. Its "small inline parser" isn't needed: the release build bundles d3 7.9.0, and `d3.csvParse` handles quoted fields (checked 2026-10-23). A Swadesh starter list is a separate and weaker follow-on, never built alongside it. The plan is in `roadmap-principles.md`, the 2026-06-23 (deferred) block.
- **Variant filter v2.** v1.5's r087 filter, generalized: variant as an entry-level attribute, the first world-scoped config slice, filtering across the specialty views, `showWhen` reading the variant, exports aware of it. Estimated at 14 to 22 r-bumps; the open question is how each view treats edges into entries the filter hides. It wants its own release slot. The plan is in `roadmap-principles.md`, the 2026-06-09 block.
- **Pen pressure** for Brush and Eraser (Drak, 2026-10-23, taking up the 2026-10-22 note that it wasn't in any scope he'd support yet, "potentially in the future"). The map editor handles Pointer Events throughout (`18_cartographia`), so a pen's `pressure` is readable on every pointer sample. Today a stroke keeps only each sample's position, interpolates the dabs between samples, and applies opacity once per stroke, so pressure-driven size has to ride through that interpolation and pressure-driven opacity means drawing dab by dab. Neither changes the schema, because a raster stroke lands as pixels. A mouse reports a constant pressure and has to keep today's behavior. Freehand is a vector tool, so pressure there would mean variable-width paths, a bigger job.
- **Game Mechanics pack.** Shelved since 2026-06-17, mid-design, with no code written; `packs/game-mechanics-pack-reference.md` is the resumption point. Of its 15 templates, 8 are locked (with revisions awaiting sign-off), 1 is proposed, and 6 are not designed, and seven decisions are open. The full SRD seed for both editions is 12 to 18 sessions, most of it extraction. Templates first and the seed later is the cheaper route, and nothing is built against either.
- **Typed relations** (the review's Pipes item 2, to the backlog by Drak's call, 2026-10-23). `relationKind` has two values, parent and spouse, and the template builder offers both. Spouse declarations carry Married and Ended dates and mirror to the partner (since v1.2), and parent declarations carry a label; every other entry-ref is a bare id, one-way, with no date, note, or reciprocity. Typed relations with properties are a schema change across the form engine, Concordance, Linea, and the exports. Backlinks, in v1.7, cover reading the other direction without one.

## Backlog: product-text defects

Three were found by the independent read of the rewritten handoff on 2026-10-23; a fourth, the site's line saying there's no repository, was found by the Pipes check the same day and fixed with Pipes item 8. Each is a help, site, or product string, not behavior, and each is small; together they're a natural first v1.7 cut, and the help and the site would move together.

- **The Concordance help says the template filter comes back all-on after a reload** ("refresh the page and all templates are visible again", in the help module's Concordance topic). Since v1.5's r134 the filter opens empty, by design.
- **The save-file schema has no `longform` or `grid` shape.** The in-app JSON Save File Schema topic's field-type list and its field-values table omit both, and cartulary.world's JSON Structure page lists `grid` as a two-dimensional array (`grid[rowIndex][colIndex]`), which it isn't. The real shape is `{ rowAxisLabel, colAxisLabel, rows:[{id,label}], cols:[{id,label}], cells:{ [rowId]:{ [colId]:{ type, value } } } }` (`makeEmptyGrid` in `05_field-system`).
- **A promoted Ephemeris event still writes "native recurrence support is not in v1.5"** into its notes (`12_trunk`). The version is stale; D.4 above is the feature it refers to.

## Decided no

- **The map editor.** From the v1 won't-have list (`docs/cartographia-plus-spec.md`, section 7) and the shipped Limitations: no custom color picker; no layer opacity, blend modes, or per-layer export; no procedural generation; no image export beyond SVG and PNG; no grid or snapping beyond the rotation knob's Shift snap; no fog of war, measurement or scale tools, dice, or initiative tracking.
- **Kalendarium.** No per-day weather data, no holidays as recurring first-class entities, no auto-advancing current date: writers and GMs move time narratively. Field-level recurrence (D.4 above) is a different layer.
- **Concordance.** The empty-on-open template filter stays blanket; a size-threshold variant was declined at v1.5's r134.
- **Glossopoeia** stops at the diachronic fork: no stem-level paradigm derivation, no per-word derivation locks, no live parent-inventory fallback for varieties (all declined 2026-06-23).
