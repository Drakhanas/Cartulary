## Patterns Drak watches for in code

When reviewing changes or auditing code:

- **CSS variable typos** (e.g. `--surface` vs `--surf2`, `--warn` missing fallback definitions — these patterns recur)
- **Scope errors** — functions defined in wrong scope, especially when refactoring
- **Stale comments** — comments that no longer match implementation
- **Missing className CSS rules** — classes referenced but not defined (e.g. `modal-notice-warn` vs `modal-notice-warning`)
- **Stale UI copy** — strings that still reference removed features
- **Locked-world guards** — every state mutation needs `if (isLocked) return;` or equivalent
- **Defensive validation gaps** — code that trusts JSON input without normalizing first
- **`alert()` calls** — convention is `flash(text, type)` for non-blocking notifications; `alert()` blocks the UI
- **Name-based template matchers** *(v1.3)* — every name-based template lookup inside `migrate()` should filter `&& t.origin === TEMPLATE_ORIGIN.BUILTIN`; lookups outside `migrate()` should consider whether origin matters too
- **Raw `typeof v === "string"` checks on select values** *(v1.4)* — v1.3+ Status / Type / etc. with `otherTextField: true` store values as `{value, customText}` objects, not strings. Any helper that inspects a select value should route through `selectValueOnly(v)` or `formatSelectDisplay(v)` so it works for both legacy bare-string and v1.3+ object shapes. `isEntryDeceased` had this bug from v1.3 through end-of-Kalendarium; surfaced and fixed during auto-age work.
- **Adding a parameter to an existing handler requires auditing every call site** *(v1.4)* — including raw `onClick={fn}` references where React fills the first parameter with the SyntheticEvent. `openNewEntry` was refactored to take an optional `templateOverride` for Cartographia; the existing `+ New Entry` button at the template list view still passed the function reference directly, so React's SyntheticEvent became the templateOverride. The event is truthy and an object, so the `templateOverride || activeTemplate` fallback never fired, and `tmpl.fields.forEach` crashed because SyntheticEvent has no `fields` array. Result: every "+ New Entry" button silently broke for the entire duration between the Cartographia ship and the HTML export QA session. Fix is two-part: wrap call sites that need no args (`onClick={() => openNewEntry()}`), and add a shape-check guard inside the handler that requires the override to look like an actual template (string `id` + array `fields`) before using it. The shape-check is the durable defense — call-site mistakes are easy to repeat; a guarded handler fails gracefully (button does nothing) instead of crashing the entry-creation flow.
- **Cell-substrate visual conflicts** *(v1.4 post-Kalendarium)* — when a new feature uses a cell's visual channel (background, border, fill, glyph) that another feature already uses, expect interference. Calendar grid season bands and has-entries originally both wanted to use the background — the fix was moving has-entries to border-channel so they could coexist. Whenever a new cell-level feature is proposed for a cell-dense view (calendar grid, Concordance nodes, Linea nodes), audit which visual channels are already in use and pick an unused one. Folding multiple states into a single channel via color-coding usually fails — users can't reliably distinguish "blue means selected" from "blue means season X".
- **A registered node-source's name is a reserved type name — guard the sentinel mapping against real templates.** *(v1.5, r081.)* `resolveTemplateRefs` maps a registered type's name (and any legacy alias) to its sentinel id so `refTemplates` strings resolve. That mapping MUST be conditional — `if (!(name in byName)) byName[name] = sentinel` — so a real user template that happens to share the name wins and the sentinel only fills the gap. Unconditional assignment silently hijacks a same-named real template, and because multi-template refs re-resolve from names on EVERY load, the hijack re-applies every load. This bit when `BODY_REF_LABEL` was renamed to "Astronomical Body" (the exact name of the deleted v1.4 built-in, a natural one for a user to recreate); the original design had avoided it by choosing a *distinct* sentinel label. Whenever a registered type's user-facing name could plausibly collide with a user template name, the guard is mandatory.
- **Date-surface walker drift** *(v1.4 final; extended v1.5)* — when adding a new date-bearing field type, or extending an existing field to carry a date, audit the WHOLE integrity group in the same patch: `reframeDateAcrossStructure`, `convertFieldsObject` (in `convertEntryDatesAcrossCalendars`), `hasOutOfRangeDates`, AND `collectCalendarDateUsages`. They must cover identical surface sets; a walker missing a surface its siblings have silently drifts user data the warning modal promised wouldn't move. Surface checklist as of v1.5: calendar-date, calendar-date-range (start/end), name-history (from/to), entry-ref relationKind=SPOUSE_KIND (marriedOn/endedOn), group subfields (recursive), grid cells of type calendar-date / calendar-date-range, world.currentMoment (collect-only). `collectEntryDatesAsAbsoluteDays` is intentionally OUT of this group (discovery-only; no grid cells). Bug #2 from the v1.4 audit and the r074 grid fix were both this exact drift. Code-level test for "did I get them all?": grep every group member's body for the new surface's marker; all must match.
- **Wheel-listener `useEffect` deps must include the ref's gating value** *(v1.4 final)* — when binding a native wheel listener to a ref-attached element via useEffect, the deps array must include whatever value gates the element's render. Empty deps `[]` runs once on mount; if the ref's element is gated behind an early return or conditional render that's not satisfied at mount, the effect captures `ref.current === null`, bails, and never re-runs when the element finally renders. The map zoom in both MapView and MapEditor had this bug — `if (!imageUrl) return <map-empty>` early-returned past the map-canvas div, so a fresh map (no image yet) never bound the wheel listener even after the image arrived. Fix: deps `[imageUrl]` (or whatever the render-gating value is). The fix runs the effect once on mount (bails harmlessly), then re-runs when the gate opens and the ref becomes non-null.
- **Sample-step assumptions in alignment finders** *(v1.5 — Ephemeris)* — when adding a new alignment type or modifying an existing one in Ephemeris Compute mode, audit the sample-step formula. Period-based sampling (`shortest_period / 100`) is the default for wide-event alignment types (phase, conjunction) but silently fails for narrow events that scale with body angular size or tolerance angle (eclipse, nodal). The eclipse test cases in r013 returned zero events under naive period-based sampling and required a geometry-aware step derivation. New alignment types must declare their event-window category (period-fraction vs geometry-fraction) and pick the matching sample-step formula. Verification must include test cases where the event window is narrow relative to the orbital period — testing only Earth-Mars-class events doesn't surface the bug. See the doctrine entry "Alignment finders use period-based sampling for wide events, geometry-aware sampling for narrow ones" for the full reasoning.

=== ADDED 2026-06-08 — standing principles ===

- **Flagship packs ship content.** The general rule "packs are templates-only" stands, but the two flagship demo packs (Space Opera, Game Mechanics) are the exception. Game Mechanics ships the full SRD as seed entries, both editions (5.1 + 5.2.1), complete. Legal under CC-BY 4.0 with attribution naming both SRDs on the pack envelope. Requires a new packs capability: pack format gains an `entries` array + a seeding import path.
- **Tags are user-only.** System/structural metadata (edition, provenance) lives in template fields, never the user's `tags` array.
- **Edition handling = 2014 / 2024 / Both** single-select per template; edition-gated fields include "Both" in their `showWhen` values so a Both entry shows the union of edition-specific fields. Seeding: identical-across-editions entity -> one Both entry; divergent entity -> split into 2014 + 2024 entries.
- **longform field type** (r086, durable): literal text + 5-space indent token + `\f` divider token, serialized per surface. Use for big prose blocks; use `textarea` where markdown / wiki-link / entry-ref support matters.
- **Comprehensive-standalone pack exception** (Game Mechanics): no roster-size cap, built-in overlap irrelevant, model every SRD entity that warrants a template.

=== ADDED 2026-06-09 — edition model superseded; variant filter ===

- **SUPERSEDES the 2026-06-08 "Edition handling = 2014/2024/Both" bullet.** Edition selects carry **{2014, 2024} only**; there is no Both option and no `{edition, Both}` showWhen unions — every edition gate is a plain single-edition value list. "Both" semantics live in a separate **`Applies to Both Editions`** select (No/Yes, No default), present only on templates with verified identical-across-edition SRD content, set by the seeder. The variant filter ORs the flag into entry visibility. **Split-on-divergence:** any cross-edition difference means two entries (2014 + 2024, flag No); the flag marks only byte-identical content, so a flagged entry's single stored field set IS both editions. Rationale: a user-selectable Both value satisfies both editions' gates simultaneously and invites incoherent merged entries; the flag's worst failure is an entry that's merely incomplete in one view.
- **Edition unset = visible everywhere.** The filter never hides an entry whose axis field is empty; this is the deliberate homebrew escape hatch (edition-agnostic user content needs no flag field).
- **Variant filter is a core primitive, not pack code** (r087). The axis is a user-named field label, matched select-type-only across templates; packs configure it rather than owning it. Scope is the entry list only; specialty views, exports, and ref pickers are never filtered at this tier (the v2 generalization owns that, deferred).
- **System fields use position convention:** Edition at field position 2, the all-variants flag at position 3, on every template that carries them.

=== ADDED 2026-06-18: Glossopoeia design doctrine (the ConLang core view) ===

- **The ConLang core view is named Glossopoeia.** Collision-clean, the field's own term for language construction. Gramattica/Grammatica was rejected (misspelled, collides with a parser generator, semantically too narrow). It is a full flagship core view: eleven workspaces under grouped collapsible nav, a language selector scoping each entity to one ConLang, cross-language refs deliberately crossing that scope. Full locked schemas live in `glossopoeia-design-handover.md`; state summary in handoff §3.
- **Glossopoeia design philosophy: maximalist scope, professional accuracy.** Drak's three conlangs are the floor, not the ceiling. Support anything that exists in linguistics whether or not his languages use it ("if it exists, add it"). Use IPA for phonology, standard typological terms throughout, Leipzig glossing in the Corpus.
- **Typology fields are closed sets with no reflexive Other+.** This is the opposite of the in-world Type/Status convention, which keeps Other+. Fixed typological inventories (places of articulation, alignment, basic word order) are closed. Genuinely open categories (phonological process types, grammatical-feature category names, pronoun types, word-building methods) may keep Other+.
- **`tags` and `group` field types stay user-only.** Never used in any built-in template or view. The new multi-select field type (the build prerequisite below) is the built-in-safe fixed-set multi-pick that replaces the reflex to reach for `tags`.
- **Rules are documentary, not executed.** Rule-shaped entities (phonological rules now, sound changes later) record input / output / environment / order as data. The engine that would actually apply them is deferred and shared with diachronics. The phonological-rule field shape is deliberately the shape diachronics' Sound Change will reuse.
- **Display-workspace pattern.** A workspace either owns its own entries (data-entry) or owns nothing and filters/arranges entries owned elsewhere (display). Glossopoeia's Noun Number and Verbs are display workspaces over the Morphology toolbox. Number was kept standalone at Drak's call ("vital importance") rather than folded into a general Nouns workspace; case and gender have no dedicated display and are read in the toolbox.
- **Grammatical features use the lean Grammatical Value form.** One entry per value (Accusative, Plural), with Category as a dropdown field on the value and NO separate Grammatical Category parent entity. An earlier split into parent-plus-child was offered and dropped; do not reintroduce it. Values being their own entries buys exactly two things: filtering words by feature, and the affix-to-value map. It does not buy table labels.
- **Grid axes are free-text and cannot reference entries; only cells can.** So paradigm and pronoun table row/column labels are typed by hand and do not pull from Grammatical Value entries. Known limitation, accepted by design, not a gap to fix. A paradigm is a grid field on the thing being inflected, never a standalone entity.
- **ConLang supersedes the built-in Language / Glossary template.** Supersede-and-migrate (Drak's choice over running both side by side). The container replaces the dual-purpose built-in; existing entries split (language-overview/dialect/naming-convention to ConLang containers, word/phrase/idiom/glossary-term to Lexemes); five built-in templates (Character, Location, Culture/People, Document, Race) re-point their language refs to ConLang. Migration is load-time, idempotent, lossless, IDs preserved, dropped data appended to Notes. The glossary-term half waits for the Lexeme schema.
- **Plain-language doctrine (established the hard way this session).** Drak does not read linguistics or data-modeling jargon and was lost entirely by a jargon-heavy schema reply. Present every Glossopoeia decision in plain words with examples from his own conlangs (Ân-lâna agglutinative with evidentiality and no tense; Ethlinde/DPE fusional with four cases and an ensouled/unensouled split; Scrap glyph script). Avoid morpheme/exponence/paradigm/inflectional/derivational and entity/node/ref-able unless glossed on the spot. This is the standing register for the remaining design work.
- **Build prerequisites locked.** A multi-select field type (Drak: "build it") and the Language / Glossary supersede-and-migrate both come before or with the view at build time. The multi-select type is a hard dependency of most locked Glossopoeia schemas.
- **Orthography ships text-only; visual script assets are the single deferred carve-out from "hold everything."** Scrap's glyph chart and TTF wait on the world-scoped asset subsystem, which stays out of v1 (and Scrap migration is still gated on it). Diachronics is also out of v1, documentary-only if ever added.


=== ADDED 2026-06-21 — portability, value-driven refs, shared-label help, doc-sync ===

- **Whole-object portability = fresh ids + deep remap + name-relink + always-new** *(v1.5, Glossopoeia import/export)*. To move a self-contained object graph (a language and all its records) between worlds: regenerate every id on import and rewrite internal references through that remap; re-link references that point OUTSIDE the exported set by NAME, not id (store a name pointer on export, resolve it in the target on import, drop unmatched with a count); never overwrite or merge on collision — always add as new and let duplicates coexist. Fresh-ids is the only id strategy that survives importing into the world the object came from. Name-relink is the only way a cross-boundary reference survives a round-trip, because ids change. This is the per-language pattern; any future "export one X out of a slice" feature follows it.

- **Classify references by VALUE, not by schema** *(v1.5)*. When walking a record's fields to find references, treat a value as a reference iff it is a known record/entry id; leave everything else (multi-select options, select values, free text) untouched. Record ids carry distinctive prefixes, so a false positive is effectively impossible, and this avoids maintaining a per-record-type map of which fields are refs — and crucially it cannot mangle a multi-select array (its option strings aren't ids). The export classifier and the import remap both rely on this.

- **Remap nested ids with a recursive deep walk** *(v1.5)*. Internal reference ids can sit inside nested structures (grid cells: `{type:"entry-ref", value:"<id>"}`), not just at the top of `fields`. A recursive walk that remaps any string equal to a remap key — and leaves keys and non-matching strings alone — fixes top-level refs and grid-cell refs in one pass. Cross-boundary refs inside grid cells are NOT relinked (the export classifier only externalizes top-level values); that gap is documented, not silently lossy — the within-language case (the common one) survives.

- **One shared label component carries field help** *(v1.5, r102)*. Field-label tooltips were added at a single point — `FieldLabelText`, which both `EntryForm` (top-level fields) and `GroupEditor` (subfields) already use — by reading an optional `help` on the field. One change covered every labelled field including group subfields. Lesson: when a presentational concern (tooltip, badge, affordance) needs to reach every field, find the shared leaf component, don't touch each call site. The feature stays dormant on fields without `help`, so it's safe app-wide while being scoped by data.

- **A field-type addition is not done until the in-app docs name it** *(v1.5, r103)*. `multiselect` shipped at r088 but was absent from the Field Types guide section, the JSON field-type enum, AND the field-values table until r103 — the in-app guide silently lagged the engine for ~16 builds. Any new field type, save-shape key, or view must update `HOME_SECTIONS` (the guide) and the JSON Save File Schema section in the same batch. Stale doc counts ("eight views" while listing nine) are a symptom of the same lag; de-hardcode counts rather than maintain them.

- **Node-execution of extracted functions is a real verification tier below browser** *(v1.5, r104 import/export)*. For pure data logic embedded in the single-file app, extracting the actual functions verbatim into a Node harness with stubbed browser globals and asserting a round-trip catches logic bugs (remap, relink, classification) that a parse-gate and a read cannot. It does NOT substitute for browser verification — it says nothing about rendering, event wiring, or flash — but it raises confidence in the data path specifically. Use it for import/export, migrations, and remap logic; still gate the UI on Drak's browser pass.


=== ADDED 2026-06-22 — Phase 2 sequencing, phonotactic-validation rulings, warn-don't-block for derived feedback ===

- **Harvest a built substrate before opening the next one** *(v1.5, Glossopoeia Phase 2)*. Within all-in-one, when a substrate is done (the syllabifier, r109), the next build cashes it out into its tier features rather than starting a fresh substrate. The word generator and phonotactic validation both ride the syllabifier and need nothing else built first; the IPA rule engine opens a new substrate and waits. Sequencing principle, not a one-off: bank the value of the last thing built before paying for the next. (Drak delegated the actual ordering — "dealer's choice, as long as the end result is right" — which is what lets this principle drive it.)

- **One check, two directions** *(v1.5, r110–r112)*. Phonotactic validation and the word generator are the same "does this word obey the language's sound rules" check pointed two ways: validation runs it forward on save, the generator runs it backward to filter candidates. Build the check once; don't write a separate generator rule-set. The check needs no new schema — the Syllable Structure already stores the shape numbers (max consonants before/after the core, onset-required, which vowels can be a core) and Phonotactic Constraints store polarity + position + a sound-sequence pattern.

- **A lone "permitted" rule is documentary, not a closed whitelist** *(v1.5, r110, ruling a1)*. A "prohibited X in position Y" constraint is machine-actionable (match it, warn). A single "permitted X" record does NOT assert that X is the *only* thing allowed there, so treating permitted records as a closed allow-list invents warnings against legitimate words. Warn on prohibited matches and on syllable-shape violations only; leave permitted records as reference unless an explicit "these are the complete set of allowed onsets" mechanism is ever built.

- **Act on the machine-readable, flag the rest — never skip silently** *(v1.5, r110, ruling b2)*. A free-text field that's sometimes machine-readable (the Phonotactic Constraint Pattern: usable when it reads back as a sequence of the language's defined sounds, not when it's prose) gets acted on where it can be, and the cases the tool can't parse are surfaced as "not auto-checked" rather than dropped without notice. Visibility over silence: the user must know which of their records the tool is and isn't enforcing.

- **Derived feedback warns inline, never blocks, never auto-edits** *(v1.5, r110, ruling c1; nothing-destroyed applied to computed output)*. A computed check on a record (the phonotactic warning) shows inline next to the data it's about (under the Syllables line in the Lexicon), recomputed live, and never prevents a save or rewrites the user's input. This is nothing-destroyed extended from data to derived signal: the tool reports, the author decides. A whole-language report of the same warnings is a separate surface, deferred to fold into the lexicon-statistics work rather than duplicated per-word and per-report.

- **The validator is what makes the syllabifier honest** *(v1.5, r109→r110)*. r109's syllabifier caps the onset by count only and pulls everything else forward, so it neither checks whether a fronted cluster is a *legal* onset nor checks coda count at all. The phonotactic validator supplies both — legal-cluster checking and a coda-count test against Max Coda. The two builds are a pair by construction: the keystone produces the split, the validator judges it.


=== ADDED 2026-06-22 (later) — machine-checkable data lives in the structured field; model distinctions as data ===

- **A machine check reads the structured field, not the free-text descriptor** *(v1.5, r110–r111)*. The phonotactic check resolves a Prohibited constraint by reading its **Phonemes link** (a set of linked sounds) as membership — none of those sounds at the constraint's Position — and only falls back to reading the **Pattern** text as a literal sound-sequence when there's no link. Resolution order: Phonemes link → Pattern-as-sequence → not-auto-checked. The lesson came from a self-inflicted bug: the Ethlinde import was authored with the real data in the Phonemes link and the Pattern used as a human description, the check (r110) read only the Pattern, and the whole language came back "not auto-checked." When a record carries both a structured ref and a prose field for the same fact, the check keys on the structured one; authoring data that puts the checkable fact only in prose silently kills the check. Applies to any future executed-rule feature (the IPA rule engine will have the same fork).

- **Model a distinction as a field; don't infer it from how the text is worded** *(v1.5, r111)*. "Velars never cluster" means k/g are legal alone but banned in a cluster — a distinction the existing Phonotactic Constraint fields couldn't express. The rejected fix keyed on the word "cluster" appearing in the description, which only works for the one phrasing the author happened to use. The shipped fix added a closed-select **Applies When** field ("Anywhere at this position" default, or "Only in a cluster" = fires only when that position holds 2+ consonants), so the property is carried as data and holds regardless of wording or language. General rule: when a check's behavior depends on a distinction, promote the distinction to a field rather than heuristic it from prose. Pair it with a no-migration default (a blank value reads as the old behavior) so existing records are untouched.

- **A re-issued import artifact is canonical for the next import, not a patch to loaded worlds** *(v1.5, r111)*. Fixing a `.conlang.json` (the Ethlinde re-issue pre-set the velar constraint's Applies When) corrects the file a fresh import will produce; it does NOT reach into a world the user already imported, because import only ever ADDS records. A user who already loaded the old file fixes their world by hand (one dropdown here) or re-imports into a scratch world. State this whenever handing over a corrected artifact, so the fix isn't assumed to be retroactive.

- **Warn-only feedback survives an authoring bug as a quiet symptom, not a false positive** *(v1.5, r110)*. Because the check warns and never blocks or edits, the import-authoring miss surfaced as "everything reads not-auto-checked" (a visible no-op) rather than bogus warnings on good words or a blocked save. The not-auto-checked line is doing its job here: it tells the user which constraints the tool isn't enforcing, which is exactly how the dead check got noticed. Keep derived checks loud about what they're NOT doing.


=== ADDED 2026-06-22 (still later) — reopening a settled rule when it's the cause; generator and rendering-layer doctrine ===

- **Reopen a settled decision when it turns out to be the cause, with the same discipline that settled it** *(v1.5, r112)*. The r109 syllabifier rule was carefully settled, then the generator exposed it as the source of illegal output. Drak chose the root-cause fix over a ship-now patch ("it might be a larger build, but 3 is the correct one"). The fix was prototyped on the real lexicon and the old spike cases before the verified function was touched, exactly how r109 was settled. A settled decision isn't permanent; it's owed a re-proof, not a workaround, when it's the thing breaking. Note the cost: changing the syllabifier changed 114 of 599 displayed Ethlinde splits, so reopening a core rule is a visible change to every loaded world, which is the reason to be sure before doing it.

- **Sonority comes from the Manner field; it's the principle behind maximal onset** *(v1.5, r112)*. Each Phoneme's Manner (Plosive, Fricative, Nasal, Trill, ...) gives a sonority rank, and the syllabifier keeps the rising-sonority run as the onset. This is why the count-based version was wrong: "as many consonants as fit" front-loads consonants that sonority says belong in the previous coda. Any future phonotactic logic that needs to know whether a cluster is well-formed reads Manner, not a separate sonority field.

- **The generator is the check run backward, and inherits whatever the check doesn't enforce** *(v1.5, r112)*. Build a candidate, syllabify and check it, keep it only if clean and novel. Because a1 leaves Permitted constraints documentary, the check enforces no legal-cluster list, so the generator can't either; it leans on the sonority syllabifier as a proxy and still lets a sonority-legal-but-language-forbidden cluster through occasionally. The lesson for any generate-by-checking feature: it's exactly as strict as the validator, no stricter, so gaps in the validator are gaps in the generator. Output is a review list (novelty deduped on pronunciation within the active language, at generate time) rather than commit-straight, so the user vets before anything lands.

- **A view that owns its own slice needs its own export builder** *(v1.5, r113 design)*. The app's exporters (`buildMarkdownExport`, `buildHtmlExport`, the per-field renderers) all walk `state.entries`. A slice-owning view (Glossopoeia, like Ephemeris) is invisible to them, so exporting it is a new builder that reuses the field-render and HTML-style helpers but iterates the view's own arrays and code-built schemas. Same shape as the import/export work: the leaf helpers are reusable, the traversal is not. Plan slice exports as new builders, not as a flag on the entry exporter.


=== ADDED 2026-06-22 (r113–r115) — slice exports reuse the theme path; the rule executor is being built ===

- **A slice export reuses the entry export's theme path, not a bespoke stylesheet** *(v1.5, r113–r114)*. The grammar export first shipped with its own hardcoded light CSS and came out black-on-white against the app's dark default. The fix was to emit the live theme through `extractThemeVars()` into a var-driven `:root` (light defaults first, live theme on top), the same mechanism the entry/world HTML export uses, with print flipping to light so a dark page doesn't go to paper. Extends the earlier "slice-owning views need their own builder" rule: the traversal is new, but the styling and theming are shared. Don't author a second stylesheet for a second exporter; pull the theme the same way.

- **The deferred rule executor is being built (r115), partly reversing "rules are documentary"** *(v1.5)*. The 2026-06-18 design block parked the engine that would apply phonological rules. r115 builds it: the Phonological Rule records become executable, output as a computed surface line on each word, the same per-record-computed-value shape as the syllable split. The reversal is scoped, not blanket — only the rules the fields can carry run, and the rest stay documentary (below). The Sound Change records that diachronics will use share this rule shape, so the executor is the substrate for the apex too.

- **A rule's own fields are the executable spec; an environment is slot notation** *(v1.5, r115)*. Unlike the phonotactic constraints (whose checkable data sat in the Phonemes link, not the prose Pattern), a phonological rule's Input → Output / Environment fields are themselves the machine-readable rule, so there's nothing to scavenge. The environment uses slot notation: `_` for the changing sound's position, `#` a word edge, `V`/`C` any vowel/consonant, literal IPA for a specific sound, `∅` for deletion. Chosen over a dropdown builder because dropdowns can't express anything unanticipated, and slot notation is the standard the field already half-speaks (V/C are the Syllable Structure's vocabulary) and reuses the IPA palette. Rules apply in the Order field, each rewriting the string before the next, so feeding and bleeding fall out for free.

- **An engine runs what its inputs can express; the rest stays documentary** *(v1.5, r115, same principle as the constraints)*. The rule engine handles regular sound→sound or sound→∅ rewrites in a sound/V/C/# context. Two of Gutter Elf's rules stay documentary: vowel reduction keys on stress (not present in a bare phoneme string) and clipping is word truncation, not a sound substitution. The engine runs the ones it can (five executable rule records after the §9 apocope split) and doesn't pretend on the two it can't. Same honesty as the phonotactic check's "not auto-checked": surface what's executable, leave the rest as a recorded note, never fake a result.

- **Diachronics shipped as the apex, all-in-one** *(v1.5, r119–r121)*. This supersedes the earlier "diachronics is out of v1, documentary-only if ever added" stance (and the design-block note that the rule shape was for a future separate Sound Change entity). It forks a parent language into a descendant: clone the parent's lexemes + phonemes into a new in-world ConLang, author the historical sound changes, run them across the lexicon to derive daughter forms. Four doctrine calls came out of it. (1) **Diachronic is a flag on Phonological Rule, not a new entity.** A historical change has the same shape as a synchronic rule; a `Diachronic` select ({Synchronic, Diachronic}) carries the distinction, the synchronic surface-form readout filters diachronic rules out, the fork reads them in. Same lesson as r111's Applies When: model the distinction as a field, don't split into a parallel entity to infer it. The shared engine was split into a core `glossRunRules(pron, rules, phonemes)` taking explicit args plus the langId wrapper, so one runner serves both lifecycles. (2) **Ancestry and borrowing are different relations.** A new `Descended From` field (on Lexeme and ConLang) is the evolved-from link, kept distinct from Source Word (borrowing), Derived From (within-language), and Variety Of (dialect/register at the same time depth). A real lexicon has inherited words next to loanwords; one field can't carry both histories. (3) **Cognates are sibling links, not ancestor-descendant.** A daughter form isn't a cognate of its parent word; it IS that word evolved. A fork sets Descended From only; sibling cognates between two daughters of one parent are a separate operation, unbuilt. (An earlier draft's "auto-link parent and child as cognates" was the wrong relationship and was dropped.) (4) **A fork is a re-runnable derivation, not a one-shot.** Daughter forms always derive from the stored parent etymon, never from the child's current form, so re-running after fixing a rule gives a clean result instead of compounding; apply overwrites prior derived forms by design (the workflow is to fix the rules, not hand-tune words). Scope is lexicon + inventory only — grammar/syntax/orthography aren't copied, so the child gets an honest empty grammar rather than the parent's grammar wearing new sounds. Unrunnable changes (blank-Input insertion, stress-keyed, lexical) are listed and skipped, daughter forms reflecting only what ran, same documentary honesty as above.


=== ADDED 2026-06-22 (r115–r117) — varieties carry no inventory; paradigm generation; documentary fallback is now cross-feature ===

- **A `varietyOf` language is self-contained after import and carries no inventory, so per-language compute needs one given to it** *(v1.5, r115)*. Cartulary languages get fresh ids and no live inheritance on import. A sociolect that leaned on its parent's phonemes imports with zero phonemes, and every per-language compute function (syllabifier, validator, generator, rule engine) silently does nothing on it. Two ways to handle it: copy the parent's inventory into the child as data (what the Gutter Elf rebuild did, a per-file fix), or add a parent-inventory fallback to those functions (a code change, DECLINED 2026-06-23 — the future path for hand-authored varieties is a one-shot copy-parent-inventory action, not live fallback). Either way, the principle holds: compute reads the language's own records, so a language that should compute must own the inventory it computes against. Don't assume a `varietyOf` inherits anything executable at runtime.

- **Auto-paradigms read a class's grid cells as affixes over the headword stem** *(v1.5, r117)*. The inflection-class grids hold endings, not full forms, so a generated form is stem + ending: a cell is an affix (plain text appends, leading `-` strips, trailing `-` prefixes, (base)/=/blank is the bare stem), the stem is the word's romanized headword, and the lexeme's Irregular Forms grid overrides the generated table by row/column label so a word that breaks its class wins. The generated paradigm is computed per-word in the Lexicon, not stored, not exported yet, same shape as the syllable split and the surface form. A separate stem field is a later add for when a word's stem differs from its headword.

- **"Documentary for what can't be executed" is now the consistent rule across three features** *(v1.5, r110–r117)*. A phonotactic constraint whose pattern isn't machine-readable shows "not auto-checked"; a phonological rule the notation can't carry (stress-keyed, lexical) stays a prose note the engine skips; a paradigm cell that's a stem change rather than an affix shows its instruction text instead of a generated form. Each surfaces what it can execute and leaves the rest as a recorded, visible note, never faking a result. Any future executable-from-data feature follows this: run what the fields can express, mark the rest documentary, never silently drop or fabricate.

- **A grid cell's ref picker is scoped by a field flag, not per-cell config** *(v1.5, r116)*. GridEditor's cell ref picker is generic and targets any entry or registered node. Narrowing it (the Corpus interlinear to lexemes) is done with a `cellRefTemplatesId` flag on the field, which GridEditor reads, rather than per-cell configuration. The remaining limit: scoping to the active language's records needs `langId` filtering on registered nodes, which the ref editor doesn't do yet, so the scope is by type across all languages. Reach for a field flag when a generic editor needs narrowing; add the registered-node `langId` filter only when active-language scope actually matters.


=== ADDED 2026-06-22 (r117–r118) — the corpus is its own memory; workspace-level tools produce records; assist over auto-correctness ===

- **Existing records are the memory; don't add a parallel store** *(v1.5, r118)*. The matcher glosses a repeated word by reusing the gloss already given to that exact word elsewhere in the corpus, so corrections carry forward with no new state field and no sync to keep. Before adding a "remembered corrections" store or a cache, check whether the records already hold the answer. The corpus knowing its own prior glosses is cheaper and can't drift from the data it's derived from.

- **A tool that needs cross-cutting data runs at the workspace level and produces a record** *(v1.5, r112 generator, r118 matcher)*. The generic grid and ref editors only know the field they're handed. A feature that needs the lexicon, affixes, class endings, and the rest of the corpus can't live inside them, so it sits atop the workspace (a panel) and emits a new record the user then edits, rather than reaching into an open editor. Two features now follow this shape; treat it as the default for any Glossopoeia tool that spans more than one record type.

- **Ship the assist even when one tier is unreliable, as long as corrections stick** *(v1.5, r118)*. The matcher's memory and whole-word tiers are dependable; its stem+ending guess is wrong often on fusional words and can't be made reliable (drevae+n vs drev+aen is genuinely ambiguous from the data). That's fine, because the product goal isn't a correct auto-segmenter, it's that the user fixes each word once and never re-glosses it. The design names its own weak tier plainly rather than pretending the guess is trustworthy. Same honesty as the documentary-fallback rule, applied to a probabilistic step instead of an inexpressible one.

- **Prefer the better design over matching existing data, and flag the seam** *(v1.5, r118)*. The eight hand-built Gutter Elf corpus examples use two tiers (Form / Gloss); the matcher writes three (Word / Parts / Gloss), the real interlinear shape. New glosses look different from the old ones. The call was to build the better shape and flag the inconsistency, not to degrade the new feature to match legacy data. Note the seam when it appears so it reads as a known difference, not a bug.

=== ADDED 2026-06-23 (later) — delete-cascade; the worldbuilding/lexical-software line; one date formatter ===

- **Deleting a thing that owns records deletes its records.** *(v1.5, r124.)* `deleteConlang` removing only the ConLang record while leaving its words/sounds/rules keyed to a dead langId was a bug: the orphans surfaced as "Unassigned." A delete that the confirm dialog describes as removing "the language and its data" must cascade across every per-language array (and scrub cross-record references the removed records held). General rule for any owner→owned slice: delete cascades to owned records, and a reference held BY a surviving record TO a deleted one gets scrubbed (the pointer, never the holder). Corollary still open: deleting a parent language leaves children's ancestry links dangling; tolerated only because the graph and the derive step skip dead pointers, not because dangling is fine.

- **Cartulary models a worldbuilder's conlang; it is not a linguistics engine. The apex is the far edge and stays there.** *(v1.5, 2026-06-23, from the apex-polish decline.)* The diachronic fork (ordered sound changes over a lexicon) is real generative machinery and sits at the edge of the worldbuilding remit; it was taken knowingly (the all-in-one vs Lexurgy call). Going further was declined. Two declined items mark the line: (1) **stem-level paradigm derivation** — a correct fusional paradigm needs a real morphological model, and the right amount of that for this tool is the inflection-class grid plus the Irregular Forms override that already ship. A wrong auto-generated cell is fixed by typing the override. Building stem derivation re-solves a solved problem at permanent ten-year maintenance cost, and the moment a fusional edge case you didn't anticipate appears it breaks. (2) **per-word derivation locks** — a guard rail for a workflow not in use (the flow is fix-the-rule-and-re-run, not hand-finish daughter words). The posture for generated linguistic output is "good enough, override when wrong," not "compute it perfectly." The moat is the in-world population (the language living in the same graph as cultures, regions, characters, with cross-refs and the family tree), not the rule math. Standalone conlang tools out-compute Cartulary on purpose; that is not the competition. The one concession to legibility worth making is CSV import (the door for other people's existing lexicons), deferred but live on the roadmap.

- **One date formatter; the user picks the format per calendar.** *(v1.5, r125.)* All date rendering routes through a single formatter (`formatCalendarDate`) that switches on `calendar.dateFormat` (a closed-set preset, not a custom token string). Do not reintroduce a second app-wide date formatter: the retired `formatDateGedcom` was exactly that, and a duplicate formatter means dates render inconsistently across views (a field one way, a timeline label another) and the user's choice governs only some of them. Format lives on the calendar, not the world, so multi-calendar worlds differ and the setting travels with import/export. Month abbreviation is user-authoritative: the user's typed value is kept verbatim (case included); only the auto-derived default normalizes. When adding any new surface that prints a date, call the one formatter; never slice a month name inline.


=== ADDED 2026-06-23 (later still) — the new-built-in re-skin test ===

- **A new built-in template earns its place by carrying an axis the nearest existing template structurally cannot, not by relabeling its fields.** *(v1.5, r126, from the House / Dynasty / Clan / Bloodline add.)* The objection to any new built-in is "that's just <existing template> with different words."
