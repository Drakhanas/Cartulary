# Cartulary doctrine -- cartulary.world documentation principles (REFERENCE)

> Carved out of `cartulary-doctrine.md` (verbatim) during the session-10 docs-diet. Site-build doctrine. Load during cartulary.world work; append new site principles here.

## cartulary.world documentation principles (added 2026-06-25)

- **Ground in the component, not the in-app help.** The in-app help proved incomplete on multiple views (Linea missing zoom/view-calendar/shift-click; Concordance feed list missing grid-cell/group refs; Stemma missing Delete-node; Field Types missing Longform Note + Grid; month reorder framed as fragile when it is actually name-tracking and safe). Always read the actual component before writing a documentation page.

- **Fix-on-find rule.** An error caught on one page is fixed everywhere it appears retroactively, in the same session. No deferred corrections.

- **Sub-tile pattern for compound views.** Ephemeris and Glossopoeia follow the Timelines model: one parent panel with sub-tiles at the top; `SUB` table + `showSub()` for content switching; `samePanel` detection to suppress scroll. Sub-tiles always precede intro prose so they appear directly under the main launchpad.

- **SOON/LIVE table discipline.** When a route goes live, update both the tile class (`soon` → live, `href="#"` → `href="#route"`) AND the JS `SOON` table (remove entry) AND the `LIVE` table (add entry). All three gates must change together. Missing any one produces a broken-looking tile or non-functioning click.


=== ADDED 2026-06-26 (session 3) -- a persistence fix must audit the state it starts persisting; em-dash verification covers entities ===

- **When a fix flips state from discarded to durable, audit the producer of that state -- the discard may have been masking a bug.** *(v1.5, r131 -> r132, Concordance.)* The concordance prune was stripping Astronomical Body / Glossopoeia node positions on every load. r131 fixed that (keep them), which immediately surfaced a latent layout bug: the force simulation had no `forceX`/`forceY` containment (`forceCenter` only recenters the centroid, it exerts no restoring pull), so disconnected nodes had always scattered -- the per-load strip-and-recool was hiding it by re-randomizing each time. r131 froze the scatter; r132 added containment and a one-time reset of the now-garbage saved positions. Lesson: a "values were being thrown away" fix is never just a one-liner. The thrown-away values were produced by something, and nothing downstream was validating them because they never survived. Before persisting them, check the producer (here, the force layout) and plan a one-time cleanup of the pre-fix garbage (idempotent, flagged) so existing files recover instead of inheriting frozen bad state. Synthetic-node positions were safe to wipe once precisely because they were never reliably persisted before -- a value users could not have depended on can be reset without loss.

- **Em-dash verification must match the HTML entity forms, not just the literal U+2014.** *(cartulary.world, 2026-06-26; refines the r130-era "Python not bash grep" rule.)* The literal-only Python check reported 0 em dashes while 38 `&#8212;` entities sat on the shipped pages rendering as em dashes. The no-em-dash rule is about rendered output, so the check must also match `&#8212;`, `&mdash;`, and `&#x2014;`. "Em-dash-free" means none of those four forms appear, verified in Python (bash grep still silently misses U+2014 in the shell locale).

- **A documentation overclaim found during an audit can be resolved by fixing the product instead of caveating the docs, when the line is still open.** *(cartulary.world + v1.5 r131-r132, 2026-06-26.)* The Concordance page claimed hand-laid layouts "survive reload, export and re-import," with "lay your stars into a star map" as the headline example -- but synthetic-node positions were being stripped every load, so the claim was false for exactly that example. In a frozen release the honest move would be a temporary caveat; in the fluid Final Release state the better move was to make the claim true (r131-r132) and leave the aspirational copy standing. Prefer fixing reality over documenting a limitation when the code line is still open and the claim is the intended behavior.


=== ADDED 2026-06-26 (session 4) -- a logged fix is not a shipped fix; the hard-check checklist gains index rows + stats bars ===

- **A changelog entry claiming a fix is not proof the fix is in the artifact -- re-verify against the file.** *(cartulary.world, 2026-06-26.)* Two Concordance site corrections logged in the session-3 block (wiki-links work in "any text field"; ghost-cleanup is "node"-general) were absent from the working helloworld.html when it came back this session. Whether the edits were lost or never saved does not matter: the doc said done, the file disagreed. Fix-on-find applies to the docs' own claims. When a hard check re-touches a page a prior session reported as fixed, confirm the fix is actually in the bytes, not just in the changelog.

- **The two surfaces a view page most reliably under-documents: the index/list row, and the stats bar.** *(cartulary.world, 2026-06-26; per-page hard-check checklist addition.)* Across five pages this session the misses clustered: Cartographia and Stemma index rows each carried more columns than the prose enumerated (node/pin count, last-updated date, tags); Concordance and Linea each had an undocumented count bar along the bottom edge of the canvas. Prose naturally describes the marquee interaction and skips the chrome. Add to every per-page hard check: (a) read the list/index row's full JSX and enumerate every column it renders, and (b) check for a stats/count bar at the canvas edge and document it.

- **Re-verify your own prior site copy against the component, not just the in-app help.** *(cartulary.world + Linea, 2026-06-26; extends "ground in the component.")* The Linea page had the canvas click model backwards -- it claimed a plain click was "reserved for dragging the canvas" and documented only Shift+click, when the component refocuses the tree on a plain node click and pans only on empty-space drag. This was not an in-app-help inheritance; the site prose itself was wrong and read plausibly. "Ground in the component" means re-reading the component even for a page that already exists and reads fine -- plausible-but-wrong is exactly the failure a hard check exists to catch.


=== ADDED 2026-06-26 (session 5) -- the logged-not-shipped pattern is a lineage break, not a one-off; reference and intro pages get hard-checked too; nav/tile parity may carry a deliberate exception; glyph accuracy is exact-codepoint ===

- **When a session's logged fixes are found missing from the file, treat it as a lineage break and re-audit everything that session touched -- not just the page in front of you.** *(cartulary.world, 2026-06-26; escalates the session-4 "a logged fix is not a shipped fix" rule.)* Session 4 caught two Concordance fixes that were logged in session 3 but absent from the working file. Session 5 found that was not a one-off: the Glossopoeia count/enumeration fixes, the entire Ephemeris label batch, and 29 of the "38 em dashes swept" were all logged in session 3 and all missing from the bytes. The pattern is not "a fix occasionally slips"; it is "an entire session's edits failed to carry into the file that became the next baseline." So the response is not page-local. When you find one logged-but-missing fix from a session, assume the whole session's output may be missing and re-verify every page that session touched against the actual file. Here that means Timelines (session-3 touched, only its em dashes re-verified since) is suspect until re-read. The cheap guard going forward: at session close, after the doc batch, re-grep the shipped file for the specific strings the session claims to have changed, and record the grep result, not just the intent.

- **Reference and intro pages are not exempt from the hard check just because the views are done.** *(cartulary.world, 2026-06-26.)* "The views have had three or four passes each, move on" is true for the views and false for the site. The two reference pages (Fields, Templates) and three of the intro pages (World settings, Concepts, Get started) each carried live errors when first hard-checked this session: an incomplete toolbar list and a wrong secret-toggle glyph on Fields; a mischaracterized Export control on Templates; a mis-sectioned Variant Filter, a wrong backup-reminder threshold, and a fabricated second Danger Zone control on World settings; a stale "guides on the way" on Concepts; a false "nothing is required" on Get started. "Views done" and "site done" are different claims. Every page that makes a factual claim about the component gets the same component-grounded read, reference and intro pages included.

- **A documented icon must be the exact codepoint the component renders; a visually similar glyph is still wrong.** *(cartulary.world, 2026-06-26, from the Fields secret toggle.)* The page documented the secrets-on glyph as `&#9689;` (◙, inverse white circle); the component renders `&#9673;` (◉, fisheye). They look alike at small size but are different characters, and a reader matching the doc against the on-screen icon would mismatch. Verify glyph documentation by the codepoint in the component source, not by eye. (The in-app help had the right pair; only the site was wrong, so this was a site-prose error, not an inheritance.)

- **A consolidated reference page is the honest way to surface a capability that is scattered across many pages; a nav-only home is allowed to break tile/nav parity by design.** *(cartulary.world, 2026-06-26, Import & Export.)* "Sharing needs more visibility" framed as a templates-and-packs concern was a quarter-truth: the export/import surface spans seven artifact types (world json/md/zip/HTML, template, pack, conlang + grammar, stemma, calendar) across six pages. The strong fix was one consolidated page that inventories all of it, with reciprocal cross-links from the owner pages, rather than promoting one slice in place. It was placed nav-only (a flat nav item, no launchpad tile) to keep the locked 3x5 grid, which makes it the first route reachable from the nav but not the launchpad. That parity break is deliberate and documented in the handoff so a future reader does not "fix" it by adding a 16th tile; whether sharing earns a tile is a 15->16 grid decision, not a bug. Correct the premise of a visibility request before building to it, and prefer consolidation over half-measures when a capability is genuinely scattered.


=== ADDED 2026-06-26 (session 6) -- in-app help is part of "feature complete" while the line is open; surface classes can multiply by design; the licensing rationale, recorded; deploy-time SSL is cert-provisioning, not the page ===

- **While the version line is open, embedded in-app help is a ship requirement, not v.next backlog.** *(v1.5, 2026-06-26.)* Across the cartulary.world hard check, grounding the site against the component repeatedly surfaced in-app help strings the component itself contradicts (wrong json-schema shapes, stale field/template lists, an undercounted enum, a wrong "leaves edit mode" claim, a section called "Moons" that renders "Celestials," a phantom "glossary" entry type). The default reflex was to log each to a v1.6 in-app-help backlog. The correct call, while v1.5 has not yet shipped, is the opposite: sweep them all into the current line (r133) before release, because "feature complete" includes the help a user reads inside the app, and shipping with two help strings fixed and ten still wrong is the inconsistent outcome. This extends the session-3 rule ("fix reality instead of caveating the docs when the line is open") one step inward: the product's own help text is reality too. The boundary is the ship event, not the version number -- once the finals upload, remaining help nits are genuinely v.next; until then they are in scope. The cost is real (an r-bump and a finals re-cut), and that cost is acceptable specifically because the line is already open and the finals re-cut is already owed.

- **A scattered or low-fit fix is better consolidated onto its own surface, and the site may carry more than one surface class by design.** *(cartulary.world, 2026-06-26, Colophon; generalizes the session-5 Import & Export rule.)* The site now has three deliberate surface classes for routed panels: tile + route (the locked 3x5 launchpad), nav-only (Import & Export, a consolidated reference that did not warrant a tile), and footer-only (Colophon, the build / license / accessibility / disclosure page that belongs at the bottom, not in the primary IA). Each parallel-surface exception is intentional and documented so a future reader does not "regularize" it by forcing everything back onto tiles. The router already tolerates routes with no tile and no nav entry: `setActive` guards both the scroll-spy lookup and the nav-link query, so a footer-only or nav-only route resolves on the same path as a tiled one. When a page's content does not fit the dominant surface (a 16th item would break a locked grid; a colophon does not belong in a feature launchpad), give it the surface that fits and record why.

- **The licensing rationale, so it is not re-derived each time the name on the license gives pause.** *(2026-06-26.)* MIT *requires* the copyright line (CC0 / Unlicense are the public-domain-dedication options that drop the name; MIT is not one of them). MIT's validity does not depend on the entire codebase being copyrightable: it grants whatever rights exist, plus the attribution requirement and the warranty disclaimer, and the disclaimer stands regardless. "AI-written software is uncopyrightable" is too strong: per USCO guidance (Part 2, Jan 2025; Thaler affirmed by the D.C. Circuit, Mar 2025), purely AI-generated output is not protectable, but a human's selection, arrangement, and creative control over the work is, assessed case by case. Cartulary's REAL 4 profile (Drak directs architecture, schema, scope, and QA; AI implements under direction) is the strong protectable case, the opposite of the denied "prompt and accept the output" cases. The copyright line uses the legal name (Shawn Fry), not the handle, because the pseudonym is not a separate legal entity. The splash taglines are public-domain-safe: they are short paraphrases of ancient creation texts attributed to the tradition, not reproductions of any copyrighted modern translation. (None of this is legal advice; it is the standing rationale for the choices already made.)

- **A static site reading "not secure" immediately after deploy is almost always the TLS cert not yet provisioned, not a problem with the files.** *(cartulary.world deploy, 2026-06-26.)* On Porkbun static hosting the free Let's Encrypt cert auto-issues, but only when the domain uses Porkbun's nameservers, and provisioning lags DNS by the normal 5-45 minute window; until the cert is live the host serves bare HTTP and the browser flags it. Mixed content (an HTTPS page pulling an HTTP asset) is the other classic cause, and it is permanently ruled out for these files because they have zero external resource loads (everything inlined) -- so if Cartulary's site ever reads insecure, it is the cert, never the page. The diagnostic order: confirm the cert exists in the host panel (it did), confirm Porkbun nameservers (required for auto-issue), check apex-vs-www coverage, then wait out the window before suspecting misconfiguration. It cleared itself well inside the window.


=== ADDED 2026-06-26 (session 7) -- an audit list is a floor not a ceiling; the offline build needs the standalone fallback by design; favicon is per-file; Concordance opens empty by design ===

- **An itemized backlog assembled as a side effect of a different task is a floor, not a ceiling -- read the surrounding surface, not just the list.** *(v1.5, r133.)* The r133 in-app-help list came out of the session-3-to-6 cartulary.world hard check: it was whatever grounding the site happened to surface, not a dedicated audit of the embedded help. Working the list immediately turned up three more code-vs-help mismatches in the exact surfaces being edited (the viewPrefs calendar keys sat in the same json-schema block as the orbital-element fix; the Templates help omitted the House/Dynasty built-in while listing two removed ones; the Field Types help omitted Grid alongside the omitted Longform Note). Fix-on-find covers these: when you are already in a surface correcting one documented mismatch, read the whole surface against the component and fix every mismatch there, not only the listed one. Treat any list whose provenance is incidental as a starting point, and verify completeness by reading the component, not by exhausting the list.

- **New or edited in-app help text is em-dash-free; the pre-existing em-dash corpus is left alone (replacements-only).** *(v1.5, r133.)* The embedded help carries ~1,114 U+2014 em dashes, authored before the no-em-dash rule. The rule applies going forward: bullets and sentences Claude adds or rewrites use colons or restructured punctuation, never em dashes. It does not trigger a corpus-wide strip of the existing 1,114 -- that is a separate, larger, higher-regression pass that nobody has asked for. "Replacements only" keeps the diff scoped to the help being corrected. If a full in-app-help em-dash strip is ever wanted, it is its own task with its own verification, not a rider on a content fix.

- **The offline dual-build requires the @babel/standalone fallback in compile_jsx.js; a bare require("@babel/core") is a cold-start blocker.** *(build infra, session 7.)* The dependency tarball set ships @babel/standalone only -- there is no @babel/core in the offline node_modules. compile_jsx.js must try @babel/core first (transformSync + @babel/preset-react, for environments that have it) and fall back to @babel/standalone (transform + the bundled "react" preset, classic runtime) when core is absent. The /mnt/project copy had lost this fallback while the handoff still described it, so a fresh-container build failed on the first JSX compile with MODULE_NOT_FOUND. Lesson: the build's library expectations are part of the build, and a doc that says "has a fallback" is not the same as the file having one -- verify the fallback is present in compile_jsx.js before trusting any synced copy, and keep build_inline.py and compile_jsx.js in the /mnt/project sync set, not just the HTML and the docs.

- **A favicon must be declared inline on every site HTML file; a missing declaration is invisible locally and blank on the host.** *(cartulary.world, session 7.)* index.html shipped with no <link rel="icon"> at all, yet showed an icon locally -- the browser was serving a cached or sibling-directory favicon for the folder, which masked the omission. On the live host the apex requested /favicon.ico, got a 404, and rendered blank, while helloworld.html (which carries the inline data-URI icon) showed correctly on both. The local "it works" was an artifact of the dev environment, not evidence the file was correct -- the same plausible-but-wrong trap the hard check exists to catch, here on the host instead of in the prose. Every site HTML file gets its own inline favicon declaration (the locked data-URI mark), verified against the host, not against a local open. Fix-on-find applies across all site files.

- **Concordance opens to an empty template filter by design; do not "fix" it back to all-on.** *(v1.5, r134.)* The Concordance template filter defaults to no boxes checked (blank graph on open) rather than all-templates. The reason is import scale: a large imported world rendered all-on cooks the entire force layout on first open and presents as a single illegible glob. Empty-on-open defers the cook and lets the user opt in per template; the all / none links make recovery one click, and the checkbox list still enumerates every template. The filter is per-session (resets to empty on reopen, not persisted), and the change is Concordance-only -- the other views' filters stay all-on. A size-threshold variant (full graph for small worlds, empty only past N nodes) was considered and declined in favor of blanket-empty for simplicity and uniform behavior. If a future reader sees the empty default and assumes it is a regression, it is not: it is the glob-avoidance default.

- **While the line is open, the ship boundary is the upload, not the version number -- and that includes help, build infra, and any small UX call that lands before the smoke.** *(v1.5, session 7; generalizes the session-6 in-app-help rule.)* Session 6 established that embedded help is part of "feature complete" while the line is open. Session 7 confirmed the same boundary holds for adjacent work: a UX default change (r134) and a build-infra fix both landed into the still-open v1.5 line rather than waiting for v1.6, because the finals re-cut and browser smoke were already owed. The cost of folding work into an open line is an r-bump and a finals re-cut, and that cost is already sunk while the line is open. The discipline is the inverse once the line closes: after the itch upload, the same changes would be v1.6. Decide by the ship event, not the version label.

- **The line closes at the upload; reset to the next minor only after the finals are live.** *(v1.5, session 8.)* The r-counter resets and the VERSION bump in build_inline.py happen only after the finals actually ship to itch, not when the build is feature-complete or even when the finals are cut. Session 7 left v1.5 "feature-complete, finals cut, browser smoke owed" and the line stayed open; session 8 passed the smoke, uploaded, and only then closed the line (VERSION 1.5 -> 1.6, r-counter -> r001). The shipped cut's r-number (r134) is the final r of that minor line; nothing in the next session reuses it. This is the close-side companion to the open-line rule above (ship boundary is the upload): both decide by the ship event, not the version label or the build state.

- **A launch session produces no r-bump.** *(v1.5, session 8.)* The session that ships the build (browser smoke, upload, favicon/infra sync, all the marketing copy) touches no product HTML, so it carries no r-number. The r-counter increments only on HTML changes; writing the itch page, the devlog, the README, the patch notes, and the community posts is not an HTML change. The changelog still gets a dated ship entry; it just records the upload and the copy, not a code iteration.

- **User-facing patch notes are a separate artifact from the changelog.** *(v1.5, session 8.)* The changelog is the internal r-by-r development record (jargon, r-numbers, build internals, bug-audit row IDs). Users get a clean PATCHNOTES.txt: feature-level, no r-numbers, no internal terms (no "synthetic templates," "registry," "absolute-day space"), plain text so it opens on double-click from the zip. Do not ship the changelog to users and do not let the patch notes drift into r-number territory. They serve different readers.

- **Marketing copy is em-dash-free on the way in, not after the fact.** *(v1.5, session 8.)* Source material carried over verbatim (prior itch pages, old README, prior community posts) tends to be full of em dashes from before the rule. Strip them while drafting, not in a cleanup pass after Drak catches them. Same Python-only verification as the in-app help (bash grep silently fails on U+2014 in the shell locale). En dashes in numeric ranges (1,500–2,000) are correct and stay.

- **Product name discipline extends to all built-in counts in published copy.** *(v1.5, session 8.)* The user-facing built-in template count is 20, not 21. The Map template exists internally but is not presented or counted as a user template (it is reached through Cartographia's "+ New Map," hidden from the Templates sidebar). Any published count — itch page, README, posts — says 20. The handoff's internal "21 user templates" phrasing was wrong and was corrected; if it resurfaces, it is the Map miscount.

- **An end-of-line file renamed to the next minor is a status marker, not a code change.** *(v1.6, session 9.)* When a version ships, the final working file may be renamed to the next minor (e.g. `Cartulary_v1.6_Working_r000.html`) to show the line has opened. That r000 is byte-identical to the shipped code except the filename: no r-counter movement, no in-app change. The first code-changed cut is r001, and that is where the in-app/export version-string literals flip (the export `<meta name="generator">` and the "Generated by Cartulary vX.Y" footer), they are an HTML change and move the r-counter, so they do not belong in the r000 rename baseline. `build_inline.py` `VERSION` drives the output filenames only, not those literals; bump it when the line opens, flip the literals at r001.

- **The cost of promoting a template to a view is gated by its graph coupling, not its field count.** *(v1.6, session 9.)* A promote-to-view severs the object from the entry-graph; the registry is the seam it re-registers through. The expensive part is inbound coupling: if other entries ref the object (lexemes are ref targets), the promotion must rebuild full ref-resolution through the registry. An object that is a graph LEAF, outbound-only edges, no inbound refs, already isolated from the general entry surfaces, is cheap (maps: pins point out, nothing points at a map, already hidden from the Templates sidebar and `EntryList`). Size the coupling before committing to the promotion; "barely a template" by field count can still be expensive if it is a ref target, and a multi-field template can be cheap if it is a leaf.

- **Maps-as-a-view synthesis pattern.** *(v1.6, session 9.)* A slice-backed view that needs both a canvas and form fields composes from two precedents: Stemma for storage/index/multiplicity (a flat top-level array, no per-template grouping, an index that lists the array and opens by id) and Glossopoeia for the fields (rendered through the shared `EntryForm` via a fixed `*Schema()` function), with the bespoke canvas (`MapView`/`MapEditor`) on top. Reuse beats hand-building: the fields ride the existing form engine, the index rides the Stemma shape.

- **A pure architecture move's success test is invisibility, and it must be scoped to the data model only.** *(v1.6, session 9.)* Promoting maps to a slice is the same kind of change as the modularization refactor: if a user notices anything different, it overreached. Promotions are exactly where adjacent features sneak in ("while I'm in here, add import/export / tweak the editor / redo the index"). Defer every adjacent feature; solve only the storage move. The acceptance test is a shipped-baseline world loading with identical rendering, identical graph nodes/edges, identical export.

- **Modularization gate design: two gates, two failure modes.** *(v1.6, session 9.)* A module-scoped (pass-like) editing workflow introduces failures the monolith never had: stale-slice edits going in, silent reassembly drift coming out. First-step VERIFY (before editing a module) is a context-completeness check, the loaded module + spine match the manifest's declared seam, the spine and module copies are the same r-number (a module carved against an older spine parses fine and is still corrupt, which the parse gate cannot catch), and the module reaches nothing outside its declared imports. End-step CONFIRM (after split/combine) is a reconstitution-parity check, for a pure split, a normalized diff against the pre-split build must show zero substantive delta; for a combine, parse-gate -> normalized diff scoped to the intended change -> browser smoke. The parse gate stays hard between them; browser smoke stays the only proof a path runs. The normalized diff needs a defined normal form (strip module wrappers, normalize join points) built into the validator, or it drowns in noise and gets ignored by the third split. The manifest is the oracle both gates check, append-updated in the same pass as every split/combine (same discipline as `FIELD_RENAMES`). And modular SOURCE only relieves AI/context cost if the EDITING workflow goes module-scoped too, load spine + one module, not the assembled tree; otherwise it buys navigation only.

- **Turnover is full integrated documents, history preserved verbatim, never append-snippets to merge by hand.** *(v1.6, session 9; correcting a prior mis-statement.)* On turnover, changelog / roadmap / doctrine are delivered as complete files: all prior content byte-exact, with the new dated block integrated, ready to drop in. The handoff is fully rewritten each batch. The journal entry is the one new session entry for manual paste. "Append-only" describes the CONTENT discipline (past entries are never rewritten or reworded; new content is added, not edited over history), it does NOT mean handing over a fragment for Drak to append himself. Deliver the whole file every time.
